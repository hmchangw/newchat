## Top-line risk assessment

**Do not merge as-is.** The PR correctly identifies a real security bug (#414) and the *core* idea — active eviction of the L1 access-check cache, keyed identically to the read path — is sound, well-commented, and genuinely tested at the unit level (`readcache` coverage 92.4%, `go test -race ./history-service/...` passes clean).

The risk is not in the eviction itself but in the four hardening mechanisms bolted around it, each of which carries independent, unreviewed failure modes:

- **Availability regression (critical).** The generation counter that guards against evict/load races is *cache-global*, not per-key. A bulk membership operation — HR sync, org removal, a Teams room reconcile — bumps it thousands of times per second, which forces every concurrent in-flight load on *unrelated* keys to re-read up to 5 times and then fail closed with a hard error. That error surfaces as a failed `msg.history` read for users who have nothing to do with the membership change, with 5× read amplification onto a now-`primary`-pinned Mongo. Three lenses found this independently.
- **The headline mechanism is partly unverified.** The evict-cancels-in-flight-load path returns `context.Canceled` *before* the generation retry runs, so on a real ctx-respecting source the retry loop is dead code and an eviction errors a concurrent reader's request instead of re-reading. The test that appears to prove the retry uses a fake source that ignores its context.
- **The hole is not fully closed.** The suspend/resume barrier covers NATS *disconnects* only. A core-NATS slow-consumer drop — likely precisely during the bulk removals this feature exists for — loses evictions with no disconnect, no error, and no metric, silently reverting to TTL-only staleness. Cross-site (federated) removals publish no `subscription.update` at the destination site at all.
- **It is unobservable.** Nothing counts evictions, suspensions, retries, or either fail-closed path. A dead subscriber or a renamed subject degrades silently back into #414.

Two further issues are worth calling out because they mean the PR does not do what its description says: `SUBSCRIPTION_READ_PREFERENCE` never reaches the access read it claims to protect (the real path was already pinned to `primary`), and the eviction subscription is a non-queue wildcard that delivers every user's high-frequency `read`/`mute`/`favorite` events to every replica, decoded in full before being discarded ~99% of the time.

**Recommended shape:** land the eviction + the subject/ctx/metric fixes as a tight PR; split the semaphore, the cancel-on-supersede, the generation counter, and the read-preference change into separate changes that can each be reasoned about on their own.

# Go expert

## critical

None at this lens.

## high

**1. `cancel`-on-supersede makes the generation-retry loop dead code in production.** `remove` cancels the in-flight `fetchCtx` (`internal/readcache/readcache.go:117-120`), but `getOrLoad` checks `err` *before* the stability check and returns (`:226-228`). A real Mongo load returns `context.Canceled`, so the retry loop at `:207-246` never runs on the exact race it was written for — the caller gets an error instead of a fresh read. It only *looks* exercised because `gatedSubSource` in `readcache_test.go` ignores its ctx. Pick one strategy: drop the cancel, or treat a `fetchCtx`-sourced `ctx.Err()` as "superseded → continue".

**2. The global `gen` and cancel-all now apply to `PreviewCache`, which is invalidated per room mutation.** `PreviewCache.Invalidate` (`readcache.go:497`) calls the same `remove` (`:111`) and is hit on every mutation (`internal/service/messages.go:690`). A preview invalidate for room X now bumps a cache-global generation that forces in-flight preview loads for *every other room* to re-read, and after 5 races returns a hard error (`:247`). Before this PR, `remove` was `lru.Remove` only. Scope the generation (per-key, or only on the sub cache) before merging.

## medium

**3. Unsynchronized read of `nats.Conn.Opts`.** `cmd/main.go:308` and `:316` read `raw.Opts.ReconnectedCB` / `raw.Opts.DisconnectedErrCB` directly. nats.go guards those fields with `nc.mu` (`SetReconnectHandler` locks; `doReconnect` reads under lock), so this is `-race`-visible. Also, a disconnect between `natsutil.Connect` and line 307 is silently missed. Better: a chaining option in `pkg/natsutil/connect.go:84-93`, set at connect time.

**4. Cache key duplicated by hand.** `account + "\x00" + roomID` appears at `readcache.go:312` and `:339`, with a comment asking readers to keep them identical. Extract `subKey(account, roomID string) string`.

**5. Dead sentinel + contradictory docs.** `readcache.go:36` says "0 disables it", `:78` mentions "a nil sem", but `newTTLCache:92-94` always allocates, so `if c.sem != nil` (`:181`) can never be false. `config.go` ("0 takes the package default") is the accurate one. Delete the dead branch and fix both comments.

**6. Semaphore slot held across all retries.** Acquired once at `:181-196` and released by `defer` after the loop, so one leader can pin a slot for up to 5×`fetchTimeout` (~50s), on top of a possible 10s acquire wait. Acquire per attempt, or put one deadline over the whole `DoChan` body.

## low

**7.** `cmd/subinvalidate.go:81` subscribes non-queue to `chat.user.*.event.subscription.update`, so every replica JSON-decodes every account's events — including high-frequency `read` / `mute_toggled` — before the action filter at `:44`. Acceptable in principle, but the fan-in is worth a note.

**8.** `errors.New(...)` at `readcache.go:247` is anonymous; make it a package sentinel so callers can use `errors.Is` instead of matching text.

**9.** `newTTLCache` grew a bare positional `int`; `defaultMaxInflight` is then passed explicitly at `:395`, `:399`, `:504` where `0` already means the same thing. Thread `CacheOption` down instead.

## nitpick

**10.** `for attempt := 0; attempt < maxLoadAttempts; attempt++` (`:208`) never uses `attempt` — Go 1.25 allows `for range maxLoadAttempts`.

**11.** The doc block above `remove` (`readcache.go:98-110`) opens with "getOrLoad returns…", so godoc attributes it to `remove`. Pre-existing, but this PR tripled its size.

## Clean

Error wrapping is consistently `fmt.Errorf("short description: %w", err)` — no bare `err`, no `"error: %w"`. No `time.Sleep` synchronization, no unterminated goroutines, no string error comparison, no silently swallowed errors. `evictor` is correctly consumer-defined and unexported; `encoding/json` (not sonic) is the right codec for this path; config validates and fails fast; lock ordering between `c.mu` and `singleflight` is non-nesting and safe.

# Performance

**1. [high] Non-queue wildcard subscribes every replica to a high-frequency event it almost always discards.** `cmd/subinvalidate.go:78` subscribes to `chat.user.*.event.subscription.update` with no queue group. That subject carries `read`, `opened`, `mute_toggled`, `favorite_toggled`, `section_moved`, `role_updated` (`room-service/handler.go:1464,2228,2305,2421,2487`) — `read`/`opened` fire on essentially every room open. Only `added`/`removed` are acted on (`cmd/subinvalidate.go:41`), and the filter runs *after* a full `json.Unmarshal` of the ~30-field `model.Subscription` payload (`:61`).
*Order of magnitude:* 10k DAU ≈ 500–2000 evt/s site-wide × ~1 KB × N replicas → **5–20 MB/s of NATS egress and 5–20k deliveries/s fleet-wide to drop ~99% of them.** Worse, `o11ynats.Conn.Subscribe` starts a `SpanKindConsumer` span per message (`otelnats/conn_traced.go:~261`), adding **500–2000 spans/s per replica** of pure noise. Fix: have publishers emit boundary-changing actions on a distinct subject/token, or at minimum gate on a `bytes.Contains` of the action before unmarshalling.

**2. [high] `gen` is global, so one eviction invalidates every in-flight load in the cache.** `readcache.go:111-124` bumps a cache-wide counter; `:236` fails the stability check for *any* key loading at that moment, forcing a full re-read (up to 5, `:207`) and then a hard `errors.New(...)` (`:247`) that surfaces to an unrelated user's `msg.history` as an internal error.
*Amplification ≈ evictRate × loadLatency:* a bulk 500-member add emits 500 bumps in a burst; with ~1 ms L2 loads that is ~50% of concurrent misses retrying, plus a real tail of fail-closed 500s for readers of *other* rooms. The `ponytail:` note at `readcache.go:63` acknowledges this — per-key generations are the fix and are cheap (one `map[string]uint64`, already guarded by `mu`).

**3. [high] The semaphore is a 10s queue with no deadline propagation, not load shedding.** `readcache.go:187-195` waits on `context.WithoutCancel(ctx)` + `fetchTimeout`. The caller has already given up at `:258`, but the leader keeps queueing, then loads, and may loop 5×10s (`:208-209`) — up to **60s of detached work per abandoned request**, occupying one of only 256 slots. Under slow Mongo this is strictly negative: it converts a latency problem into retained work and, eventually, `load slots exhausted` errors after a wait longer than any client timeout. The wait bound should be the caller's *remaining deadline* (a few hundred ms), not `fetchTimeout`.

**4. [medium] Reconnect purge is a fleet-synchronized cold start.** `readcache.go:155` + `cmd/main.go:~310`. A cluster-wide NATS blip purges 100k entries on every replica at once; L1 hit rate goes to 0 for the 2m TTL window. Mongo is largely shielded (the loader goes through the 90m Valkey L2, `cmd/main.go:264`), but Valkey QPS jumps by roughly the L1 hit rate — **~10× at a 90% hit rate** — and per-read latency goes ~100 ns → ~0.5–1 ms for that window. Acceptable, but it deserves a jittered/incremental re-arm rather than an instantaneous global flush, plus a metric.

**5. [medium] The strict-`primary` flip does not touch the path the PR describes.** `subL2Source.GetHistorySharedSince` (`cmd/main.go:79`) routes to the `subauthcache` tier, whose collection is *already* `readpref.Primary()` (`cmd/main.go:256`). The new read preference on `NewSubscriptionRepo` (`internal/mongorepo/subscription.go:27`) therefore only affects `GetSubscription`, i.e. pin/unpin (`internal/service/pin.go:38`) — low rate, negligible cost. Good news for throughput, but `internal/config/config.go:51-56` claims it "covers … GetSubscription / GetHistorySharedSince", which is misleading; `mongorepo`'s `GetHistorySharedSince` is effectively unreachable in production.

**6. [medium] The 256 cap silently lands on `RoomCache` / `PreviewCache` too** (`readcache.go:395,399,504`), which previously had no cap and run 10s TTLs (`config.go:113,124`) — the highest-miss-rate caches in the service. Only the sub cache is tunable (`HISTORY_SUB_CACHE_MAX_INFLIGHT`). At 500 ms Mongo latency the cap yields **~512 loads/s** before requests start queueing 10s and erroring. Give the other two an env knob.

**7. [low] Cancelling superseded loads is mostly churn.** The cancel pays off only when a load is blocked in Mongo *and* an eviction for that exact key lands — membership-change rate, order 1e-4 of loads. The cost is paid on every load: a `loadHandle` alloc, a map insert + delete, and two extra acquisitions of the single global `mu` per attempt (`readcache.go:212-226`). Note also the asymmetry — a gen race retries, a cancel fails the request outright (`:228`).

**8. [nitpick] `account + "\x00" + roomID`** (`readcache.go:312`, `:338`) allocates a string per call on the hot path. Trivial against an L2 round trip, but it is built twice for an evict+read pair and could use a small `[]byte` scratch or a struct key.

# Observability

**1. [high] The new NATS entry point discards the correlation context — every log line from it is uncorrelated.** `cmd/subinvalidate.go:78` binds the handler as `func(_ context.Context, msg *nats.Msg)`, and `:53` / `:62` then use package-level `slog.Warn`. The o11y facade explicitly documents that this ctx carries the consumer span ("calls to `slog.InfoContext(ctx, …)` will include the consumer's traceId and spanId" — `o11y@v0.11.0/nats/conn.go:177-192`), and `pkg/obs/obs_test.go:619-632` pins that traceId/spanId/request_id come from ctx only. The repo norm is overwhelming (178 `slog.*Context` call sites; e.g. `internal/service/rooms.go:142`). As written these two Warns land with **no traceId, no spanId, no request_id** — exactly what CLAUDE.md §"Request Logging & Tracing" forbids at an entry point. One-line fix: accept `ctx`, thread it into `evictOnSubscriptionUpdate`, use `slog.WarnContext`.

**2. [high] The security fix is unobservable in production.** Nothing counts evictions. `readcache.go:111-125` (`remove`) and `cmd/subinvalidate.go:68` (`ev.Evict`) emit no metric, so there is no way to answer "is invalidation actually running?" A dead subscriber, a renamed subject, or a payload-shape change all degrade silently back to TTL-only staleness — **#414 re-appearing with zero signal.** Suggest `cache_evictions_total{cache,tier,result=applied|skipped_action|bad_subject|undecodable}` in `pkg/cachemetrics` (which already has the `cache`/`tier` attribute shape, `pkg/cachemetrics/cachemetrics.go:61-69`), plus the required §13 row in `docs/specs/o11y/nats-metrics-contract.md` — `pkg/obs/instrument_registry_test.go:50` fails the build otherwise.

**3. [medium] Two new, operationally distinct failure modes collapse into one existing series.** Slot exhaustion (`readcache.go:194`) and the fail-closed "evictions raced every load attempt" (`readcache.go:247`) both surface only as `cache_errors_total{cache="history_sub",tier="l1"}` via `readcache.go:252`, indistinguishable from a Mongo failure. They do reach one boundary log via `errnats` `Classify` (`internal/service/utils.go:51`), but only as a message substring — not alertable. A saturation event and a fail-closed authz denial each deserve their own attribute or counter.

**4. [medium] Read amplification and added latency are invisible.** The retry loop (`readcache.go:207-245`) can issue up to 5 source loads per read while only one `Miss` is recorded (`:256`), so under eviction churn Mongo QPS can be **5× the miss rate with nothing explaining it**. The semaphore wait (`:187-195`) can add up to `fetchTimeout` (10s) to a user read with no duration histogram.

**5. [medium] Suspend/resume produce log lines only, no metric.** `cmd/main.go:314` and `:322`. While suspended, every access check bypasses L1 and hits Mongo pinned to strict `primary` — incident-shaped, and only inferable second-hand from a hit-rate collapse. A `cache_suspended` up/down gauge (or reusing the eviction counter with `result="suspend"/"resume"`) makes the state alertable.

**6. [medium] Log-spam risk at Warn.** `cmd/subinvalidate.go:53,62` logs once per message on a non-queue wildcard subscription that receives every account's updates, including the high-frequency `read` action. A schema change or one rogue publisher floods Warn at full fan-out rate **on every replica**. Prefer Debug + a counter, or rate-limit.

**7. [low] Duplicate/inconsistent transition logs.** `pkg/natsutil/connect.go:84-90` already logs disconnect/reconnect *with* connection metrics; the new handlers add a second line per transition, and log reconnect at `Warn` (`cmd/main.go:314`) where natsutil uses `Info` for the same recovery event.

**8. [low] Silent skip on a malformed event.** `cmd/subinvalidate.go:65` returns with no log and no counter when an `added`/`removed` event carries an empty `roomId`. That is a producer bug, not a normal filter, and it is currently indistinguishable from the intentional `read`/`mute_toggled` skip.

**9. [nitpick] Secrets discipline is clean.** The raw payload is never logged; only `action`-derived control flow, `account`, and `subject` (identifiers, consistent with e.g. `internal/service/reactions.go:58`). No `fmt.Println`/`log.Println`, no text loggers, no per-read logging inside the suspend barrier (`readcache.go:160-176`), and the startup config log (`cmd/main.go:324`) carries no secrets.

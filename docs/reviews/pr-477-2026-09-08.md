## Top-line risk assessment

**The core change is correct, well-tested at its centre, and materially improves
the codebase.** `FromReply`'s two design properties — recognition by discriminator
rather than by decodability, and keeping an unmodellable failure untyped — are
the right calls, and the five fail-opens fixed in the later commits are real
defects that were each reproduced before being changed. The oplog-transformer
one was silently discarding migration operations.

**What holds it back from "merge as-is" is not the helper — it is the blast
radius of the 21 call-site conversions, which is wider than the PR body states.**
Three specific gaps:

1. **The PR's own "read one, you've read them all" claim is false.** The five
   "mechanical" sites comprise three distinct pre-change shapes and three distinct
   consumption shapes. One of them — `broadcast-worker/parent_fetcher.go` — turns
   a silent degraded fan-out into no fan-out plus a full `MaxDeliver` NAK budget
   under version skew. That is a deliberate and defensible trade, but it is not
   mechanical and it is not mentioned.
2. **Two behaviour regressions ride along unflagged**: `room-service`'s
   `not_room_member` remap is now gated behind a valid code (a legacy peer's 403
   becomes a 500), and `tools/clientsim`'s unknown-code replies flip from terminal
   to retried-forever, which the surrounding code explicitly warns must not happen.
3. **TDD coverage is uneven.** The five headline fixes each got a red test. The
   sixteen other converted sites got none, including three branches in
   `botplatform-service` that exist specifically to prevent a panic, and the new
   null-rejection logic in `user-service/roomclient`, which sits in a package at
   **0% unit coverage** behind an integration tag that cannot run without Docker.

None of this is a reason to abandon the approach. All of it is a reason to land
the missing tests and either fix or explicitly document the three behaviour
changes before merge.

**Also worth noting for the author's confidence in the guards:** one claim raised
during review — that the semgrep rule's `"/pkg/errcode/"` path exclude is
malformed and would break the blocking `sast` gate — was checked directly against
the real scanner and **does not hold**; the full-tree scan is clean. Two *other*
bypasses of the guard pair were found and empirically confirmed (§6).

### The "triple unmarshal on SUCCESS" premise does not hold — measured

`pkg/errcode/remote.go:56-58` returns `nil` **as soon as the probe finds no `"error"`
key, before `Parse`**. A success reply takes **one** stdlib pass, same as the old
`errcode.Parse(...)` it replaced — and slightly cheaper, because the probe struct
decodes into a `RawMessage` instead of `Error`'s `Metadata map[string]string`.
248 B → 192 B, 4 → 4 allocs. **No regression on the case that dominates.** *(no finding)*

### Findings

- **`low` — error path: three stdlib passes, 2.1× allocations.** `remote.go:56`
  (probe), `:61` (RawMessage → string), `:68` (`Parse` re-decodes the whole payload).
  Measured 344 B/8 allocs → 776 B/17 allocs, ~2× ns. Error replies are rare in steady
  state, so this is an acceptable trade for the correctness win; not worth optimising
  unless a failing peer produces sustained error volume (e.g.
  `room-service/memberlist_client.go:110` during a cross-site outage, where each reply
  then also builds a metadata kv slice).
- **`medium` — the stdlib pass on the sonic hot path is now centralised; that is the
  fix *opportunity*, not a regression.** `broadcast-worker/parent_fetcher.go:68`,
  `message-gatekeeper/fetcher_history.go:92`,

  sonic workers, but they **already** paid an `encoding/json` scan via `errcode.Parse`
  on the pre-PR line — the codec mismatch is pre-existing, not introduced, and

  now sits on every reply in five hot-path workers behind **one** function, so a

  would remove a full stdlib scan per reply repo-wide **with one edit**. On the
  50-room batch that scan is ~60-85 µs/reply — the largest single win available here.
  Follow-up, not a blocker.
- **`low` — `exemptions_contract_test.go` costs ~3.5 s of every `make test` run of

  `user-service/roomclient/client.go:110-118` — one extra `json.Unmarshal` into

- **`nitpick` — `{"error":null}` success shape costs +3 allocs / +112 B**

# Lens: Observability

- **`high` — an unrecognised remote code loses its structured `code` dimension at the
  boundary; it survives only as free text inside `cause`.**
  `pkg/errcode/remote.go:73` builds
  `fmt.Errorf("remote returned unknown error code %q: %s", e.Code, e.Message)`
  (and `:70` for the undecodable case). At the boundary, `classify.go:22-23` takes the
  untyped branch — `e = &Error{Code: CodeInternal, Message: "internal error", cause: err}`
  — so the emitted attrs at `:32-36` are
  `code=internal, reason="", cause="remote returned unknown error code \"upstream_only_code\": upstream boom"`.
  Note `underlying` is populated **only** in the `hasErrcode` branch (`:19-21`), so it
  is absent here: the remote code exists in exactly one place, an interpolated
  substring of `cause`. Before this PR those sites relayed typed and logged
  `code=upstream_only_code`. CLAUDE.md §Logging ("structured fields as key-value
  pairs, never interpolated strings") is violated in effect — an operator cannot
  `group by code` or filter on the foreign code without regex-scraping a message.
  **The severity is not that the untyping is wrong — it is right — but that the PR
  discards the dimension instead of moving it.** Fix: have `FromReply` return an error
  carrying the remote code as a retrievable field (e.g. an exported
  `RemoteCodeError{Code, Message}` with `errors.As` support), and have `Classify`
  append `remote_code` when it matches. `errors.As(*errcode.Error)` still finds
  nothing, so the whole point of the change survives.
- **`high` — no metric or counter exists for "a peer replied with something this build
  cannot model" — the exact version-skew signal a rolling deploy needs.** The
  client-side RPC metric is blind to reply envelopes: `pkg/natsmetrics/metrics.go:84-89`
  `classifyRequestOutcome(err)` returns `RequestSucceeded` for `err == nil`, and
  `Request` (`:621-627`) is called with the *transport* error only — e.g.
  `notification-worker/presence.go:81` records the sample **before the envelope is even
  read**. So the five newly-fixed fail-opens change behaviour from "silent nil/zero-value
  success" to "an `internal`-classified failure that the RPC histogram still counts as a
  success". Operators will see an unexplained rise in `code=internal` (Error-level per
  `classify.go:44-50`) **with no dimension to slice by**. Worse in the hot path:
  `broadcast-worker/handler.go:1412` calls `errcode.Terminal(err)`, which finds nothing
  in an untyped error, so a foreign-code reply is now NAKed for the full `MaxDeliver` —
  the same comment block warns this "hold[s] an ack-pending slot for 66 s per message …
  fills the consumer's budget". The visible symptom becomes
  `terminal_reason=max_deliver` and consumer saturation, **with nothing naming the
  cause**. Recommend one counter, e.g.
  `chat.errcode.remote_unusable_total{operation, kind=unknown_code|undecodable}`.
- **`medium` — `notification-worker/presence.go:87-89` deletes two structured fields.**
  Was `"error", errResp.Message, "code", errResp.Code, "chunk", …`; now
  `"error", remoteErr, "chunk", len(ch)`. Because
  `(e *Error) Error() string { return e.Message }` (`pkg/errcode/error.go:14`), even the
  *recognised*-code case now logs only the message — **`code` is gone entirely from this
  line**, not just for unknown codes. Keep it via `errors.As` + `ee.Code`.
- **`medium` — `FromReply` embeds an unbounded, remote-controlled string into error text
  that reaches logs.** `remote.go:70,73` interpolate `message` / `e.Message` with no
  length cap; both `e.Code` (a plain string type) and the message are peer-controlled.
  That text lands verbatim in `cause` at `classify.go:35` and in
  `room-service/memberlist_client.go:120` (`"detail", remoteErr.Error()`). The repo
  already has the precedent three files away: `admin-service/client_update.go:147`
  `maxUpstreamBodyLogLen = 256` + `truncateForLog`. No client leak (Classify replaces
  the message with `"internal error"`), so this is log-bloat/injection hygiene, not
  disclosure — but a peer can write arbitrary bytes into your log lines through a code
  field. *(Same defect as bug & security #2.)*
- **`medium` — `FromReply(data []byte)` is ctx-less, so it cannot annotate the client
  span or correlate.** Every call site has a `ctx` in hand (e.g.
  `user-service/roomclient/client.go:100`, `search-service/room_client.go:36`). The o11y
  facade's `request {subject}` span (`o11y@v0.12.0/nats/conn.go:304-330`) ends OK on a
  transport-successful reply, so an envelope failure leaves the client span **unmarked**
  and carries no `remote_code` attribute. A ctx-taking variant (or a call-site
  `span.RecordError`) would give traces the dimension logs are also missing — same fix
  as the first finding, one layer up. **Request-ID propagation itself is unharmed**: the
  only ctx-aware log on a changed path, `memberlist_client.go:119`, correctly uses

- **`low` — `slog.Warn` without ctx on a touched line.**
  `notification-worker/presence.go:87` uses `slog.Warn`, not `WarnContext`, inside a
  goroutine that has `ctx` (used at `:81`). Pre-existing style, but the line was

- **`low` — "never log AND return": no new violations, one retained double-log.**
  `memberlist_client.go:119-121` warns then returns a *different* `errcode.Internal`,
  which Classify logs again at Error level — two lines per event. That shape predates

- **`low` — operator-visible failure messages in oplog-transformer and admin-service
  genuinely improve.** `data-migration/oplog-transformer/historyclient.go:104-110` now

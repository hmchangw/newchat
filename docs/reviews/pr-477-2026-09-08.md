## Top-line risk assessment

**The core change is correct, well-tested at its centre, and materially improves
the codebase.** `FromReply`'s two design properties — recognition by discriminator
rather than by decodability, and keeping an unmodellable failure untyped — are
the right calls, and the five fail-opens fixed in the later commits are real
defects that were each reproduced before being changed. The oplog-transformer
one was silently discarding migration operations.

**What holds it back from "merge as-is" is not the helper — it is the blast
radius of the 21 call-site conversions, which is wider than the PR body states.**
Three specific gaps:

1. **The PR's own "read one, you've read them all" claim is false.** The five
   "mechanical" sites comprise three distinct pre-change shapes and three distinct
   consumption shapes. One of them — `broadcast-worker/parent_fetcher.go` — turns
   a silent degraded fan-out into no fan-out plus a full `MaxDeliver` NAK budget
   under version skew. That is a deliberate and defensible trade, but it is not
   mechanical and it is not mentioned.
2. **Two behaviour regressions ride along unflagged**: `room-service`'s
   `not_room_member` remap is now gated behind a valid code (a legacy peer's 403
   becomes a 500), and `tools/clientsim`'s unknown-code replies flip from terminal
   to retried-forever, which the surrounding code explicitly warns must not happen.
3. **TDD coverage is uneven.** The five headline fixes each got a red test. The
   sixteen other converted sites got none, including three branches in
   `botplatform-service` that exist specifically to prevent a panic, and the new
   null-rejection logic in `user-service/roomclient`, which sits in a package at
   **0% unit coverage** behind an integration tag that cannot run without Docker.

None of this is a reason to abandon the approach. All of it is a reason to land
the missing tests and either fix or explicitly document the three behaviour
changes before merge.

**Also worth noting for the author's confidence in the guards:** one claim raised
during review — that the semgrep rule's `"/pkg/errcode/"` path exclude is
malformed and would break the blocking `sast` gate — was checked directly against
the real scanner and **does not hold**; the full-tree scan is clean. Two *other*
bypasses of the guard pair were found and empirically confirmed (§6).

# Service: room-service

`make test SERVICE=room-service` → `ok … 1.661s`. Both reply readers converted; no
`errcode.Parse` remains in the service.

### (a) Diff correctness

- **`medium` — the reason-remap is now gated behind `Code.Valid()`, changing
  caller-visible semantics.** `room-service/memberlist_client.go:111-134`. The old
  order checked `ee.Reason == errcode.RoomNotMember` *before*
  `!ee.Code.Valid() || ee.Message == ""`, so a peer replying
  `{"error":"…","reason":"not_room_member"}` with no code, an unknown code, or an
  undecodable field mapped onto `errNotRoomMember`. That reply now routes into the
  untyped branch and returns `errcode.Internal` — **403 + `not_room_member`
  becomes 500** — and the metrics defer at `:92-96` no longer excludes it, so a
  business rejection records as a request failure. The comment at `:128-131`
  documents the loss; no test pins it.
- **`low` — remote message dropped on the degrade path.** `:121` returns fixed
  text where the old code returned `errcode.Internal(ee.Message)`. Safer, but
  wire-visible, and `TestNATSMemberListClient_UnknownCode_DegradesToInternal`
  (`memberlist_client_test.go:191-212`) asserts only the code.
- **`low` — log lost its structured fields.** `:119-120` folds the peer's `code`
  and `message` into `"detail", remoteErr.Error()`, so the code is recoverable
  only by parsing a sentence — against CLAUDE.md §3 "structured fields as
  key-value pairs, never interpolated strings".

### (b) Scope drift

No findings. `nc.Request`/`RequestMsgWithContext` exists at exactly
`reader_history.go:74` and `memberlist_client.go:98`; both converted, nothing else touched.

### (c) Abstraction changes

Adoption is **complete and correct**. `reader_history.go:87-92` behaves
*identically* for a canonical NotFound envelope. The changed cases are strict
improvements: previously `ok && ee.Code.Valid()` let an unknown-code or
undecodable envelope fall through to the `messageProjection` decode (`:98-101`),
returning zero-valued meta with `found=true, err=nil` **and** a success metrics sample.

- **`medium` — that fix is untested.** No `reader_history` test covers the
  unknown-code / undecodable envelope no longer reading as a found message.

**Test redness verified against `28b97da`:**
`TestNATSMemberListClient_UndecodableEnvelope_IsNotAnEmptyMemberList`
(`memberlist_client_test.go:162`) is **genuinely red** — `Error.Metadata` is
`map[string]string` (`pkg/errcode/error.go:9`), so `Parse` failed on
`"metadata":{"retryAfter":5}` and the reply then decoded cleanly into
`ListRoomMembersResponse` yielding `(nil, nil)`.

- **`nitpick`** — `TestNATSMemberListClient_UnknownCode_DegradesToInternal` is
  **green on old code** (the old `!ee.Code.Valid()` already returned `Internal`),
  so it is a characterization test, not a Red-phase one.

### (d) Design coherence

Coherent; the `FromReply` → `errors.As` idiom matches CLAUDE.md Tier 1.

- **`nitpick` — an empty `"error"` still reads as success.** `FromReply` returns
  nil for `""`/`null` (`pkg/errcode/remote.go:64`), so a refusal with an empty
  message decodes into an empty member list at `memberlist_client.go:146-150`.
  Unreachable today (`errcode.New` panics on an empty message), but it is the same
  "refusal reads as no members" shape the PR exists to close.

### (e) Project-pattern adherence

No findings. Subjects via `pkg/subject` (`memberlist_client.go:80`,
`reader_history.go:74`); no stream, idgen, consumer, outbox or event-struct changes.

### (f) Client-API doc rule

**No violation.** Only outbound client helpers changed; no `chat.user.{account}.`
handler touched, so `docs/client-api.md` is not required.

- **`low`** — finding (a1) does alter what a client sees from `member.list` against

# Service: botplatform-service

`go build ./botplatform-service/` clean; `errors` was already imported in both files.

### (a) Diff correctness

**The panic really existed — verified.** At base, `bot_forwarder.go` and
`dm_ensurer.go` did
`if ee, ok := errcode.Parse(reply.Data); ok { return …, errcode.New(ee.Code, ee.Message, …) }`.
`Parse` explicitly does **not** validate `Code` (`pkg/errcode/parse.go:8-10`) and
`New` **panics** on a non-canonical Code (`pkg/errcode/options.go:11-15`), so any
legacy peer replying without `"code"`, or a newer peer with a code outside this
build's set, crashed the handler. The three replacements remove that: an
unrecognised code arrives untyped from `FromReply` (`pkg/errcode/remote.go:70-74`),
`errors.As` finds nothing, and the site returns before `New`.

- **`medium` — bare `return nil, remoteErr` at `bot_forwarder.go:92`, `:159`,
  `dm_ensurer.go:71`.** CLAUDE.md §3 forbids returning a bare `err`, and this drops
  the call-site provenance the typed branch is careful to add. All three upstreams
  (bot-room-service, bot-message-handler, `dm.ensure`) now log the identical
  `"remote returned an error this build cannot decode: …"` with nothing saying which
  RPC produced it. `admin-service/room_onduty.go:117` **in this same PR** wraps it
  (`fmt.Errorf("room restricted rpc returned an unusable error envelope: %w", remoteErr)`);
  botplatform should match.
- **`low`** — the reconstruction at `bot_forwarder.go:94-96` / `dm_ensurer.go:73-75`
  drops `ee.Metadata`. Pre-existing, but `room-service/memberlist_client.go` was
  edited in this PR to preserve it, so the two remote-relay sites now diverge.

### (b) Scope drift

None. 30 added lines, three sites, no unrelated refactor. No `errcode.Parse`

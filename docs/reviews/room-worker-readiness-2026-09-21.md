## Executive summary

The ROOMS consumer pattern, OUTBOX ordered-lane federation, `pkg/subject` usage, dedup-id helpers and shutdown order all match CLAUDE.md, and code quality is strong. The high finding is a client contract break: `publishAsyncJobResult` emits `status:"error"` for any non-nil error before `HandleJetStreamMsg` NAKs a transient one for retry, so a Mongo blip tells the client the job failed and minutes later that the same `requestId` succeeded — `docs/client-api.md` describes the result as terminal. Performance carries the real cost: `GetRoom`, `ListByRoom` and `GetSubscription` fetch whole documents (the first drags the room's private key on every DM redelivery), the Teams reconcile does a per-member `GetUser` and a per-member synchronous PubAck where a batch call already exists, no per-job deadline exists so a wedged Mongo call leaks a `MAX_WORKERS` slot, and the writer's own L1 room-meta cache is never invalidated after a rename. The ROOMS durable has no `FilterSubjects`, so every mute toggle from room-service is a wasted delivery plus a WARN. Coverage is 62.7%, and the `HandleJetStreamMsg` dispatcher — the only production entry point — is 0% at every layer.

## 3. Architecture — score 3

### Evidence

- [high] Transient failures are reported to the requester as a terminal `AsyncJobResult{status:"error"}` and then retried — `room-worker/handler.go:187-191` — `publishAsyncJobResult` is deferred in every process fn and sets `status=error` for ANY non-nil err, with no `errcode.IsPermanent` check (comment at :212-214 says the Ack/Nak decision is deliberately independent). `HandleJetStreamMsg` then `SettleQuiet`s (:284), which Naks non-permanent errors, so a Mongo blip yields "error" to the client followed minutes later by "ok" for the same `requestId`. `docs/client-api.md:1328` documents the result as the terminal outcome of the job, not of one attempt.
- [high] Un-projected reads violate the "always project precisely" MUST, and `GetRoom` drags the room key along — `room-worker/store_mongo.go:174` (`GetRoom` FindOne, no projection), `:89` (`ListByRoom`), `:300` (`GetSubscription`). `CreateRoom` writes the key into the room doc as `encKey` (`store_mongo.go:247`), so every post-add re-read (`handler.go:1180`) and duplicate-key reconcile (`handler.go:230`) fetches key material it never uses.
- [medium] ROOMS consumer keeps the repo-default `MaxDeliver=6` (~12.6 min) for durable state mutations — `room-worker/main.go:479-486` — `buildConsumerConfig` calls only `stream.DurableConsumerDefaults(s)`. `message-worker/main.go:373` and `inbox-worker/main.go:1051` opt into `stream.WithOutageRetryBudget`, `roomlist-worker/main.go:392` into `WithUnlimitedRedelivery`. A Mongo outage longer than the budget silently drops member add/remove/create/rename after the requester was already told "error" (finding 1).
- [medium] No producer-side per-room ordering: `member.add` and `room.rename` for one room run on concurrent workers (`main.go:335-350`, `MAX_WORKERS=100`) and can enqueue onto the OUTBOX ordered lane out of causal order — `room-worker/handler.go:2423-2427` acknowledges this; the FIFO lane only fixes transport skew. A rename can still reach the remote before the add that creates the sub it renames.
- [medium] Teams-mode reconcile swallows transient store errors per chat and Acks the batch — `room-worker/teamsroomcreate.go:33-40` — `reconcileTeamsRoom` errors (including `create room`/`bulk create subs` Mongo failures, :77-79, :162-164) are WARN-logged and the envelope returns nil, so a transient outage loses that chat's membership until an unrelated later batch happens to include it. No permanent/transient split.
- [medium] Message-type dispatch uses raw subject suffix literals instead of `pkg/subject` — `room-worker/handler.go:261-278` — `strings.HasSuffix(subj, ".member.add")`, `".create"`, `".room.rename"`, `strings.Contains(subj, ".teams.room.canonical.")` duplicate token knowledge that lives in `pkg/subject/subject.go:684,217`; `HasSuffix(".create")` also matches any future `*.create` subject that lands on `chat.room.canonical.{site}.>`.
- [low] Duplicates `pkg/jobguard.Run` instead of using it — `room-worker/main.go:428-436` — every other worker (`message-worker/main.go:391`, `broadcast-worker/main.go:556`, `inbox-worker/main.go:959`) uses `jobguard.Run`; the local copy omits the stack trace `jobguard.Guard` logs (`pkg/jobguard/jobguard.go:35-45`) and the `MarkHandlerPanic` hook (`:53-55`), so panics here are harder to diagnose and invisible to that metric.
- [low] Dependencies injected by poking unexported fields from main, bypassing the constructor — `room-worker/main.go:268-283` — `handler.publishUsers`, `.dekProvisioner`, `.valkey`, `.reconcileTTL` are set after `NewHandler`. Sibling services use functional options (`message-worker/handler.go:53`, `inbox-worker/handler.go:181`).
- [low] Store relies on unique indexes it never ensures — `room-worker/store.go:66-70,116` — `BulkCreateSubscriptions`/`BulkCreateRoomMembers` idempotency depends on `(roomId,u.account)` / `(rid,member.type,member.id)` unique indexes; `store_mongo.go` has no `EnsureIndexes`/`Indexes()` call, so correctness depends on `room-service` having started first.
- [low] Sync-DM federation builds its dedup ID by hand — `room-worker/handler.go:2537-2538` — `payloadSeed+":"+other.SiteID` differs in shape from every other `federate` call, which uses `natsutil.InboxDedupID` (`pkg/natsutil/request_id.go:160-168`).
- [low] Rename BadRequest interpolates `err.Error()` from `json.Unmarshal` — `room-worker/handler.go:2330` — contradicts the rule stated at `:1557-1559` (SyntaxError embeds payload bytes) and reaches the client via `fillAsyncError`.

### Recommendations

- [high] In `publishAsyncJobResult`, publish `status:error` only when `errcode.IsPermanent(jobErr)` (or when `jsretry.IsLastAttempt`); on a transient Nak publish nothing (or a distinct `retrying` status documented in `docs/client-api.md`) — `handler.go:187-191` — stops clients from treating a retried job as failed.
- [high] Add `SetProjection` to `GetRoom`, `ListByRoom`, `GetSubscription` and exclude `encKey` everywhere the key is not needed — `store_mongo.go:89,174,300` — satisfies the MUST and keeps key bytes out of hot-path decodes.
- [medium] Build the consumer with `stream.DurableConsumerDefaults(stream.WithOutageRetryBudget(s, jsretry.DefaultBackoff))` — `main.go:480` — aligns with message-worker/inbox-worker so a one-hour Mongo outage retries instead of dropping membership writes.
- [medium] Move subject classification into `pkg/subject` (e.g. `ParseRoomCanonical(subj) (op, ok)`) and switch on the returned op — `handler.go:261-278` — one source of truth for the ROOMS token layout.
- [medium] In `processTeamsRoomCreate`, classify per-chat errors: Nak the batch (return the error) on non-permanent store failures, skip only permanent/malformed chats — `teamsroomcreate.go:33-40`.
- [low] Replace `runJobWithRecovery`'s recover block with `jobguard.Run` (keep the request-id minting wrapper) — `main.go:428-436`.
- [low] Convert post-construction field pokes into `NewHandler` options — `main.go:268-283`.

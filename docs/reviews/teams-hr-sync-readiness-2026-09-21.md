**Overall score:** 2.5 / 5 (baseline 2026-09-01: 2.8, Δ -0.3)

## Executive summary

`teams-hr-sync` walks Microsoft Graph groups, diffs the result against `hr_employee`, and emits the delta — either as NATS events for `hr-sync-worker` (stream mode) or by writing Mongo directly (direct mode, the migration path). Its structure is genuinely good: consumer-defined interfaces, constructor DI, an injected `publishFunc`, subjects built exclusively from `pkg/subject` with no raw `fmt.Sprintf` anywhere, and a clean `emitter` seam. It scores 2.5 because the two write paths disagree with each other, the destructive path has no guard rail, and the riskiest code has no tests at all.

The most consequential finding is that **nothing bounds the quit batch**. Every stored row absent from the Graph walk becomes a quit, and the consumer runs it as an unfiltered `DeleteMany` by account. A group that returns HTTP 200 with an empty `value` — a revoked app permission, an accidentally emptied group, a typo in `SYNC_GROUPS` — is not an error in `collect.go:36`, so one successful-but-wrong Graph response wipes a whole site's HR directory, which `portal-service` then left-joins against. There is no max-quit ratio and no min-member floor anywhere in the pipeline. Compounding it, `ListTeamsEmployees` reads the entire collection with `bson.M{}` although its name, the README and an integration test all claim it is scoped to `source:"teams"` rows — `model.IEmployee` has no `source` field at all, so the "legacy rows survive" assertion is vacuous and any future non-Teams HR feed into the same collection gets diffed and deleted.

Second, the publish order breaks the service's own stated self-healing contract. `employees.upsert` is awaited and acked before `users.upsert` is attempted (`publisher.go:38-53`), but `hr_employee` — updated by the first message — *is* the diff baseline. If the second publish fails, the next run sees no delta and the user identity rows are never written. That is permanent, silent loss, and both `README.md:10` and `main.go:37` claim the opposite. Reversing the two lines fixes it: the baseline-advancing publish must go last. Related, neither upsert event carries a `Timestamp`, against CLAUDE.md's rule for every `pkg/model` event struct — `search-sync-worker` already pays for that absence with a stream-sequence last-write-wins workaround.

Third, direct mode and `hr-sync-worker` are two hand-written implementations of one documented contract and have already diverged on every detail: match key (`employeeId` vs `account`), `_id` rule (`= employeeId` vs a minted UUIDv7), and which fields are skipped on empty. `users.account` carries a unique index, so a direct-mode backfill against a database holding a native user without an `employeeId` matches nothing, inserts a duplicate account, and fails mid-run — after the employees were already written. That filter is also unindexed: no service creates `{employeeId: 1}` on `users` and this one defines no `EnsureIndexes`, so a 20k-employee migration is O(N·M) collection scans. The README points at a `pkg/hrstore` that would have prevented all of this; it does not exist, and the README now conceals the duplication rather than documenting it.

Coverage is 57.1%, and the gap sits exactly on the dangerous code: all three `WriteStore` methods are at 0% with no test of any kind, unit or integration — including the hand-built `$set` whose entire reason for existing is the comment "must never touch roles/services/password on the live auth store". A future edit to a full-document replace would pass every test in the repo. Both data-corruption guards in `UpsertUserIdentities` are likewise unreached.

On throughput, the whole upsert set ships as one JetStream message with no size check or chunking, so a directory in the low tens of thousands crosses `max_payload` — and it bites on the very first run, when the diff baseline is empty and every employee is an upsert. Nothing self-heals, because nothing was published; the next run rebuilds the identical oversized batch. Every other batching publisher in the repo caps itself.

## 2. Code quality — score 3

### Evidence

- [high] A partial publish silently and permanently drops user identities — `teams-hr-sync/publisher.go:38-53` — `publishSync` publishes `employees.upsert` then `users.upsert`. The diff baseline is `hr_employee` only (`store.go:17`) and `hr-sync-worker` creates `users` rows *solely* from `users.upsert` (`hr-sync-worker/handler.go:34-43`), so if the first lands and the second fails, the next run sees no delta for those accounts and never re-emits them. The "a lost publish self-heals" claim (`main.go:37-39`) does not hold here.
- [high] Direct mode writes `users` with a different identity key than the stream consumer — `teams-hr-sync/write_store.go:73-85` vs `hr-sync-worker/store.go:84-96` — this service filters on `{"employeeId": …}` and forces `$setOnInsert _id = employeeId`; the worker filters on `{"account": …}` and mints a UUIDv7 `_id`. Two implementations of one documented contract. A `direct` backfill against a DB where an account already exists without an `employeeId` matches nothing and **inserts a second `users` doc for the same account** on the live auth store.
- [medium] `ListTeamsEmployees` is not scoped to Teams-sourced rows — `teams-hr-sync/store_mongo.go:56-58` — the filter is `bson.M{}` (whole collection) and `model.IEmployee` has no `Source` field (`pkg/model/teams_employee.go:29-42`), so the method name and the README's `source:"teams"` claim are both untrue. Any `hr_employee` row from a non-Teams producer is diffed as a departure and published as a quit → `DeleteMany` downstream. The test assertion "the legacy row never does" (`integration_test.go:163`) is vacuous — no legacy row is ever inserted.
- [medium] Mode-conditional required config is only half enforced — `teams-hr-sync/config.go:55,62` — `MONGO_READ_URI` and `NATS_URL` are `required,notEmpty` unconditionally, yet `runDirectMode` (`main.go:169-181`) touches neither. `DIRECT_WRITE_URI` got a hand-rolled conditional check (`main.go:55-59`); the symmetric case did not, so a migration run must invent dummy Mongo/NATS URLs.
- [low] The request ID reaches only two log lines — `teams-hr-sync/main.go:100-125` — `logger := slog.With("requestId", …)` is local to `run`; `ctx` carries the ID (`main.go:99`) but the default JSON handler (`main.go:27`) is not context-aware, so the drain error (`main.go:153`) and `write_store.go:69` emit without it. CLAUDE.md requires it on *all* log lines. The key also disagrees with `pkg/jsretry`'s `request_id`.
- [low] Silent-skip warn carries no identifying field — `teams-hr-sync/write_store.go:69` — `"skip user identity upsert: empty employeeId"` names no account, so an operator cannot tell which rows were dropped from a backfill. `account` is not a secret and belongs here.
- [low] README has drifted from the code — `teams-hr-sync/README.md:15,48-51,53-54,61-64` — it documents a `pkg/hrstore` package that does not exist (`write_store.go:20-21` says so), `model.ChangeTypeNewHire/Update` (actual: `IChangeTypeNewHire`), a `transform.SourceTeams` tag that exists nowhere, and an example typed `*model.Org`/`model.Employee` that will not compile against `transform/transform.go:41`.
- [nitpick] Dead + undocumented config — `deploy/docker-compose.yml:29` sets `ORG_TYPE=group`, read by no Go file; conversely `GRAPH_PROXY_URL/USERNAME/PASSWORD` (`config.go:34-43`) are absent from the README table.
- [nitpick] `stats.Overridden` is counted before the dedup check — `collect.go:45-52` — an account present in two groups increments it twice for one emitted row. Also `fmt.Errorf` with no verbs at `config.go:100` (use `errors.New`), and a stray "ponytail:" token in the doc comment at `transform/transform.go:34`.

### Recommendations

- [high] Make the employee/user pair atomic — `publisher.go:38-53` — either publish `users.upsert` first (a re-published user upsert is idempotent; a re-published employee is what closes the diff), or have `hr-sync-worker` derive identities from the `employees.upsert` batch so one message carries both. Removes a silent, unrecoverable identity gap.
- [high] Reconcile `UpsertUserIdentities` across the two writers — `write_store.go:73-85` — key on `account` and mint the `_id` the same way `hr-sync-worker/store.go:84-96` does (or extract the shared logic), and add a test asserting the two produce identical documents. Prevents duplicate `users` rows on the auth store.
- [medium] Filter the diff baseline to rows this producer owns — `store_mongo.go:57` — add a `source`-style discriminator to `model.IEmployee`, write it on upsert, and filter both the read and `QuitTeamsEmployees`. Then make `integration_test.go:163` actually insert a foreign row so the assertion has teeth.
- [medium] Validate `MONGO_READ_URI`/`NATS_URL` per mode — `main.go:49-59` — require them only when `HRSyncMode == modeStream`, mirroring the existing `DIRECT_WRITE_URI` check, and fix the README's required column.
- [low] Install a context-aware handler at `main.go:27` that lifts `natsutil.RequestIDFromContext` onto every record, then drop the ad-hoc `slog.With` — one correlation ID across the whole run, including `pkg/` logs.
- [low] Rewrite the README against the current code (`pkg/hrstore`, `SourceTeams`, `IChangeType*`, the example's signatures) and delete `ORG_TYPE` from `deploy/docker-compose.yml:29`.

## 3. Architecture — score 3

### Evidence

- [high] Publish ordering breaks the "a lost publish self-heals" contract — `teams-hr-sync/publisher.go:38-53` — `employees.upsert` is published *before* `users.upsert`. hr-sync-worker persists `hr_employee` from the first message (`hr-sync-worker/handler.go:30`), and that collection IS this service's diff baseline (`main.go:205`). If the second publish fails, the next run sees the employees already stored, emits no upsert, and the `users` identity rows are never written — permanent silent loss, not self-healing. Reversing the two makes the failure replayable (the baseline-advancing publish must go last).
- [high] Direct mode's `users` upsert key diverges from hr-sync-worker's and will hard-fail on a real migration target — `teams-hr-sync/write_store.go:73` vs `hr-sync-worker/store.go:93` — this service filters `{employeeId}` and `$setOnInsert _id = employeeId`; hr-sync-worker filters `{account}` and mints a UUIDv7 `_id`, deliberately so it "covers HR-feed users and migrated externals alike". `users.account` carries a unique index (`user-service/mongorepo/users.go:43`), so any pre-existing account without an `employeeId` misses this filter, upserts a new doc, and trips duplicate-key. `BulkWrite` is unordered (`pkg/mongoutil/collection.go:173`), so the run partially applies then errors — and errors identically on every retry.
- [high] No guard rail on a destructive quit batch — `teams-hr-sync/differ.go:38-40` — every stored row absent from the Graph walk becomes a quit, and the consumer `DeleteMany`s it (`hr-sync-worker/store.go:112`). A group that returns 200 with an empty `value` (revoked app permission, accidentally emptied group, a `SYNC_GROUPS` typo) is not an error in `collect.go:36`, so one bad-but-successful Graph response wipes a whole site's HR rows. There is no max-quit ratio / min-member floor anywhere in the pipeline.
- [medium] The diff baseline is another service's collection, read with an empty filter that contradicts its own name — `teams-hr-sync/store_mongo.go:56-58` — `ListTeamsEmployees` selects `bson.M{}`, and `model.IEmployee` has no `Source` field (`pkg/model/teams_employee.go:29-42`), so the "teams-sourced rows only" contract the README asserts (`README.md:8`) is not enforced. Today only hr-sync-worker writes `hr_employee`, so it is latent — but the moment a second HR source exists, its rows become quits.
- [medium] Unbounded single-message publish with no chunking or size check — `teams-hr-sync/main.go:184-188`, `publisher.go:76-81` — the entire delta goes out as one zstd'd JetStream message. A cold start (empty baseline → every employee is an upsert) or any mapper change that touches every row publishes the whole org at once; past `max_payload` the publish fails every run identically, so the feed wedges rather than degrades. No `Nats-Msg-Id` either, so JetStream dedup is unused on re-publish.
- [medium] `direct` mode duplicates hr-sync-worker's write logic instead of sharing it — `write_store.go:22-29`, `README.md:15,48` — the README points at `pkg/hrstore` as a shared `Store`; no such package exists in the tree. The two hand-rolled copies have already drifted (finding 2), which is the failure mode a shared package prevents.
- [low] No `BOOTSTRAP_STREAMS` knob / `bootstrap.go` although the service publishes to `HR-{central}` — `teams-hr-sync/config.go:15-78` — the spirit is honored (hr-sync-worker is sole owner, `hr-sync-worker/bootstrap.go:29`) and `deploy/docker-compose.yml:7` says so, but local dev can't stand this up against a fresh NATS alone.
- [low] Stale env in the compose file — `deploy/docker-compose.yml:29` — `ORG_TYPE=group` matches no `config` field; `transform.go:34` notes the concept was dropped.
- [nitpick] `pkg/shutdown.Wait` and `pkg/obs.Init` are both skipped — `main.go:71,143` — defensible for a one-shot binary and consistent with sibling jobs (`teams-room-creation/main.go:66`). Defer order is correct (drain before Mongo disconnect, `main.go:139/147`) and the drain deadline correctly detaches from the cancelled ctx (`main.go:150`).

### Recommendations

- [high] Publish `users.upsert` before `employees.upsert` — `publisher.go:38-53` — one-line reorder; makes a mid-run failure replayable by the next CronJob fire instead of permanently dropping identity rows.
- [high] Make `mongoWriteStore.UpsertUserIdentities` key on `account` with `employeeId` set conditionally, mirroring `hr-sync-worker/store.go:69-99` — better, extract the shared write surface into the `pkg/hrstore` the README already documents and have both services consume it, so drift is impossible.
- [high] Add a destructive-change circuit breaker before `emit` — `main.go:229-240` — abort the run when quits exceed a configurable fraction of the baseline (e.g. `MAX_QUIT_RATIO`, default ~0.1) or when any configured group returns zero members; log and exit 1 so the Job records it and a human looks.
- [medium] Chunk upsert batches to a configured max element/byte count and publish with a deterministic `Nats-Msg-Id` — `publisher.go:76-81` — bounds the message under `max_payload` and lets JetStream dedup absorb a re-publish after a partial run.
- [medium] Filter the baseline read to Teams-sourced rows (add a `source` field to `model.IEmployee` and to the projection) or rename `ListTeamsEmployees` to match what it does — `store_mongo.go:56`.
- [low] Add `Bootstrap bootstrapConfig` + a `bootstrap.go` that creates `stream.OrgSyncStream(central)` only when `BOOTSTRAP_STREAMS=true`, and set it in the compose file — `config.go:78`, `deploy/docker-compose.yml:7`.
- [low] Delete `ORG_TYPE` from the compose file and fix the README's `pkg/hrstore` / `model.ChangeTypeNewHire` references (actual: `model.IChangeTypeNewHire`) — `README.md:15,48,53`.

## 6. Integration — score 2

### Evidence

- [high] Published upsert events carry no `Timestamp` — `pkg/model/teams_employee.go:44-54` — `IEmployeeWithChange`/`IUserWithChange` are bare-array NATS event structs with no `Timestamp int64`, and `publisher.go:38,50` publish them without one (only the quit batch sets it, `publisher.go:68`). CLAUDE.md requires it on every `pkg/model` event struct; `search-sync-worker` already pays for its absence with a `sequencedCollection` seam and stream-sequence LWW script (`search-sync-worker/collection.go:55-68`, `spotlight_org.go:24-28`).
- [high] Partial publish permanently desyncs the users lane — `publisher.go:38-53` — employees.upsert is awaited and acked before users.upsert is attempted. If users.upsert fails the run exits, but the next run diffs against `hr_employee`, already updated by the worker (`main.go:205-209`), so rows compare equal and identities are never republished. `README.md:10-11` and `main.go:36-39` claim "a lost publish self-heals" — true for quits, not users.
- [high] `ListTeamsEmployees` has no source filter — `store_mongo.go:57` — the find is `bson.M{}` over the whole `hr_employee` collection, yet `README.md:8` and `integration_test.go:70,163` assert it reads `source:"teams"` rows only (and `model.IEmployee` has no `Source` field at all). Every non-Teams row is diffed as a departure and emitted as a quit, which `hr-sync-worker/store.go:111-117` runs as an unfiltered `DeleteMany` by account, also emptying the directory `portal-service` left-joins (`portal-service/store_mongo.go:43-47`). The test's "legacy row never quits" assertion is vacuous — no legacy row is inserted.
- [high] Direct mode and `hr-sync-worker` implement the same contract differently — `write_store.go:62-95` vs `hr-sync-worker/store.go:69-109` — match key `employeeId` vs `account`; `_id` = employeeID vs a minted UUIDv7; skip-on-empty `employeeId` vs empty `account`; direct `$set`s `account`, the worker does not. The same person gets a different `_id` depending on which mode ran first, breaking the derivable-id invariant `write_store.go:80-83` claims. Against a live `users` collection with user-service's unique `account` index (`user-service/mongorepo/users.go:43`), a native user with no `employeeId` makes direct mode insert a duplicate account → duplicate-key error mid-run, after employees were written.
- [medium] Cleared org fields never converge, so rows republish forever — `pkg/model/teams_employee.go:7-15` — the nine `IOrg` bson tags are `omitempty` and the consumer's `$set` is built by `bson.Marshal` (`pkg/mongoutil/bulk.go:49-60`), so an org field emptied in Graph is dropped and the stale value survives. The producer's struct compare (`differ.go:34`) then flags that employee `update` every run — a permanent republish loop and a stale spotlight-org doc.
- [medium] Whole upsert set published as one unbounded message — `publisher.go:38,50` — no chunking or size guard. A first run, a backfill, or a mapper change marking every row `update` yields one message that can exceed NATS `max_payload` (zstd only postpones it), failing the run.
- [medium] No `Bootstrap bootstrapConfig` / stream-existence check — `config.go:15-78` — CLAUDE.md requires every service that publishes to a JetStream stream to carry the `BOOTSTRAP_STREAMS`-gated helper; this one has neither the field nor a startup verify, so a deploy pointed at a site without `HR-{central}` fails per-publish instead of at startup. `hr-sync-worker/bootstrap.go:27-42` does both.
- [medium] `EmployeeIDFromGraphID` duplicated with only a comment binding it — `transform/transform.go:67-69` vs `pkg/teamsmigrate/teamsmigrate.go:65-67` — each has its own determinism test (`transform/transform_test.go:60-65`, `pkg/teamsmigrate/teamsmigrate_test.go:37-40`); nothing asserts the two produce equal output, so a change in either silently splits one identity into two.
- [low] Quit `SiteID` is decorative — `publisher.go:57-71` groups quits per site but publishes all on the central subject, and `hr-sync-worker/store.go:111-117` ignores `batch.SiteID`, deleting globally. The per-site `HR-{siteID}` streams the worker bootstraps (`hr-sync-worker/main.go:76-83`) get nothing from this producer.
- [nitpick] Stale deploy/doc references — `deploy/docker-compose.yml:29` sets `ORG_TYPE=group`, absent from `config.go`; `README.md:54` names `transform.SourceTeams` and `model.ChangeTypeNewHire`, neither of which exists.

### Recommendations

- [high] Add `Timestamp int64` to `IEmployeeWithChange`/`IUserWithChange` (or a thin batch wrapper) and stamp it with `time.Now().UTC().UnixMilli()` at `publisher.go:38,50` — this is the CLAUDE.md rule, and it lets `search-sync-worker` retire its stream-sequence guard.
- [high] Publish employees + users as one unit, or make the users lane self-healing — `publisher.go:38-53`; e.g. publish users.upsert first, or derive the diff baseline from both collections, so an employees-only success cannot strand identities.
- [high] Either add a `source` field to `model.IEmployee` and filter on it in `store_mongo.go:57` and in `QuitTeamsEmployees`, or delete the source claims in `README.md:8` and `integration_test.go:70,163` — today the code and its stated contract disagree about a mass-delete path.
- [high] Reconcile `write_store.go` with `hr-sync-worker/store.go` (one match key, one `_id` rule, one skip rule) and cover it with a shared test — ideally lift the write surface into a package both import, as `README.md:48-51` already claims is the case.
- [medium] Chunk the upsert publishes to a bounded batch size and fail fast on an oversize payload — `publisher.go:76-82`.
- [medium] Add `Bootstrap bootstrapConfig` plus a stream-existence verify before the first publish — `config.go`, `main.go:156-163` — matching `hr-sync-worker/bootstrap.go:27-42`.
- [medium] Drop `transform.EmployeeIDFromGraphID` and call `teamsmigrate.EmployeeIDFromGraphID` directly — `transform/transform.go:67` — a compile-time link beats a comment.

## 7. Performance — score 3

### Evidence

- [high] The whole upsert set ships as ONE JetStream message with no size check or chunking — `teams-hr-sync/publisher.go:38` (also `:50`, `:67`), marshalled and zstd'd whole at `publisher.go:76-82`. `IEmployeeWithChange` is ~400 B of JSON (10 `IOrg` fields, `pkg/model/teams_employee.go:6-16`, plus 10 employee fields), so at plausible zstd ratios the batch crosses the NATS default 1 MB `max_payload` in the low tens of thousands of employees. Nothing bounds it: no `nc.MaxPayload()` read, no split. It bites on the worst run: the first stream-mode run diffs against an empty store, so `d.Upserts` is the whole directory. It does not self-heal — nothing is published, so the next run rebuilds the identical batch. Every other batching publisher in the repo caps itself (`broadcast-worker/roomactivity.go:175`, `notification-worker/emit.go:52`, `history-service/cmd/main.go:369`).
- [high] Direct-mode user upserts filter on an unindexed key, making each bulk op a collection scan — `teams-hr-sync/write_store.go:73` (`SetFilter(bson.M{"employeeId": u.EmployeeID})`). Across the whole tree the only `users` index is the unique `account` one from `user-service/mongorepo/users.go:42-44`; no `employeeId` index is created by any service or seed script, and this service defines no `EnsureIndexes` at all — CLAUDE.md requires indexes in the store constructor or an `EnsureIndexes` at startup. A migration of N employees against M user docs is N unindexed `UpdateOne`s, O(N·M) examinations; at N=M=20k that is hours. The sibling consumer avoids it by filtering on the indexed `account` (`hr-sync-worker/store.go:91`).
- [medium] No deadline bounds any MongoDB operation. `main.go:71` builds the run context from `signal.NotifyContext` with no timeout, and `ConnectRead` applies only `ServerSelectionTimeout` (`pkg/mongoutil/poolconfig.go:50`, 2s; `pkg/mongoutil/tuning.go:59` is the sole timeout applied) — never a client operation timeout. A stalled cursor in `ListTeamsEmployees` or a slow `BulkWrite` hangs the pod indefinitely; the only backstop is the `activeDeadlineSeconds` the comment at `main.go:69` assumes, which appears nowhere under `teams-hr-sync/deploy/`. Under `concurrencyPolicy: Forbid` one hung run silently suppresses all later syncs.
- [medium] `ListTeamsEmployees` materializes the entire `hr_employee` collection every run — `store_mongo.go:56-58`, filter `bson.M{}`, no limit, no batching, one slice. The projection is explicit and reflection-derived (`store_mongo.go:21-42`) and the diff needs every field for `*prev != *c` (`differ.go:34`), so the read is defensible — but peak RSS is ~4 full copies (`stored`, `current`, `Upserts`, `users`) plus marshal and zstd buffers.
- [low] `mongoutil.BulkUpsert` pays a `bson.Marshal` + `bson.Unmarshal` round-trip and a fresh `bson.M` per document to build a statically-known `$set` — `pkg/mongoutil/bulk.go:48-60`, looped at `pkg/mongoutil/collection.go:187-189`, reached from `write_store.go:51`.
- [low] Groups are walked strictly sequentially — `collect.go:30-63`: one `GetGroup` then a serial page loop per group, each request bounded at 30s (`pkg/msgraph/msgraph.go:271`). Wall clock is the sum over groups and pages with zero overlap, with no knob to shorten it.
- [nitpick] `seen` is allocated with no size hint and grows to one entry per member — `collect.go:29`.

Checked and absent: goroutines, `time.Sleep`, `map[string]interface{}` payloads, `$lookup`, N+1 store calls in a loop. `encoding/json` is correct here (not a hot-path worker), the Graph token is cached (`pkg/msgraph/msgraph.go:496`), paging streams via callback, `go vet ./teams-hr-sync/...` clean.

### Recommendations

- [high] Chunk the upsert publishes into size-bounded batches — `publisher.go:76-82`. Read `nc.NatsConn().MaxPayload()` in `runStreamMode` (`main.go:143-163`), pass the cap into `newPublisher`, emit successive fitting messages. Removes a hard ceiling on directory size that first bites on day one.
- [high] Add an `EnsureIndexes` on the direct-write store creating `{employeeId: 1}` on `users`, called from `runDirectMode` before the first write — `write_store.go:37-42`. Or re-key the filter to `account` to match `hr-sync-worker/store.go:91`; that also removes the latent duplicate-`account` insert the `employeeId` filter can produce against the unique index.
- [medium] Wrap the context from `main.go:71` in `context.WithTimeout` from a new `SYNC_TIMEOUT` knob (~30m default), bounding both Mongo and the Graph walk and stopping one hung run from suppressing all later ones.
- [medium] Stream the diff baseline instead of materializing it — `store_mongo.go:56`: use the raw cursor and build `storedByAccount` (`differ.go:21`) incrementally so only the map is resident.
- [low] Replace `BulkUpsertByID` with a hand-built `$set` (as `UpsertUserIdentities` already does at `write_store.go:72-85`) on the direct-mode employee path — `write_store.go:51` — dropping two BSON conversions per document.
- [low] Walk groups with a small bounded worker pool in `collect.go:30`, merging into `seen`/`out` under a mutex and paired with `msgraph.WithMaxIdleConns`; keep it bounded so the tenant throttle gate is not tripped.

# bot-message-worker — production readiness review

**Date:** 2026-09-21  
**Branch:** `claude/production-readiness-report-2026-09-21` @ `fe27c91` (base `main`)  
**Overall score:** 1.8 / 5 (baseline 2026-09-01: 2.5, Δ -0.7)  
**Method:** six independent expert reviews (one per dimension) against `CLAUDE.md` and Go-at-scale practice; every finding cites `file:line` on this tree.

## Executive summary

bot-message-worker is the weakest service in the fleet on this audit. Every reviewer flagged the same thread-partition defect: bot thread replies bind `thread_room_id` to the parent *room* ID, while message-worker keys that table by a Mongo ThreadRoom UUID and stamps it onto the parent row, and history-service resolves replies only through that stamp. Bot replies therefore land in a partition no reader queries, and the shared thread-count scan then runs over that wrong partition and blind-writes the result onto the parent, clobbering the user pipeline's count. It also decodes a `MessageEvent` envelope that bot-room-service does not send, so system messages arrive as zero-valued rows that fail and NAK until dropped. Four structural protections its twin has are missing: no outage retry budget (a Cassandra outage past roughly six minutes permanently drops bot messages, versus the hour message-worker survives), no `jobguard` panic guard on the worker goroutine, the consume loop is outside the WaitGroup so the Cassandra session can close under an in-flight message, and no per-message deadline or heartbeat. On the storage rules, none of the ten create INSERTs pin `USING TIMESTAMP` as CLAUDE.md requires, and the encrypted paths bind literal nulls inline — the exact shape the rulebook forbids, which will silently stop clearing legacy rows the moment someone adds the pending pin. `buildCassandraMessage` aliases rather than copies the quoted parent, so the at-rest split mutates the caller's message, and it skips the attachment re-encode, silently dropping quoted attachments on encrypted messages. Coverage is 14.1%, the lowest in the fleet: the entire Cassandra store, bootstrap and wiring are at zero, and `SaveMessage` and both encrypted paths have never been executed by any test.

## 2. Code quality — score 2

## 3. Architecture — score 2

### Evidence

- [high] Bot thread replies are written under a different `thread_room_id` than user replies to the same thread, so they are invisible to thread reads and corrupt the parent's `tcount` — `bot-message-worker/handler.go:65-66` passes `threadRoomID := m.RoomID`; `message-worker/handler.go:380-384` keys the same table by a Mongo ThreadRoom `idgen.GenerateUUIDv7()`. `history-service/internal/cassrepo/thread_messages.go:29` reads `WHERE thread_room_id = ?` with the client's ThreadRoom ID, so a bot reply lands in a partition nobody reads; worse, `store_cassandra.go:276-279` then runs `threadcount.Maintain` over the room-ID partition (bot replies only) and stamps that count onto the shared parent row, clobbering the user pipeline's count.
- [high] `bot-room-service` publishes a bare `model.Message` on the stream this worker decodes as `model.MessageEvent` — `bot-room-service/sysmsg.go:17,46-55,65` vs `handler.go:32-40` and `pkg/model/event.go:29-32` (`{event,message,siteId,timestamp}`). The bare `{id,roomId,type,sysMsgData,createdAt}` decodes cleanly into a zero `evt.Message`; there is no post-decode validation (contrast `message-worker/handler.go:98`), so `SaveMessage` is attempted with empty `message_id`/`room_id` and zero `created_at`, is rejected or written as junk, and the transient branch NAKs it 6× over 12.6 min (`jsretry.go:52-59`, `consumer.go:20`). Every bot room sysmsg is lost, and the `isPermanent` path (`handler.go:41-47`, `metrics.go:9`) is unreachable because nothing produces a Permanent error.
- [high] Consumer loop goroutine is outside the WaitGroup — `main.go:160-173` only `wg.Add`s per-message workers. A message returned by `iter.Next()` and parked on `sem <-` (`:166`) is invisible to the drain step (`:185-194`), so `nc.Drain`/`cassSess.Close()` (`:195-196`) can run under it. `message-worker/main.go:290-295` counts the loop and documents this hazard. `iter.Next` errors are also swallowed (`:163-165`).
- [high] Handler runs without `jobguard.Run` — `main.go:168-171` calls `h.HandleJetStreamMsg` directly. Every other JetStream worker wraps it (`message-worker/main.go:391`, plus broadcast/notification/inbox/outbox/gatekeeper/hr-sync); a deterministic panic here leaves the message un-acked and crash-loops the pod on redelivery.
- [high] No plaintext create pins `USING TIMESTAMP` — `store_cassandra.go:97-116,175-207` (0 hits for `USING TIMESTAMP` in the service) vs `message-worker/store_cassandra.go:192-207,284-320`. CLAUDE.md's Cassandra section says the service "should be pinned when next touched"; it was touched (#407 added `countAndSetParentTcount`, which now runs *after* the commit at `:208-211`/`:263-266` and can NAK an already-committed create), yet the pin was not ported. The encrypted creates also bind `null` inline (`:144,:154,:234,:245,:257`), the form CLAUDE.md says never to use, instead of separate unpinned `stripLegacyPlaintext*` UPDATEs (`message-worker/store_cassandra.go:245,255`).
- [medium] Retry budget diverges from the twin: `buildConsumerConfig` (`main.go:211-216`) uses bare `DurableConsumerDefaults`, while `message-worker/main.go:373` applies `stream.WithOutageRetryBudget(s, jsretry.DefaultBackoff)`. A Cassandra outage longer than ~12.6 min drops bot messages after the bot was told 200.
- [medium] `MESSAGE_BUCKET_HOURS` is not validated — `main.go:38,108`; `message-worker/main.go:105-108` rejects `< 1`. A `0` yields `windowMs=0` and a divide-by-zero panic in `msgbucket.Sizer.Of` on the first message.
- [medium] No `deploy/azure-pipelines.yml` (only Dockerfile + compose; 29 of 37 services have one) and no `//go:generate mockgen` in `store.go:10` (hand-rolled `fakeStore` in `handler_test.go:21`), both against CLAUDE.md's per-service layout.
- Compliant (not restated as findings): consumer-defined narrow `Store` interface, constructor DI, `pkg/subject`/`pkg/stream` builders only (`main.go:147,214`), `bootstrap.go:23-37` sets only `Name+Subjects` and verify-only when disabled, high-throughput `cons.Messages()`+semaphore pattern, durable `bot-message-worker`, backoff from `DurableConsumerDefaults`, `jsretry.Nak` (no bare `Nak()`), `shutdown.Wait` order correct, no INBOX/OUTBOX involvement.

### Recommendations

- [high] Resolve the thread room the same way `message-worker` does (create/lookup the Mongo ThreadRoom, or have `bot-message-handler` resolve and stamp `ThreadRoomID` on the event) and pass that ID to `SaveThreadMessage` — `handler.go:65`; this also makes `threadcount.Maintain` count the right partition.
- [high] Make `bot-room-service/sysmsg.go:46-55` publish `model.MessageEvent{Event: EventCreated, Message, SiteID, Timestamp}`, and add post-decode validation in `handler.go:39` returning `errcode.Permanent(errcode.BadRequest(...))` for empty `ID`/`RoomID`/zero `CreatedAt`, so poison is dropped once with a metric instead of retried.
- [high] `wg.Add(1)`/`defer wg.Done()` around the loop goroutine, log `iter.Next` errors, and wrap the handler call in `jobguard.Run` — `main.go:160-173`, mirroring `message-worker/main.go:290-319,389-402`.
- [high] Port `writeTS`/`USING TIMESTAMP` to the five plaintext creates and replace inline `null`s with separate unpinned strip UPDATEs — `store_cassandra.go:97-116,138-157,175-207,226-262`; port `store_cassandra_writetime_test.go` alongside.
- [medium] Apply `stream.WithOutageRetryBudget(s, jsretry.DefaultBackoff)` in `buildConsumerConfig` — `main.go:212`.
- [medium] Reject `MessageBucketHours < 1` at startup — `main.go:75-77`.
- [medium] Add `deploy/azure-pipelines.yml` and the `//go:generate mockgen` directive in `store.go`.

### Evidence

- [high] Wire-shape mismatch with `bot-room-service` sysmsgs: the worker decodes `model.MessageEvent` and persists `evt.Message`, but `bot-room-service` publishes a bare `model.Message` on the same subject, so every sysmsg decodes to a zero `Message` — `bot-message-worker/handler.go:248-256` — `bot-room-service/sysmsg.go:46-55,65` marshals `model.Message` directly to `subject.BotCanonicalCreated`, and its own test pins that shape (`bot-room-service/handler_test.go:418`). A bare `Message` has no `message` key, so `m.ID`/`m.RoomID` are `""` and `CreatedAt` is zero; `SaveMessage` then INSERTs an empty partition key (`store_cassandra.go:97-103`), which Cassandra rejects, the gocql error is not an `errcode` so `isPermanent` says transient (`handler.go:257,286-292`), and the event is NAKed through `MaxDeliver` and dropped. Bot-created room membership sysmsgs never reach Cassandra (nor search-sync-worker, which also decodes `MessageEvent`, `search-sync-worker/messages.go:180`).
- [high] `thread_room_id` contract diverges from `message-worker`/`history-service`: bot thread replies use the parent room's ID as the partition key — `bot-message-worker/handler.go:281-282` (test pins it: `handler_test.go:127`). `message-worker` partitions by a Mongo `ThreadRoom` UUIDv7 (`message-worker/handler.go:380`) and stamps it onto the parent row (`:464`); `history-service` resolves replies only through that stamp (`history-service/internal/service/threads.go:64-73`, `internal/cassrepo/thread_messages.go:29`). Bot replies therefore land in a partition no parent row points to and are never returned by the thread RPC; a bot-first thread leaves the parent unstamped ("no replies"). Worse, `countAndSetParentTcount` (`store_cassandra.go:211,266,276-279`) runs the shared exact scan on `thread_room_id = roomID` (`pkg/threadcount/count.go:191`) and blind-SETs the parent's `tcount`, so bot and user writers overwrite each other's count for the same parent. All bot replies in a room also share one unbounded partition.
- [medium] `MESSAGE_BUCKET_HOURS` is not validated positive, unlike its peers — `bot-message-worker/main.go:38,108` — `msgbucket.New(0)` yields `windowMs=0` and `Of` divides by it (`pkg/msgbucket/bucket.go:16,21`), so `MESSAGE_BUCKET_HOURS=0` panics on the first message in a worker goroutine instead of failing at startup; `message-worker/main.go:106` and `history-service/internal/config/config.go:284` reject it. Default 360 does match all peers (`message-worker/main.go:51`, `history-service/internal/config/config.go:71`).
- [medium] All six create INSERTs ride the client clock — `store_cassandra.go:97-116,138-157,175-206,227-262` — while `message-worker` pins plaintext creates with `USING TIMESTAMP` (`message-worker/store_cassandra.go:192`). No cross-service cell conflict arises (history-service edits/deletes are also unpinned and later), but a redelivery after an edit still restores the original body; CLAUDE.md names this service as the outstanding migration.
- [low] Sender UDT semantics differ from user rows: `toSender` writes the combined display name into `eng_name` and leaves `company_name`/`app_id`/`app_name` empty — `store_cassandra.go:28-35` — whereas `message-worker` writes `EngName`/`ChineseName` separately (`message-worker/handler.go:836-841`); `BotIdentity.AppID/AppName` (`pkg/model/bot.go:29-30`) never reach the UDT columns that exist for them (`docker-local/cassandra/init/02-udt-participant.cql:5-6`).
- [low] Docs drift on this stream: `docs/nats-traffic-estimation.md:53` lists subject `chat.bot.msg.canonical.{siteID}.>` and consumers "Bot Broadcast Worker, Bot Notification Worker"; code is `chat.bot.canonical.{siteID}.>` (`pkg/subject/bot.go:74`) and the only consumers in the tree are this worker and `search-sync-worker`. `docs/cassandra_message_model.md:89-90` names only `message-worker`/`history-service` for the bucket knob while `:102` names this service as a tcount writer.
- [nitpick] `visible_to` is omitted from every INSERT — `store_cassandra.go:98-102` vs `message-worker/store_cassandra.go:191` — harmless today because `bot-message-handler` never sets it (`bot-message-handler/handler.go:164-177`).

### Recommendations

- [high] Make `bot-room-service/sysmsg.go` publish `model.MessageEvent{Event: EventCreated, Message: msg, SiteID, Timestamp: time.Now().UTC().UnixMilli()}` (or have the worker accept both shapes) and add a cross-service wire test that decodes the sysmsg fixture with the worker's decoder — `bot-room-service/sysmsg.go:46-55`, `bot-message-worker/handler.go:248` — restores sysmsg persistence and stops each one burning six redeliveries.
- [high] Align the thread partition contract: either have the worker resolve/create the `ThreadRoom` via the same store path `message-worker` uses and stamp the parent's `thread_room_id`, or route bot thread replies through `MESSAGES-CANONICAL` so `message-worker` handles them — `bot-message-worker/handler.go:277-283` — until then, disable `countAndSetParentTcount` for bot replies so it cannot clobber user counts.
- [medium] Reject `MessageBucketHours <= 0` at startup — `main.go:75-77` — fail-fast instead of a per-message divide-by-zero panic.
- [medium] Pin plaintext creates with `USING TIMESTAMP` from `CreatedAt` (encrypted ones stay unpinned) and add the writetime test mirroring `message-worker/store_cassandra_writetime_test.go` — `store_cassandra.go:97-116,175-206`.
- [low] Carry `BotIdentity.AppID/AppName/EngName/ChineseName` through `model.Message` (or a bot-specific sender field) so `toSender` can populate the UDT the same way `senderFrom` does — `store_cassandra.go:28-35`.
- [low] Fix `docs/nats-traffic-estimation.md:53` subject/consumer list and add `bot-message-worker` to `docs/cassandra_message_model.md:89-90`.

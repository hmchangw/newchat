# message-gatekeeper — production readiness review

**Date:** 2026-09-21  
**Branch:** `claude/production-readiness-report-2026-09-21` @ `4e34d6b` (base `main`)  
**Overall score:** 3.3 / 5 (baseline 2026-09-01: 3.3, Δ +0.0)  
**Method:** six independent expert reviews (one per dimension) against `CLAUDE.md` and Go-at-scale practice; every finding cites `file:line` on this tree.

## Executive summary

message-gatekeeper is the site's single MESSAGES ingress and is in good shape: error tiering is textbook, the consumer pattern, backoff, dedup and shutdown all match the rulebook, gosec and the repo semgrep rules are clean, and the handler logic outside `main` sits above 90% coverage. The findings that matter are contract and correctness gaps rather than structure. `docs/client-api.md`'s msg.send success schema has drifted from the wire: the reply is the full `model.Message` including `type` and raw base64 `attachments`, while the doc says `type` is not populated and lists neither field; the error table documents a not-found string history-service never emits and omits six rejections the gatekeeper does emit. A late redelivery or the client retry the docs recommend can leave two rows in `messages_by_room`, because `CreatedAt` is minted per delivery and the canonical dedup window is the 2-minute server default, so the doc's "a retry can never leave two copies in history" claim is false for the timeline table. The large-room rejection path logs and returns the same error (double-logged by `Classify`), the request-ID bridge from the payload is applied only inside `processMessage` so the client reply header and NAK logs carry a different ID, and the handler context has no per-message deadline while the per-leg timeouts sum past `AckWait`. Coverage is 66.4% only because `main` holds 28% of the tree's statements at 0%; the history `GetMessageByID` client and its wire mirror are hand-copied in three services, the L1 cache knobs are re-declared per service with a `60s` vs `2m` default drift, and `processMessage` is a 216-line function with a 1051-line test table.

## 2. Code quality — score 4

## 3. Architecture — score 4

### Evidence

- [medium] History `GetMessageByID` request client is hand-rolled three times across services — `message-gatekeeper/fetcher_history.go:24-114` — `broadcast-worker/parent_fetcher.go:24-76` and `notification-worker/parent_fetcher.go:38-76` carry the same struct (`nc *o11ynats.Conn` + `metrics natsmetrics.Publisher`), the same `getMessageByIDRequest` wire mirror, the same 2s constant and the same `errcode.Parse` envelope-detect. `fetcher_history.go:38-39` admits the source struct "isn't importable", so history-service's reply contract is now mirrored in three consumers that must be edited in lockstep.
- [medium] `historyParentFetcher` depends on the concrete `*o11ynats.Conn` rather than a consumer-defined interface — `message-gatekeeper/fetcher_history.go:24,33` — the only thing it needs is `Request(ctx, subj, data, timeout)`. The direct consequence is that the untagged unit test `fetcher_history_test.go:27-40` boots an in-process `nats-server` (`natsserver.NewServer`, line 30), against CLAUDE.md's "never connect to real ... NATS in unit tests". Hermetic (Port -1, no network) and shared with five sibling files, so the spirit holds, but the letter does not and the fix is a one-method interface.
- [low] Panic guard is opt-in per service instead of default in the shared consume loop — `message-gatekeeper/main.go:283-296` — `guardedProcessor` is a 3-line adapter re-declared in `broadcast-worker/main.go:554`, `message-worker/main.go:391`, `notification-worker/main.go:363`, etc.; the comment at `main.go:283-291` records that this very service once shipped without it. For the site's only MESSAGES consumer that omission is a crash loop, so `natsmetrics.Start` (`pkg/natsmetrics/loop.go:24`) should apply `jobguard.Run` itself.
- [low] Subject grammar parsed outside `pkg/subject` — `message-gatekeeper/handler.go:327-333` — `accountFromSubject` re-implements `chat.user.{account}` token extraction with `strings.Split`, the one place in the service that knows subject layout without going through the package. `subject.ParseUserRoomSiteSubject` (`pkg/subject/subject.go:113-119`) is the sanctioned parser; a lenient `ParseUserAccount` sibling belongs next to it.
- [low] Synchronous request/reply coupling on the async ingress path with a non-configurable timeout — `message-gatekeeper/fetcher_history.go:19`, `handler.go:464,477` — every thread reply/quote issues up to two `nc.Request` calls to history-service with a hard-coded 2s `historyRequestTimeout`, while the neighbouring `ThreadParentRecheckDelay` is env-driven (`main.go:53`). A slow (not down) history-service holds each worker slot ~2-4s, and the `MaxWorkers` semaphore (`main.go:231`) is shared with plain sends, so thread traffic can head-of-line-block the site's single MESSAGES consumer. Fail-open tiering (`handler.go:596-617`) is correct; the knob just isn't exposed.
- [low] `processMessage` fuses four concerns in one 215-line body — `message-gatekeeper/handler.go:338-553` — pure request validation (`341-415`, no dependencies), subscription/large-room authz (`418-456`), enrichment (`462-503`) and event build/publish (`505-552`). `resolveThreadParent`/`resolveQuoteSnapshot` already show the extraction pattern; the validation block is the obvious next `validateSendRequest(req, siteID) error`.
- [nitpick] `bootstrapStreams` is not a no-op when disabled — `message-gatekeeper/bootstrap.go:62-71` — it performs `js.Stream()` existence checks. Every sibling does the same (`broadcast-worker/bootstrap.go:38`, `message-worker/bootstrap.go:61`, `inbox-worker/bootstrap.go:59`) and fail-fast is the better behaviour; CLAUDE.md's "no-ops when Enabled=false" wording is what drifted.
- [nitpick] Exported `Handler`/`NewHandler`/`MongoStore`/`NewMongoStore` in `package main` — `handler.go:62,107`, `store_mongo.go:19,31` — CLAUDE.md asks for unexported handler/store implementations; siblings are mixed (`broadcast-worker/store_mongo.go:34` uses `mongoStore`). Cosmetic in a main package.

Verified clean: subjects only via `pkg/subject` (`handler.go:152,317,532`); stream schema `Name+Subjects` from `pkg/stream` behind `BOOTSTRAP_STREAMS` (`bootstrap.go:24,48-58`); `cons.Messages()`+semaphore via `natsmetrics.Start`, `PullMaxMessages(2*MaxWorkers)`, WaitGroup (`main.go:222-236`); durable named after the service, backoff via `stream.DurableConsumerDefaults(stream.WithOutageRetryBudget(...))`, no hardcoded `BackOff` (`main.go:277-281`); only `jsretry.Nak` (`handler.go:254`); shutdown `iter.Stop → wg.Wait → nc.Drain → DB disconnect` via `shutdown.Wait` (`main.go:248-269`); two-method consumer-defined `Store` with mockgen (`store.go:12,25-28`); publish/reply injected as func fields (`handler.go:65-66`); canonical publish deduped with `WithMsgID` (`handler.go:534`); no INBOX/OUTBOX involvement.

### Recommendations

- [medium] Extract a shared history client (`pkg/historyclient` or reuse `user-service/historyclient`) with one `GetMessageByID(ctx, account, roomID, siteID, id, into any)` and the envelope-detect in one place — `message-gatekeeper/fetcher_history.go`, `broadcast-worker/parent_fetcher.go`, `notification-worker/parent_fetcher.go` — collapses three wire mirrors into one so a history-service reply change is a single edit.

- [high] `docs/client-api.md` §4 msg.send success schema has drifted from the reply the gatekeeper actually sends — `message-gatekeeper/handler.go:813-814`, `:844` — The reply is `sonic.Marshal(msg)` of the full `model.Message`, which carries `Type: req.Type` and `Attachments: req.Attachments` (raw base64 blobs, not decoded `Attachment[]`; `handler_test.go:2374` asserts `attachments` is present). `docs/client-api.md:6437` states the gatekeeper does **not** populate `type`, and the success tables at `docs/client-api.md:6420-6435` and `docs/client-api/request-reply.md:2299-2312` list neither `type` nor `attachments`.
- [high] msg.send error table documents a wire string the service never emits and omits six it does — `message-gatekeeper/handler.go:943-949` — A terminal quote-fetch error is returned verbatim from history-service, whose not-found text is `message not found` (`history-service/internal/service/utils.go:88,91`), not `quoted parent {id} not found` as `docs/client-api.md:6467` claims; the `forbidden`/`outside_access_window` passthrough (`history-service/internal/service/messages.go:437`) is undocumented for quotes. Undocumented rejections: `invalid quoted parent message ID` (`handler.go:665`), `too many attachments` (`:686`), `attachment[i] must not be empty` (`:691`), `attachments exceed maximum size` (`:696`), `unmarshal send message request` (`:476`), and the permanent `internal` `canonical message exceeds broker max_payload` (`:836`).
- [medium] A late redelivery or a same-`id` client retry can leave two rows in `messages_by_room` — `message-gatekeeper/handler.go:758,808,830` — `CreatedAt` is `time.Now()` per delivery and the dedup key for `created` is the bare message ID (`pkg/natsutil/canonical_dedup.go:44`) inside the server-default 2-minute window (`bootstrap.go:54-57` sets no `Duplicates`). If the canonical publish lands but the Ack at `:558` is lost and redelivery arrives >2 min later (pod down across a rollout, or the client retry the docs recommend after `unavailable`), message-worker writes a second row because `created_at` is a clustering column (`docs/cassandra_message_model.md:244`). `docs/client-api.md:6469` asserts "a retry can never leave two copies in history", which is false for the timeline table.
- [medium] The history-service request/reply wire shape is hand-mirrored in four consumers — `message-gatekeeper/fetcher_history.go:39-63` — `getMessageByIDRequest` and the narrow projection are duplicated in `broadcast-worker/parent_fetcher.go:37-44`, `notification-worker/parent_fetcher.go:51-58` and `room-service/reader_history.go:50,108` because the source lives under `history-service/internal/models` (`message.go:74`). A field rename in history-service breaks quote/thread-parent resolution silently (both paths fail open: placeholder / ship without `threadParentMessageCreatedAt`).
- [medium] L1 cache knobs re-declared per service with their own `envDefault` — `message-gatekeeper/main.go:54-55,60-61` — `ROOM_META_CACHE_TTL`/`ROOM_META_CACHE_SIZE` and `USER_CACHE_TTL`/`USER_CACHE_SIZE` carry their own tags here and in `broadcast-worker/main.go:73-77`, `notification-worker/main.go:57-71`, `room-worker/main.go:57-60` (where the TTL default is `60s`, not `2m`). The L2 tiers are correctly mounted from `roommetacache`/`userstore`/`subauthcache` (`main.go:57-62`), so this is the in-process LRU only, but it is the exact drift CLAUDE.md's "declare once in the owning package" rule exists to prevent.
- [low] Raw subject parsing beside the `pkg/subject` parser — `message-gatekeeper/handler.go:623-629` — `accountFromSubject` re-implements `chat.user.{account}` extraction with `strings.Split`; every subject *build* (`MsgCanonicalCreated`, `UserResponse`, `MsgGet`) correctly uses `pkg/subject`, so this is a parse-only duplication.

### Recommendations

- [high] Fix `docs/client-api.md` §4 and `docs/client-api/request-reply.md` msg.send success schema: add `type` (echoed when `"important"`) and `attachments` (base64 blobs, **not** decoded), and delete the "does not populate `type`" sentence — `docs/client-api.md:6420-6437` — clients parsing the reply against the doc will mis-render attachment sends.
- [high] Correct the error table: replace `quoted parent {id} not found` with the passthrough `message not found` (`not_found`), add the `forbidden`/`outside_access_window` quote passthrough, and add the six missing rejections listed above — `docs/client-api.md:6453-6470` — the table is the frontend's branching contract.
- [medium] Make the `created` canonical event idempotent across redeliveries: derive `CreatedAt` deterministically (e.g. from the JetStream message metadata timestamp of the original MESSAGES publish, which is stable across redeliveries) or set an explicit `Duplicates` window on MESSAGES-CANONICAL that covers the outage retry budget — `handler.go:758`, `pkg/stream/stream.go:22` — closes the duplicate-timeline-row window and makes the docs' "never two copies" claim true.
- [medium] Move `GetMessageByIDRequest` and the by-id reply projection into `pkg/model` (or `pkg/model/cassandra`) and import it from all four consumers — `fetcher_history.go:39-63` — one struct, one place to change, compile-time drift detection.
- [medium] Add an L1 `CacheConfig{Size,TTL}` to `roommetacache` and `userstore` (like their `TTLConfig`) and mount it in each service — `main.go:54-55,60-61` — removes the four-way tag duplication and the `60s` vs `2m` default split.
- [low] Replace `accountFromSubject` with a `pkg/subject` helper (e.g. `subject.AccountToken(subj)`) — `handler.go:623` — keeps every subject parse in one package.

## 7. Performance — score 4

### Evidence

- [medium] Sender display-name lookup fetches whole `users` documents on every cold miss — `message-gatekeeper/handler.go:490` → `pkg/userstore/userstore.go:87` — `FindUserByID` runs `FindOne(ctx, bson.M{"_id": id})` with no projection, while its sibling `FindUserByAccount` (`userstore.go:99`) projects the seven-field `userProjection`. The gatekeeper needs only `engName`/`chineseName` (`handler.go:492`) but decodes `Services`, `Settings`, `Permissions` and `Chatlist` (`pkg/model/user.go:71-79`), then `pkg/userstore/l2.go:304` marshals the full struct into Valkey and `cache.go:60` pins it in a 10 000-entry L1. Violates CLAUDE.md "Always project precisely" on the message-send hot path.
- [medium] No per-message deadline or `InProgress` heartbeat; the sum of per-leg timeouts exceeds `AckWait` — `message-gatekeeper/main.go:233-236`, `pkg/natsmetrics/loop.go:55-66` — the handler ctx carries no deadline (o11y `Next` only restores baggage). Each leg is individually bounded: subscription 10s (`subcache.go:18`), room meta 10s (`pkg/roommetacache/roommetacache.go:34`), user 10s (`pkg/userstore/cache.go:19`), up to three 2s history RPCs plus a 150ms wait (`fetcher_history.go:19`, `handler.go:586-589`), canonical publish 5s (nats.go `defaultAPITimeout`). Worst case ≈ 41s against `ACK_WAIT=30s` (`pkg/stream/consumer.go:19`). A stalled-dependency incident then has JetStream redeliver a message whose first attempt is still running: the canonical publish is deduped only by the stream's default 2m window (`pkg/stream/stream.go:22-27` sets no `Duplicates`), but the client receives two replies. `room-worker` already uses `jsretry.Heartbeat`; this consumer does not.
- [low] Unsubscribed senders bypass every cache tier and cost one Mongo `FindOne` per message — `message-gatekeeper/subcache.go:88-91`, `pkg/subauthcache/subauthcache.go:197-199` — negative results are deliberately not cached at L1 or L2. A client publishing to a room it is not in (the subject ACL permits any `roomID`) drives an unbounded Mongo read rate that the breaker never trips (not-subscribed is a success per `store_mongo.go:77-78`). The just-joined correctness argument (`main.go:124-125`) justifies no long negative TTL, not the absence of a seconds-scale one.
- [low] Quote-path sonic codecs are not pre-warmed — `message-gatekeeper/pretouch.go:14-18`, `fetcher_history.go:53,75,97` — `quotedParentProjection` and `getMessageByIDRequest` are distinct types with their own JIT codecs; the comment's reasoning ("narrow projection … needs no warm-up") is wrong: the first quoted/thread send after each boot pays sonic's compile latency inside a 2s request budget.
- [low] `time.Sleep` used as goroutine synchronization in a unit test — `message-gatekeeper/subcache_test.go:146` — sleeps 20ms so 20 goroutines "probably" enter `DoChan` before `close(gate)`; the assertion does not actually depend on it (late callers hit L1 after the first populate), so it is pure flake surface. `:114` waits for wall-clock TTL expiry of `expirable.LRU`, which has no clock injection — tolerable.
- [nitpick] Message body marshalled twice per accepted send — `message-gatekeeper/handler.go:527` and `:548` — `evt` embeds `msg` (`pkg/model/event.go:31`), so the same `Message` is sonic-encoded once for the canonical event and once for the reply (up to 20KB content + 8KB attachments).
- [nitpick] Subject split twice per message — `message-gatekeeper/handler.go:147` (`accountFromSubject`, `strings.Split`) then `:152` (`subject.ParseUserRoomSiteSubject`, `pkg/subject/subject.go:114`, another `strings.Split`) — two slice allocations where one parse would do.

### Recommendations

- [medium] Add `options.FindOne().SetProjection(userProjection)` to `FindUserByID` — `pkg/userstore/userstore.go:87` — one-line fix that shrinks the cold-miss BSON decode, the Valkey L2 payload and the L1 footprint for all three hot-path consumers (gatekeeper, broadcast-worker, message-worker); confirm no caller reads `Settings`/`Permissions`/`Chatlist` through the cache first.
- [medium] Bound each message with a deadline derived from `stream.ConsumerSettings.EffectiveAckWait()` (e.g. 80%) in the `guardedProcessor` closure, and/or start `jsretry.Heartbeat` per message as `room-worker` does — `message-gatekeeper/main.go:233-236` — so an attempt either finishes or NAKs before JetStream redelivers, eliminating the duplicate-reply window.
- [low] Set an explicit `Duplicates` window on MESSAGES-CANONICAL at least as long as the longest possible in-flight attempt plus one redelivery gap — `pkg/stream/stream.go:22-27` — today dedup silently relies on the 2m server default.
- [low] Cache "not subscribed" at L1 for a few seconds (keyed like positives, invalidated on the existing bust path) or rate-limit per `(account, roomID)` miss — `message-gatekeeper/subcache.go:88-91` — caps the Mongo read amplification from a misbehaving client without meaningfully delaying a just-joined member.
- [low] Add `reflect.TypeOf(quotedParentProjection{})` and `reflect.TypeOf(getMessageByIDRequest{})` to `pretouchTypes` and fix the comment — `message-gatekeeper/pretouch.go:14-18` — removes the first-quote JIT spike from the 2s history budget; extend `pretouch_test.go` to assert the set.
- [low] Replace the 20ms sleep with a gate that counts goroutine entry (a `sync.WaitGroup` released inside the mocked `GetSubscription`, or drop the sleep entirely) — `message-gatekeeper/subcache_test.go:146`.
- [nitpick] Parse the subject once and pass the account into the log enrichment — `message-gatekeeper/handler.go:147,152` — and consider slicing the reply bytes out of the already-encoded event rather than re-marshalling `msg` — `handler.go:548`.

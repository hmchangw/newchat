# upload-service — production readiness review

**Date:** 2026-09-21  
**Branch:** `claude/production-readiness-report-2026-09-21` @ `4c07ee6` (base `main`)  
**Overall score:** 3.2 / 5 (baseline 2026-09-01: 3.0, Δ +0.2)  
**Method:** six independent expert reviews (one per dimension) against `CLAUDE.md` and Go-at-scale practice; every finding cites `file:line` on this tree.

## Executive summary

upload-service handles untrusted user files and its input-validation boundary does not hold. The media-type allow/deny filter trusts the client's declared `Content-Type` whenever it is set and not the generic fallback, so a client posting SVG bytes labelled as a PNG defeats the default SVG blacklist entirely — and the code comment two functions away asserts the opposite invariant. The images endpoint is worse: it validates by filename extension only, with no sniffing and no filter, so the same file renamed passes. Neither endpoint caps the request body, so the whole upload is spooled to the container's temp directory before any size check runs, and the images path can spool a quarter of a gigabyte per request; nothing bounds concurrent uploads either, although the service's own comment says ephemeral storage must fit the concurrent-upload total. Exploitability is capped, not closed, by the download path always sending an attachment disposition and a locked-down content policy. On the integration side two contract breaks would make real data unreachable: the collection the download path reads has no producer anywhere in the repository (the migration pipeline writes a differently-named one), and legacy attachment URLs of one shape are rewritten onto a route the service does not serve, contradicting both the code's own comment and the client API doc. The Drive client carries no request context, so that leg loses request-ID logging, trace parentage and cancellation, and it runs on a bare transport with two idle connections per host. Coverage is 76.7%, three points under the floor, and the gap is concentrated: `run` is untested, every error branch of the file-upload handler is uncovered while the equivalents on the images handler are tested, and the config test covers one field of thirty-five.

## 2. Code quality — score 3

### Evidence

- [high] The media-type allow/deny gate is bypassable with a client-supplied `Content-Type` — `upload-service/mediatype.go:217` — `resolveMediaType` returns the declared type verbatim whenever it is non-empty and not `application/octet-stream`, without reading a byte (asserted by `mediatype_test.go:163` and `:282`). A client posting SVG bytes as `Content-Type: image/png` gets `mime = "image/png"`, so `h.mimeFilter.allowed` (`handler.go:277`) never sees the real type and the default `FILE_UPLOAD_MEDIA_TYPE_BLACKLIST=image/svg+xml` (`main.go:75`) is defeated; a whitelist is defeated the same way. The comment at `handler.go:268-272` asserts the opposite invariant ("the real type comes from the bytes and the name … Filtering THAT … is what stops a blacklisted upload arriving under a generic label"), so code and stated contract disagree. Exposure is capped, not closed, by the download path always sending `Content-Disposition: attachment` + `Content-Security-Policy: default-src 'none'` (`handler.go:377-381`, `:430-436`).
- [high] The images endpoint validates untrusted files by filename extension only — `upload-service/handler.go:469` — `preprocessFiles` gates on `drive.AllowedImageFileTypes[filepath.Ext(...)]` (png/jpeg/jpg/heic, `pkg/drive/images_file.go:9`) with no sniff and no `mimeFilter`. `evil.svg` renamed `evil.png` is accepted and stored as an image. Same class as the finding above; both should route through `resolveMediaType` + `mimeFilter`.
- [high] No cap on the request body, so the size check runs after the upload is already on disk — `upload-service/handler.go:237` / `:254` — `c.MultipartForm()` parses and spools the *entire* body (anything over `MaxMultipartMemory = 1 MiB`, `main.go:32/181`) to the OS temp dir before `fh.Size > h.maxFileSize` is evaluated; with `FILE_UPLOAD_MAX_FILE_SIZE=-1` the check is skipped entirely. Nothing calls `http.MaxBytesReader` anywhere in the service. Sibling `media-service/upload.go:58` does exactly this ("Size cap before reading the body"), so the pattern exists in-repo. An authenticated client can exhaust the pod's ephemeral storage inside one 15-minute `ReadTimeout` window.
- [high] A knob shared by two services is re-declared with its own env tag and default — `upload-service/main.go:101` — `MinioDownloadTimeout time.Duration \`env:"MINIO_DOWNLOAD_TIMEOUT" envDefault:"5m"\`` is declared identically and independently in `client-update-service/config.go:24`. CLAUDE.md §6 Configuration: a knob used by more than one service is declared once in the owning package (`pkg/minioutil`) and mounted as a named field, never re-declared per service. Values agree today; the drift the rule exists to prevent is one edit away.
- [low] Sentinel error compared with `!=` instead of `errors.Is` — `upload-service/main.go:228` — `if err != nil && err != http.ErrServerClosed`. Works today only because `srv.Shutdown` returns the unwrapped sentinel. The repo majority (`media-service/main.go:143`, `admin-service/main.go:174`, `botplatform-service/main.go:160`) uses `errors.Is`.
- [low] A missing MinIO object is reported as 503, not 404 — `upload-service/handler.go:419-422` — every `s3.Open` failure, including `NoSuchKey` from the `Stat` probe (`store_minio.go:136`), becomes `errcode.Unavailable`. The Mongo-metadata-present / object-absent case is a genuine 404; as written it burns the error budget and invites client retries that can never succeed.
- [nitpick] Request-ID log plumbing duplicated — `upload-service/middleware.go:140` re-inlines the exact body of `logCtx` (`handler.go:91`) instead of calling it.
- [nitpick] Bare `return err` — `upload-service/store_minio.go:55` — `cancelReadCloser.Close` passes the inner Close error through unwrapped. Defensible for an `io.Closer`, but it is the one un-annotated error return in the service.

### Recommendations

- [high] Make `resolveMediaType` sniff-authoritative for the *filter* decision — `mediatype.go:216` — either drop the declared-type shortcut, or keep the declared value as the recorded type while filtering on the sniffed/extension-derived type. Add a table case for "declared image/png + SVG bytes → rejected".
- [high] Run `preprocessFiles` through the same resolver + `mimeFilter` — `handler.go:463` — so both endpoints share one validation path for untrusted bytes.
- [high] Wrap the body before parsing: `c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, limit)` at the top of `HandleUploadFile`/`HandleUploadImages` (`handler.go:212`, `:135`), mirroring `media-service/upload.go:58`; give `FILE_UPLOAD_MAX_FILE_SIZE=-1` a hard ceiling rather than "unbounded".
- [medium] Move `MINIO_DOWNLOAD_TIMEOUT` into a `minioutil.Config` mounted as a named field in both services — `main.go:101`, `client-update-service/config.go:24`.
- [low] `errors.Is(err, http.ErrServerClosed)` at `main.go:228`; map `minio.ToErrorResponse(err).Code == "NoSuchKey"` to `errcode.NotFound` at `handler.go:421`.

## 3. Architecture — score 4

### Evidence

- [medium] Upload body is fully spooled to disk BEFORE any size limit is applied — `upload-service/handler.go:254` — `c.MultipartForm()` (`handler.go:161`, `:237`) calls `ParseMultipartForm(MaxMultipartMemory)`, which streams the *entire* body to temp files with no aggregate cap; the `fh.Size > h.maxFileSize` check runs after that. No `http.MaxBytesReader` anywhere in the service. The images endpoint compounds it: `MAX_IMAGES=10` × `MAX_IMAGE_SIZE_BYTES=25 MiB` = 250 MiB of spool per request, again only checked post-parse (`handler.go:465`). `FILE_UPLOAD_MAX_FILE_SIZE=-1` (documented as legal, `main.go:71`) makes it unbounded.
- [medium] Nothing bounds concurrent uploads, although `main.go:32` states the requirement — `upload-service/main.go:179-208` — the comment says "ephemeral storage must fit the concurrent-upload total", but no `ginutil.MaxConcurrency`, no `ginutil.LimitListener`, and `ReadTimeout`/`WriteTimeout` are 15m (`main.go:206-207`), so a slow client holds its spooled temp file that long. `user-service` uses both levers (`user-service/main.go:398`, `user-service/routes.go:25`); this service, the one that actually writes to disk, uses neither.
- [medium] The two upload endpoints use different trust models for media type — `upload-service/handler.go:469` vs `:272-281` — `HandleUploadFile` sniffs content, promotes a renamed SVG (`mediatype.go:485`) and runs `mimeFilter` (default blacklist `image/svg+xml`). `HandleUploadImages` validates only `filepath.Ext` against `drive.AllowedImageFileTypes`, so `payload.svg` renamed `logo.png` passes there — exactly the bypass `resolveMediaType` exists to close. Mitigated on read by `Content-Disposition: attachment` + `default-src 'none'` (`handler.go:377-381`), so not a live XSS, but the boundary is inconsistent.
- [medium] Access log is not trace-correlated — `upload-service/middleware.go:76` — uses `slog.Info`, not `slog.InfoContext`. `obs.Init` installs the o11y SDK logger as the slog default (`pkg/obs/obs.go` package doc), so the one line per request that ops greps carries no trace/span id, unlike `pkg/ginutil/middleware.go:67` and `media-service/middleware.go:50`.
- [low] Request-ID and access-log middleware are re-implemented instead of taken from `pkg/ginutil` — `upload-service/middleware.go:58-86` — `ginutil.RequestID()`/`AccessLog()` exist and are used by 7 services (auth, user, portal, admin, tcard, botplatform, teams-room-inspector). The local copy also drops `idgen.ResolveRequestID`'s malformed-inbound Warn (`pkg/ginutil/middleware.go:23-29`). The local `corsMiddleware` is genuinely different (credentialed allowlist vs `ginutil.CORS`'s wildcard) and is justified.
- [low] Drive URL/token are not `required` — `pkg/drive/config.go:12-13`, mounted at `upload-service/main.go:103,105` — `MONGO_URI`, `MINIO_*`, `SITE_ID`, `BOTPLATFORM_URL` are all `required`, but an empty `DRIVE_URL` starts the service cleanly and every upload then 500s at runtime. CLAUDE.md requires connection strings/secrets be `required`.
- [low] Session callers' `p.SiteID` is carried but never enforced — `upload-service/middleware.go:216-232` — the comment argues membership gating makes locality redundant; that holds only if `account` is globally unique, since `MemberSiteID` filters on `u.account` alone (`store_mongo.go:31`). `media-service/middleware_auth.go:46` enforces locality explicitly.
- [low] No `mongoutil.WarnMissingIndexes` guard on the borrowed `subscriptions` collection — `upload-service/store_mongo.go:26-41` — the `(roomId, u.account)` index is `room-service/store_mongo.go:124`'s; `inbox-worker/main.go:563` and `user-service/mongorepo/subscriptions.go:80` use the repo's consumer-side warn pattern for this exact dependency.

Verified correct, no action: flat layout per CLAUDE.md; consumer-defined `Store` with only the two methods used + mockgen directive (`store.go:11-37`); consumer-side `driveClient`/`objectStore` (`handler.go:40-49`); constructor DI; routes only in `routes.go` with `/healthz`; all error paths via `errhttp.Write` with Tier-1 `errcode`, no log-and-return; `shutdown.Wait` order correct and the bind-failure path returns before `<-shutdownDone` (`main.go:227-231`) rather than hanging. No NATS client at all, so every JetStream/stream-bootstrap/subject-builder/outbox rule is N/A. `go vet` clean.

Two-store consistency: there is no dual write. The service performs **zero** writes — `Store` is read-only, MinIO is read-only (`store_minio.go` has only `Open`), and blob+metadata are written together by the external Drive service (`pkg/drive/uploader.go:93`). The `uploads` docs read by `HandleDownloadMinioS3File` come from the legacy stack (`main.go:55-56`). MinIO-ok/Mongo-fail cannot occur. Residual gap: orphan blobs — `HandleUploadFile` returns an attachment and the client separately publishes the message, with no GC if it never does. `media-service` does **not** consume this service's output (different bucket and collections); they are siblings, not a pipeline.

### Recommendations

- [medium] Wrap `c.Request.Body` in `http.MaxBytesReader` sized to `maxFileSize` (or `maxImages × maxImageSize`) before calling `c.MultipartForm()` — `upload-service/handler.go:161,237` — moves rejection to first-byte instead of after a full disk spool, and makes `FILE_UPLOAD_MAX_FILE_SIZE` an actual resource bound.
- [medium] Add `ginutil.MaxConcurrency` on the `/api/v1` group and `ginutil.LimitListener` on the listener, with an `UPLOAD_MAX_CONCURRENT` knob — `upload-service/main.go:192,200` — turns the `main.go:32` disk-sizing comment into something the service enforces rather than assumes.
- [medium] Run `resolveMediaType` + `h.mimeFilter.allowed` inside `preprocessFiles` as well — `upload-service/handler.go:463-481` — one validation model for both upload paths; the reader is already open there, so the sniff is free.
- [medium] Switch the access log to `slog.InfoContext(c.Request.Context(), ...)` — `upload-service/middleware.go:76` — restores trace correlation; simplest form is to delete `requestIDMiddleware`/`accessLogMiddleware` and use `ginutil.RequestID()`/`ginutil.AccessLog()`, keeping only the local `corsMiddleware`.
- [low] Mark Drive URL/token required — `pkg/drive/config.go:12-13` (`env:"URL,required,notEmpty"`) or validate in `run()` after `env.ParseAs` — fail fast instead of 500ing every upload. Check the other `drive.Config` consumers before changing the shared tag.
- [low] Collapse `NewHandler`'s ten positional parameters into a `handlerDeps`/`handlerConfig` struct — `upload-service/handler.go:72-73` — adding the next knob currently touches `main.go`, `handler.go` and every construction site in `handler_test.go`.

## 6. Integration — score 3

## 7. Performance — score 3

### Evidence

- [high] No request-body cap: the configured size limits are enforced only *after* the whole body is spooled to disk — `upload-service/handler.go:237` (parse) vs `:254` (cap), and `handler.go:161` vs `:169`. `c.MultipartForm()` → `ParseMultipartForm(1 MiB)` writes everything past 1 MiB to `os.TempDir()` with no overall ceiling, so an authenticated room member POSTing 50 GiB (or 10k images) fills ephemeral storage and is only then rejected with "file size exceeds limit". The sibling service already does it right: `media-service/upload.go:58` installs `http.MaxBytesReader` before reading. No gateway cap exists either (`docker-local/traefik`, no `maxRequestBodyBytes`).
- [medium] No admission control on a service whose per-request cost is a multi-hundred-MiB temp file plus a Drive connection held for minutes — `upload-service/routes.go:20-26` and `main.go:180-197` use neither `ginutil.MaxConcurrency` (`pkg/ginutil/limit.go:20`) nor `ginutil.LimitListener`, both repo-owned and used by `user-service/routes.go:25` / `main.go:398`. With `ReadTimeout` 15m (`main.go:206`) concurrency is bounded only by how many sockets clients open.
- [medium] Drive client runs on a bare `&http.Transport{}` — `pkg/drive/uploader.go:64`, installed into both the upload and download clients at `:66-67`. Zero `MaxIdleConnsPerHost` means the stdlib default of **2**, so the 3rd concurrent upload/download pays a fresh TCP+TLS1.3 handshake, and there is no `DialContext` timeout, `TLSHandshakeTimeout` or `IdleConnTimeout` — a blackholed Drive host hangs to the 5m client timeout. `restyutil.WithMaxIdleConns` exists and is used for the botplatform hop at `main.go:191`, but not here.
- [medium] Nothing on the Drive leg is context-aware, so a client disconnect never cancels the upstream work — `pkg/drive/uploader.go:159` uses `http.NewRequest` (not `NewRequestWithContext`), and `:202`/`:227` issue resty calls with no `SetContext`. The handler interface itself takes no `ctx` (`upload-service/handler.go:40-44`). An abandoned 100 MiB download keeps pulling from Drive for up to 5m, and the otelhttp egress span has no parent, so the dominant latency component is invisible in the request trace.
- [medium] `http.Server` sets no `IdleTimeout` — `upload-service/main.go:200-208`. Go then falls back to `ReadTimeout`, so every keep-alive connection is held **15 minutes** idle. Peers use 60s/120s (`search-service/main.go:318`, `user-service/httpserver.go:21`).
- [low] No startup index assertion for the membership query `{roomId, u.account}` — `upload-service/store_mongo.go:128`. The index is created by `search-service/store_mongo.go:43`, and other consumers guard with `mongoutil.WarnMissingIndexes` (`inbox-worker/main.go:563`, `user-service/mongorepo/subscriptions.go:80`); upload-service does neither, so a missing index degrades silently into a collection scan per upload *and* per download.
- [low] Membership is re-read from Mongo on every request (`handler.go:445`), including each `<img>`-driven download in a room view. `pkg/roomsubcache` exists for exactly this, though its `Member` projection carries `HomeSiteID`, not the room's `siteId` this handler needs — so adoption is not a drop-in.

Verified negatives (no finding): body streaming is real and regression-tested end to end — `upload-service/upload_stream_test.go:321` asserts a 100 MiB upload peaks under 16 MiB heap, and `pkg/drive/multipart.go:349` builds the multipart body as a reader chain with a summed `Content-Length`. Image dimensions use `image.DecodeConfig` (`upload-service/dimensions.go:28`), which reads only the header and allocates no pixel buffer, so there is no decompression-bomb amplification. Both Mongo reads project explicitly (`store_mongo.go:130`, `:145`), there is no `$lookup`, no N+1 loop, no `map[string]interface{}` payload, no `time.Sleep`, and both goroutines in `main.go:211,217` terminate. MinIO downloads are bounded by `MINIO_DOWNLOAD_TIMEOUT` with the cancel released on `Close` (`store_minio.go:72-98`), and the botplatform auth hop is singleflighted, semaphore-capped and pool-tuned (`pkg/botauth/botauth.go:68`, `main.go:191`).

### Recommendations

- [high] Wrap `c.Request.Body` in `http.MaxBytesReader` before `c.MultipartForm()` in both upload handlers — `handler.go:237`, `handler.go:161` — sized `maxFileSize` (and `maxImages × maxImageSize`) plus envelope slack. Turns a disk-exhaustion vector into an early 413 and makes the existing caps actually load-bearing.
- [medium] Add `ginutil.MaxConcurrency(N, onShed)` to the `/api/v1` group in `routes.go:20`, sized from a new `MAX_CONCURRENT_UPLOADS` env var. Sheds with 429 + Retry-After instead of letting temp files and Drive sockets pile up.
- [medium] Build the Drive transport from `http.DefaultTransport.Clone()` (keeping only the `TLSClientConfig` override) and apply `restyutil.WithMaxIdleConns(32)` — `pkg/drive/uploader.go:64-67`. Restores dial/TLS-handshake/idle timeouts and stops per-request handshakes past 2 concurrent transfers.
- [medium] Thread `context.Context` through `driveClient` (`handler.go:40-44`) into `NewRequestWithContext`/`SetContext` at `pkg/drive/uploader.go:159,202,227`, so client disconnects cancel the upstream transfer and the Drive span nests under the server span.
- [medium] Set `IdleTimeout: 60 * time.Second` on the server at `main.go:208`, so idle keep-alives are not held for 15 minutes each.
- [low] Call `mongoutil.WarnMissingIndexes(ctx, s.subscriptions, "roomId_1_u.account_1")` from `NewMongoStore` (`store_mongo.go:117`) to make a missing index loud instead of a silent per-request scan.

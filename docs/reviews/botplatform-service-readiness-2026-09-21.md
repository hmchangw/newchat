**Date:** 2026-09-21

**Overall score:** 2.8 / 5 (baseline 2026-09-01: 2.8, Δ +0.0)  
**Method:** six independent expert reviews (one per dimension) against `CLAUDE.md` and Go-at-scale practice; every finding cites `file:line` on this tree.

## Executive summary

botplatform-service is competently built — clean logging, projected reads, a correct breaker predicate, tested middleware — but it sits on a revocation hole that spans two services. Admin-service's deactivate and password-reset paths delete sessions directly inside their transaction and return only an error, so they never hand any session IDs to the cache-busting helper, while this service authenticates every bot request from that same cache with a 90-minute TTL that slides on load error. A deactivated or password-reset bot therefore keeps authenticating for roughly an hour, and indefinitely while MongoDB is down. Three contract problems follow. Two documented member-management endpoints do not exist at the paths the client API publishes, so an SDK written from the doc gets a 404 on both — flagged in the previous audit and still unfixed. Remote error envelopes are re-emitted without validating the code field, which the error package explicitly warns will panic. And `SESSIONS_MAX_PER_ACCOUNT` and `BCRYPT_COST` are re-declared per service, with two independently-defaulted session caps enforcing limits on one shared collection; `BCRYPT_COST` is dead here but still a hard startup gate. Operationally, downstream-unavailable is misclassified as a 500 rather than a retryable 503 because the transport switch is hand-rolled instead of using the shared helper; `/healthz` pings Mongo with no separate readiness probe, so an outage the session cache is designed to survive instead restarts pods; the request deadline sits below the NATS budgets it wraps, making the documented 15-second room-management timeout unreachable; and the idempotency middleware buffers request bodies before the size cap applies. Coverage is 56.5%: the entire NATS forwarding layer, the first-time-DM flow and the routing store are untested at every tier, and the login handler is a drifted clone of admin-service's that has already lost its timing-attack guard.

## 2. Code quality — score 4

### Evidence

- [medium] Bot-route error logs carry no request ID — `botplatform-service/middleware.go:51` — `requireBot` never calls `errcode.WithLogValues` nor rewrites `c.Request` context, so every `Classify` line from the 5 bot endpoints plus the rate-limit/idempotency middlewares (`middleware.go:70,128,136,151`, `middleware_idempotency.go:55,62,74`) logs `request failed` without `request_id`. `HandleLogin`/`HandleValidate` do it (`handler.go:90,194`), as do sibling services in their auth middleware (`user-service/middleware.go:46`, `media-service/middleware_auth.go:33`, `upload-service/middleware.go:140`). CLAUDE.md §3 requires the ID "in all log lines".
- [medium] Idempotency middleware reads the request body unbounded — `botplatform-service/middleware_idempotency.go:60` — `io.ReadAll(c.Request.Body)` runs *before* the handler, and the only size cap (`http.MaxBytesReader`, `bot_handlers.go:193`) lives downstream in `bindStrict`. No global limit is wired (`main.go:118-127`; `ginutil.TimeoutConfig` only sets a deadline). An authenticated bot can make the process buffer an arbitrary body per request.
- [medium] The 15s room-management budget is unreachable — `botplatform-service/bot_forwarder.go:75` — `forwardRoomMgmt` derives `context.WithTimeout(ctx, 15*time.Second)` and `newNATSDMEnsurer` gets 15s (`main.go:116`), but the parent request context is already capped by `ginutil.TimeoutConfig.RequestTimeout`, `envDefault:"10s"` (`pkg/ginutil/timeoutconfig.go:18`, not overridden in `deploy/docker-compose.yml`). Those calls always die at 10s; the comments at `bot_forwarder.go:55` / `main.go:115` and the TTL sizing rationale at `config.go:54` all assert 15s.
- [low] Idempotency sentinel release uses the (possibly cancelled) request context — `botplatform-service/middleware_idempotency.go:89` — `ctx` is captured at `:51` and reused after `c.Next()`. On a 2xx whose client disconnected, `Del` fails and the key is held for the full TTL, so honest retries get 409 `bot_in_flight` for up to 60s.
- [low] Error text is string-matched and a raw decoder message is returned to the client — `botplatform-service/bot_handlers.go:211` — `strings.Contains(msg, "unknown field")` is exactly the string-comparison CLAUDE.md §3 forbids, and `:212` writes the stdlib decoder's own text onto the wire. A test pins the behaviour (`bot_handlers_test.go:76`), which contains the drift risk; `encoding/json` exposes no typed error here. Also `:219` compares `err != io.EOF` instead of `errors.Is`, and the `*json.SyntaxError` variable at `:206` is misnamed `unknownErr`.
- [low] Bare `err` returns — `botplatform-service/store_mongo.go:99` and `main.go:154` — both return the callee's error unwrapped; CLAUDE.md §3 requires `fmt.Errorf("<what this fn was doing>: %w", err)`.
- [low] Infra failures dressed as `errcode.Internal` instead of a raw wrapped error — `botplatform-service/middleware.go:70` — CLAUDE.md's Tier-1 rule says an infra failure returns `fmt.Errorf(...: %w)` and collapses to `internal` at the boundary. The same service does it the documented way for the identical operation at `handler.go:210` (`fmt.Errorf("find session: %w", err)`). Same pattern at `middleware.go:128,136,151`, `middleware_idempotency.go:55,62,74`, `bot_forwarder.go:84,141`.
- [low] Dependencies poked in after construction rather than injected — `botplatform-service/main.go:106,114,116` — `newHandler` (`handler.go:46`) takes only the store; `subs`, `forwarder` and `dmEnsurer` are assigned as fields, so a wiring omission is a nil-deref at request time instead of a compile/startup error. CLAUDE.md: "Handler structs hold dependencies injected via constructor".
- [nitpick] Log-and-return on the denial path — `botplatform-service/handler.go:180` — `slog.WarnContext` then `errhttp.Write`, which runs `Classify` and logs again (`pkg/errcode/classify.go:40`). CLAUDE.md says never log AND return, but `admin-service/login.go:145` does the same, so this is a repo-wide idiom, not a local slip.
- [nitpick] `accessLogMiddleware` (`botplatform-service/middleware.go:23`) is a copy of `ginutil.AccessLog` (`pkg/ginutil/middleware.go:62`) plus three fields; `subscription_store.go:17` has a `model.model.` typo.

### Recommendations

- [medium] Set `errcode.WithLogValues(ctx, "request_id", c.GetString("request_id"))` and push it onto `c.Request` inside `requireBot` — `middleware.go:51` — one line restores per-log correlation across the whole bot surface, matching `user-service/middleware.go:46`.
- [medium] Wrap the idempotency read in `http.MaxBytesReader(c.Writer, c.Request.Body, botRequestBodyMaxBytes)` — `middleware_idempotency.go:60` — reuses the constant already defined at `bot_handlers.go:190` and closes the unbounded buffer.
- [medium] Reconcile the HTTP request deadline with the room-mgmt budget — either raise `REQUEST_TIMEOUT` above 15s in `deploy/docker-compose.yml` + the prod manifest, or make `forwardRoomMgmt`'s timeout a config field like `f.timeout` — `bot_forwarder.go:75` — today the documented 15s never applies.
- [low] Release the sentinel with `context.WithoutCancel(ctx)` — `middleware_idempotency.go:89` — prevents a disconnected client from locking its own opID for the TTL.
- [low] Wrap the two bare returns (`store_mongo.go:99`, `main.go:154`) and switch `bot_handlers.go:219` to `errors.Is(err, io.EOF)`; return a fixed message at `:212` rather than the decoder's text.
- [low] Move `subs`/`forwarder`/`dmEnsurer` into `newHandler`'s signature — `handler.go:46` — makes incomplete wiring a compile error.
- [nitpick] Factor the three extra fields into `ginutil.AccessLog` (optional attrs) and drop the local copy — `middleware.go:23`.

## 3. Architecture — score 3

### Evidence

- [high] Shared session-store ownership is broken for revocation: admin-service's two transactional revoke paths never bust the L2 cache botplatform-service authenticates from — `admin-service/store_mongo.go:387` (`DeactivateAndRevoke`) and `admin-service/store_mongo.go:355` (`UpdateUserPasswordAndRevoke`) `DeleteMany` on `session.Collection` directly inside the tx and return only `error`, so the handlers (`admin-service/handler.go:483`, `:701`) have no `_id`s to hand `sessioncache.BustMany` — unlike `handler.go:599`/`:620`, which do bust. BP resolves every bot request through that cache (`botplatform-service/store_mongo.go:43`, read at `middleware.go:63`), and `valkeyutil.RefreshAfter` is ¾ TTL (`pkg/valkeyutil/tier.go:38`), so a deactivated or password-reset bot keeps authenticating for ~67.5m at the 90m default (`pkg/sessioncache/ttlconfig.go:14`) — indefinitely while Mongo is down, since `serveHit` slides the TTL on load error (`pkg/valkeyutil/readthrough.go:180`). `session.Store` was explicitly reshaped to return deleted `_id`s for this (`pkg/session/session.go:36-41`); these two paths bypass it.
- [high] Downstream-down is misclassified as an internal fault: `bot_forwarder.go:79` / `:136` and `dm_ensurer.go:58` hand-roll transport classification and match only `DeadlineExceeded`/`nats.ErrTimeout`. With bot-message-handler or bot-room-service not subscribed, `RequestMsgWithContext` returns `nats.ErrNoResponders` (no `UseOldRequestStyle` anywhere in the repo), which falls into the `default` arm → `errcode.Internal` → HTTP 500 logged at error level, instead of the 503 `nats_no_responders` the repo-wide helper `natsutil.RequestFailure` produces (`pkg/natsutil/request_failure.go:47`, used by 8 other services). No test covers it (`bot_forwarder_test.go` only has the timeout case at :92).
- [high] `/healthz` nullifies the degraded-mode design: `routes.go:10` → `handler.go:56` pings Mongo and returns 503. The sibling service sharing `pkg/session` splits this correctly — `admin-service/handler.go:651` `healthz` is unconditional 200, `:657` `readyz` pings. BP has no `/readyz`, so a Mongo outage either restarts pods (liveness) or pulls them from the LB (readiness), which is exactly what the session L2 tier exists to prevent.
- [medium] Middleware ordering defeats the body cap: `middleware_idempotency.go:60` does an unbounded `io.ReadAll(c.Request.Body)` before the handler, so `botRequestBodyMaxBytes`' `http.MaxBytesReader` (`bot_handlers.go:193`) only rejects the request after the full body is already buffered. Authenticated, but rate-limit still allows 600 req/min/caller.
- [medium] Handler dependencies are assigned post-construction, not injected: `newHandler` (`handler.go:46`) takes only store+cfg; `main.go:106`, `:114`, `:116` then set `h.subs`, `h.forwarder`, `h.dmEnsurer` as fields. A `handler` with nil collaborators is constructible, and the nil-deref is a runtime panic in a bot endpoint, not a compile error — contra the CLAUDE.md constructor-DI rule.
- [medium] `cfg.Valkey.Validate()` is never called (`main.go:47-55` validates Pool/Breaker/HTTP only). Empty `VALKEY_ADDRS` in production silently disables rate limiting, idempotency *and* the session cache with a `slog.Warn` (`main.go:95`); three other services (`search-service/main.go:161`, `notification-worker/main.go:89`, `user-presence-service/main.go:77`) call the ready-made `Validate`.
- [medium] Idempotency key diverges from its own design: the spec specifies `bodyHash = sha256(canonicalizeJSON(body))`, "stable across whitespace / key-order" (`docs/superpowers/specs/2026-07-15-bot-messaging-pipeline-design.md:539`); `computeOpID` hashes raw bytes (`middleware_idempotency.go:101`). A retry that re-serializes differently silently misses the sentinel and duplicates the operation.
- [low] `botForwarder.timeout` is honoured only on the msg path; `forwardRoomMgmt` hardcodes `15*time.Second` inline (`bot_forwarder.go:75`), so the struct field lies and room-mgmt timeouts can't be varied in tests.
- [low] Second store interface lives outside `store.go` with no mockgen directive — `subscriptionStore` at `subscription_store.go:28`; `store.go:10` is the only `//go:generate`. Deviates from the per-service layout rule and leaves `FindForBot`/`FindDMForBot` hand-faked.
- [nitpick] `newStoreMongo` builds its own `session.NewMongoStore(db)` (`store_mongo.go:33`) while `main.go:75` builds a second one for `EnsureIndexes`; the session store is constructed, not injected.

### Recommendations

- [high] Make revocation bust the cache structurally: have `DeactivateAndRevoke`/`UpdateUserPasswordAndRevoke` route their deletes through `session.Store` (or return the deleted `_id`s) and call `sessioncache.BustMany` at `admin-service/handler.go:483`/`:701` — otherwise the whole L2 tier is a ~68-minute revocation hole for bots.
- [high] Replace the three hand-rolled transport switches with `natsutil.RequestFailure` — `bot_forwarder.go:79`, `:136`, `dm_ensurer.go:58` — and add an `ErrNoResponders` test case; a down bot-room-service should be a retryable 503, not a 500.
- [high] Split probes: keep `/healthz` unconditional and add `/readyz` doing the Mongo ping, mirroring `admin-service/routes.go`. Cite `handler.go:56`.
- [medium] Wrap the idempotency read in `http.MaxBytesReader` at `middleware_idempotency.go:60` (or hoist one body-cap middleware ahead of the chain) so the declared cap is actually enforced.
- [medium] Pass `subs`, `forwarder` and `dmEnsurer` into `newHandler` (`handler.go:46`) so a mis-wired handler cannot compile, and call `cfg.Valkey.Validate()` in `main.go` behind a non-dev guard.
- [medium] Canonicalize the body before hashing in `computeOpID` (`middleware_idempotency.go:101`), or amend the design doc to state byte-exact retries are required.
- [low] Move `subscriptionStore` into `store.go` with its own mockgen directive, and give `forwardRoomMgmt` a `roomMgmtTimeout` field instead of the literal at `bot_forwarder.go:75`.

## 5. Maintainability — score 3

### Evidence

- [high] `SESSIONS_MAX_PER_ACCOUNT` and `BCRYPT_COST` are re-declared per service with their own `envDefault` — `botplatform-service/config.go:34,37` and `admin-service/config.go:38,44` — violating CLAUDE.md §Configuration ("a knob shared by more than one service is declared once, in the package that owns the thing it configures"). Both services write the *same* shared `sessions` collection (`docs/client-api.md:7367`), so two independently-defaulted FIFO caps can enforce different limits on one collection; `pkg/session` and `pkg/pwhash` are the natural owners.
- [medium] `BCRYPT_COST` is dead in this service, yet it is a hard startup gate — `botplatform-service/main.go:44-46`. The only password call is `pwhash.Verify` (`handler.go:228`), which takes no cost; `pwhash.Hash` is never called here (repo grep: only `admin-service/handler.go:395,686`, `login.go:188`). So `BCRYPT_COST=2` refuses to boot a service the value cannot affect, and `deploy/docker-compose.yml:28` advertises it as meaningful.
- [medium] `DevMode` is dead config — declared `botplatform-service/config.go:57`, wired in `deploy/docker-compose.yml:29`, read nowhere in the tree.
- [medium] `HandleLogin` (`botplatform-service/handler.go:89-175`) is a near line-by-line clone of `admin-service/login.go:58-140`: bind → find user → role gate → `pwhash.Verify` → `IsActive` → `sessiontoken.New/Hash` → build `session.Session` → insert → `DeleteBeyondCap` → cache bust. `rolesToStrings` (`handler.go:232`) duplicates the inline loop at `login.go:107-110`. Worse, `forwardRoomMgmt:75` hardcodes `15*time.Second` while the identical budget is injected for the DM ensurer at `main.go:116` and `config.go:55`'s comment ("exceeds the 15s NATS timeout") documents a literal living in another file.
- [medium] Handler dependencies are poked in after construction — `main.go:105-107,114,116`: `newHandler` takes 2 of 5 deps, and `subs`/`forwarder`/`dmEnsurer` (`handler.go:26-28`) are assigned by field. - [medium] The exact code that most needs a refactor is the code with no test cover: `forwardRoomMgmt`, `createRoom`, `addMembers`, `removeMembers` (`bot_forwarder.go:57,94,98,102`) and all of `dm_ensurer.go:31,35` are **0.0%**, as is every `store_mongo.go` and `subscription_store.go` method (service tree 56.5%). - [low] `pkg/botauth` already owns the bot-credential vocabulary, and this service re-implements it: header names are string literals at `middleware.go:55-56` vs `botauth.HeaderUserID/HeaderAuthToken`; `containsBotRole` (`middleware.go:104-106`) duplicates `botauth.HasRole`; `errBotInvalidToken` (`helper.go:21-22`) reproduces `botauth.errInvalidToken` message-and-reason exactly.
- [low] `run()` is 131 lines (`main.go:34-164`) — config validation, obs, Mongo, Valkey, stores, NATS, Gin, server and shutdown in one body; past the ~80-line threshold and the only function that must change for any new dependency.

## 6. Integration — score 3

### Evidence

- [high] Two documented bot endpoints do not exist — `botplatform-service/routes.go:69,72` — code registers `POST /api/v1/rooms/:roomID/members/add` and `.../members/remove`; `docs/client-api.md:8591-8592,8709-8710` publish `POST` and `DELETE /api/v1/rooms/:roomID/members`. Any SDK written from the doc gets 404 on both. Already flagged in `docs/reviews/botplatform-service-readiness-2026-08-31.md:174` and still unfixed.
- [high] Remote errcode envelope re-emitted without `Code.Valid()` — `botplatform-service/bot_forwarder.go:87,146`, `dm_ensurer.go:66` — `pkg/errcode/parse.go:8-11` states callers re-emitting a parsed envelope MUST check `Code.Valid()` because `New` panics (`pkg/errcode/options.go:11-15`). `Parse` only requires a non-empty `error` field, so a version-skewed/foreign responder replying without `code` panics the Gin handler (recovered to a bare 500). The compliant repo pattern is `ok && ee.Code.Valid()` (`broadcast-worker/parent_fetcher.go:68`) or relaying `e` unchanged (`user-service/roomclient/client.go:50`); `room-service/memberlist_client.go:103-115` documents this exact trap.
- [high] `SESSIONS_MAX_PER_ACCOUNT` re-declared per service — `botplatform-service/config.go:34` and `admin-service/config.go:44` — both drive `DeleteBeyondCap` on the same shared collection (`pkg/session/session.go:19`, `handler.go:152` / `admin-service/login.go:125`). CLAUDE.md §Configuration requires one declaration in the owning package (`pkg/session`) mounted as a named field; the tag-level default cannot stop the two from disagreeing about the FIFO cap on identical rows. Contrast the correctly-mounted `sessioncache.TTLConfig` at `config.go:28`.
- [medium] `BCRYPT_COST` re-declared and unused — `botplatform-service/config.go:37`, validated at `main.go:44-46` but referenced nowhere else; `pwhash.Verify` takes no cost. Duplicates `admin-service/config.go:38` (the only real user, `pwhash.Hash`). Dead knob plus the same one-declaration violation. `DevMode` (`config.go:57`) is likewise never read.
- [medium] `X-Bot-Identity` never carries display-name or app fields — `bot_forwarder.go:114-118,62-66`, `dm_ensurer.go:43` — BP is the sole producer (verified repo-wide), and `session.Session` (`pkg/session/session.go:23-30`) has no `EngName`/`ChineseName`. So `bot-message-handler/handler.go:114,169` resolves `UserDisplayName` to the raw account on every bot message, and `BotOwnerResp.appId/appName` (`bot-room-service/handler.go:282`) are permanently absent. BP already projects `engName`/`chineseName` at login (`store_mongo.go:66-67`) and uses them for `me.name`.
- [medium] §10.2 401 body documented wrongly — `docs/client-api.md:8563` says the 401 "Body carries `{"valid": false, ...}`", but `handler.go:207` writes the errcode envelope (`{"code","reason","error"}`) via `pkg/errcode/errhttp/errhttp.go:15`. `pkg/botauth` only reads the status so it is unaffected, but any other server-to-server consumer is misled.
- [medium] 403 `not_a_bot` is undocumented and the 401 row is wrong — `docs/client-api.md:8638` says a session that "lacks bot role" returns 401 `invalid_token`; `middleware.go:81-84` returns 403 `not_a_bot` (`pkg/errcode/codes_botplatform.go:33`). No §10.4-10.7 table lists that status.
- [medium] Derived view drift — `docs/client-api/request-reply.md:256-260` lists only login + validate; the five bot HTTP endpoints of §10.3-10.7 are missing entirely, which CLAUDE.md forbids.
- [low] Idempotency guarantee overstated — `docs/client-api.md:8595-8600` says the sentinel "rejects duplicates inside its TTL window (30 s / 60 s)". `middleware_idempotency.go:88-94` deletes the key on any non-5xx, so only *in-flight* duplicates are rejected; a sequential retry after a 200 is forwarded and mints a second message (`bot_forwarder.go:111`).
- [low] §10.3 DM routing row names the wrong key — `docs/client-api.md:8589` says the lookup is `(bot, otherAccount)`; `bot_handlers.go:70` and `subscription_store.go:51-55` key on the path's **userID** via `idgen.BuildDMRoomID`.
- [nitpick] `pkg/principal/principal.go:8` documents the endpoint as `POST /v1/auth/validate`; the real path is `/api/v1/auth/validate` (`routes.go:13`, `pkg/botauth/botauth.go:32`).

### Recommendations

- [high] Pick one member-endpoint shape and make code and doc agree — `routes.go:69,72` vs `docs/client-api.md:8591-8592,8709-8710`. The design spec (`docs/superpowers/specs/2026-07-15-bot-messaging-pipeline-design.md:33-34`) matches the code, so amend §10.3/§10.7 to `/members/add` + `/members/remove`.

- [medium] Delete `BcryptCost` and `DevMode` from `botplatform-service/config.go:37,57` and the validation at `main.go:44-46`; if a shared cost knob is wanted later, it belongs in `pkg/pwhash`.
- [medium] Carry `EngName`/`ChineseName` on `session.Session` and populate `model.BotIdentity` at `bot_forwarder.go:114-118,62-66` and `dm_ensurer.go:43`, so bot messages and room-owner blocks stop degrading to the raw account.

## 7. Performance — score 3

### Evidence

- [high] Request body is buffered unbounded before the size cap runs — `botplatform-service/middleware_idempotency.go:60` — `io.ReadAll(c.Request.Body)` with no limit runs in the idempotency middleware, i.e. before the handler. The 96 KiB cap (`bot_handlers.go:190`, `http.MaxBytesReader` at `:193`) is applied to the already-buffered copy restored at `middleware_idempotency.go:66`, so it bounds the decode but not the allocation. `/api/v1/login` and `/api/v1/auth/validate` have no cap at all (`handler.go:93`, `:197` — plain `ShouldBindJSON`).
- [high] Gin's request deadline (10s) sits below the NATS budgets it wraps — `main.go:124` + `pkg/ginutil/timeoutconfig.go:18` (`REQUEST_TIMEOUT` `envDefault:"10s"`, not overridden in `deploy/docker-compose.yml`). `forwardRoomMgmt` derives a 15s child ctx (`bot_forwarder.go:75`) and the DM ensurer another 15s (`main.go:116`); a child cannot outlive its parent, so both are silently clamped and the documented 15s room-mgmt budget is unreachable.
- [high] First-time DM spends two serial budgets inside one 10s request — `bot_handlers.go:73-92` — on a subscription miss it calls `dmEnsurer.Ensure` (15s nominal) then `forwarder.sendDM` (3s, `main.go:114`), 18s of intended budget. Under the 10s cap a slow ensure burns the deadline and the send fails instantly on an expired ctx → 503 after the room was created.
- [medium] No in-flight cap on a CPU-bound login path — `routes.go:12`, `handler.go:120` — bcrypt (`pkg/pwhash/pwhash.go:26`) is tens of ms of non-preemptible CPU per attempt, a ctx deadline cannot cancel it, and `/api/v1/login` is not rate limited (rate limiting exists only on bot routes, `routes.go:29`). The repo's shed primitive `ginutil.MaxConcurrency` (`pkg/ginutil/limit.go:20`, used at `user-service/routes.go:25`) is not wired here, so a login burst queues work that runs even after clients give up.
- [medium] `BCRYPT_COST` is inert — `config.go:37`, validated at `main.go:44` — nothing calls `pwhash.Hash`; verify cost comes from the stored hash. The one lever that looks like it trades login CPU does nothing.
- [medium] Auth precedes rate limiting, so invalid-token floods are never shed — `routes.go:24-31` (`auth` first, `rateLimit` second). `sessioncache` is positive-only (`pkg/valkeyutil/readthrough.go:151`, `pkg/sessioncache/sessioncache.go:91`), so every bad token costs a Valkey GET miss plus a Mongo `_id` FindOne, and the breaker deliberately exempts `session.ErrNotFound` (`store_mongo.go:56`) so nothing fences it.
- [low] Per bot message: 5 serial Valkey round trips (session GET; caller INCR `middleware.go:134`; global INCR `:149`; SETNX `middleware_idempotency.go:72`; DEL `:89`) plus an uncached Mongo subscription read (`bot_handlers.go:41`, `:155`) plus the NATS RPC. The room→siteID routing decision is re-read from Mongo per message though the repo has L2 precedent for exactly this read class (`pkg/subauthcache`, `pkg/roomsubcache`).
- [low] The fixed-window limiter permits ~2x burst across a boundary and pins all global traffic to one cluster slot — `middleware.go:149` (single key `"botrl:global"`).
- [nitpick] Every login pays an extra Mongo Find with a blocking sort — `handler.go:152` → `pkg/session/session.go:106-112`: the sort `{issuedAt:-1,_id:-1}` is not fully served by the `{account:1,issuedAt:1}` index (`pkg/session/session.go:218`). Bounded by the 100-session cap, so cheap, but it is a round trip on every login even when under cap.

### Recommendations

- [high] Move the cap ahead of the buffering: wrap `c.Request.Body` in `http.MaxBytesReader(..., botRequestBodyMaxBytes)` inside `middleware_idempotency.go:60`, or add an engine-level body limit in `main.go` covering login/validate. Bounds worst-case memory to `concurrency × 96 KiB`.
- [high] Reconcile the timeout budgets: set `REQUEST_TIMEOUT` above the longest downstream budget (e.g. 20s) in the deployment, or derive child timeouts from the parent's remaining budget rather than hardcoding 15s (`bot_forwarder.go:75`, `main.go:116`). Add a test asserting `REQUEST_TIMEOUT > roomMgmt` so the invariant cannot silently invert again.
- [high] Bound the first-DM path explicitly — `bot_handlers.go:78` — give `Ensure` a fraction of the remaining deadline and reserve the send's 3s, so a slow ensure returns a useful error instead of consuming the send's budget.
- [medium] Wire `ginutil.MaxConcurrency` (with a `MAX_CONCURRENCY` knob) on the engine at `main.go:126`, sized near `GOMAXPROCS` for the bcrypt path, plus a per-account/IP limiter on `/api/v1/login`. Turns a login burst into fast 429s instead of a CPU queue.
- [medium] Either use `cfg.BcryptCost` (rehash-on-verify when the stored cost differs) or delete it and its validation (`config.go:37`, `main.go:44`).
- [medium] Put the rate limiter before `requireBot` keyed on `x-user-id`/client IP (`routes.go:24`), so token-spray traffic is shed before it reaches Valkey and Mongo.
- [low] Cache the bot's room→siteID routing decision behind a short-TTL L2 (pattern: `pkg/subauthcache`), removing one Mongo round trip from every bot message.

# bot-message-handler — production readiness review

**Date:** 2026-09-21  
**Branch:** `claude/production-readiness-report-2026-09-21` @ `6c855de` (base `main`)  
**Overall score:** 2.8 / 5 (baseline 2026-09-01: 3.2, Δ -0.4)  
**Method:** six independent expert reviews (one per dimension) against `CLAUDE.md` and Go-at-scale practice; every finding cites `file:line` on this tree.

## Executive summary

bot-message-handler is small and idiomatic — error tiering is clean, subjects come only from the builder package, the stream bootstrap is correct, and no file or function exceeds the size thresholds — but its two send handlers are near-clones and only one of them is tested at all. `handleSendDM` is at zero percent coverage: the DM room-ID derivation, the empty-parameter rejection and the non-member Forbidden are unverified, and that is the branch most likely to drift from its twin. Four reviewers converged on the same stream-contract break: this service publishes a `MessageEvent` envelope onto BOT-MESSAGES-CANONICAL while bot-room-service publishes a bare `model.Message` on the identical subject, so the worker decoding both shapes silently writes empty rows for one of them. Three more contract defects sit alongside: the event `Timestamp` is taken from a client-supplied header rather than publish time as the rulebook requires, with no sanity bound on the value; the rooms projection reads a legacy `t` key that only bot-room-service writes, so room type comes back empty for any room the user-facing path created; and the guard knobs `MAX_CONCURRENCY` and `REQUEST_TIMEOUT` are re-declared locally at different defaults instead of mounting the owning package's config. On the hot path the mention flow fetches every subscriber ID in the room to test membership of a handful of mentions, then issues one user lookup per mention, with no cap on mention count anywhere — two bounded queries would replace work proportional to room size. None of the caching tiers the equivalent human path uses are wired, so every bot send pays at least two Mongo round trips against the primary. There is no integration test, no mockgen mocks and no CI pipeline definition — gaps shared by all three bot services.

## 3. Architecture — score 3

### Evidence

- [high] Shared guard knobs re-declared locally instead of mounting `natsrouter.GuardConfig` — `bot-message-handler/main.go:37-38`, `:61` — CLAUDE.md §6 Configuration: a knob owned by another package is mounted as a named field, "never re-declare the env tag and `envDefault` in a service". `MAX_CONCURRENCY`/`REQUEST_TIMEOUT` are already declared on `pkg/natsrouter/guard.go:21,24` (256/10s); this service redeclares them at 200/10s and hand-builds the struct. room-service (`main.go:61`), room-worker (`main.go:54`), media-service, search-service and history-service all mount `Guard natsrouter.GuardConfig`. Only bot-room-service (`main.go:57`) shares this deviation, so operators reading `MAX_CONCURRENCY` get two different defaults across the fleet.
- [medium] The "room lives at this site" defence does not check the site — `bot-message-handler/handler.go:58-68`, `store.go:15-16`, `store_mongo.go:57-59` — `FindRoom` queries `{_id: roomID}` with no `siteId` predicate, and the handler discards the returned `Room` (its `SiteID`, `Type`, `Name` are never read; `Subscription.SiteID` likewise, `handler.go:143`). Remote rooms and remote subscriptions ARE mirrored into the local `rooms`/`subscriptions` collections by inbox-worker (`inbox-worker/handler.go:442` → `main.go:144`, and the federated sub at `handler.go:317` carries the origin `SiteID`), so both guards pass for a room hosted elsewhere. BP routes on `sub.siteId` (`docs/client-api.md:8611`); a routing bug therefore publishes the message onto the wrong site's BOT-MESSAGES-CANONICAL rather than being rejected — exactly what the defence-in-depth exists to catch.
- [medium] No `//go:generate mockgen` directive and no `mock_store_test.go` — `bot-message-handler/store.go:11-23`, `handler_test.go:26-47` — CLAUDE.md's per-service layout and §4 require mockgen-generated mocks in `mock_store_test.go`; 25 of 28 services with a `store.go` carry the directive (e.g. `message-gatekeeper/store.go:12`). The hand-rolled `fakeStore` has no call/argument assertions and silently returns `nil, nil` when `ListMemberIDsFn` is unset (`handler_test.go:39-44`), so a regression that stops gating mentions would still pass.
- [medium] `deploy/` has no `azure-pipelines.yml` — `bot-message-handler/deploy/` (only `Dockerfile`, `docker-compose.yml`) — CLAUDE.md §1/§5 require all three per service; 29 services have one. There is no CI/CD definition to build or ship this service's image.
- [medium] `Register` and the whole DM route are untested — `bot-message-handler/handler.go:71-76`, `:79-125`; `handler_test.go` has ten tests, all `TestHandleSendRoom_*`. Nothing exercises `handleSendDM`, the `{userID}` param, `idgen.BuildDMRoomID`, or the pattern→handler binding, so a swapped `ServerBotDMSendPattern`/`ServerBotMsgRoomSendPattern` pairing or a `c.Params.Get` key typo compiles and ships. This is the bulk of the 40.9% statement coverage.
- [low] `handleSendDM` and `handleSendRoom` duplicate ~40 lines of identical `model.Message` assembly and publish flow — `handler.go:111-124` vs `handler.go:164-183` — with no shared `buildMessage` helper, and only one of the two twins is tested (previous finding), so they can drift silently.
- [low] Store interface offers no batched user lookup, forcing an N+1 — `handler.go:285` inside the `range requested` loop at `:275` — one `FindUser` round-trip per mention under the request deadline. A `FindUsers(ctx, ids)` on the consumer-defined interface would be one query. (Cross-ref: performance dimension.)
- [nitpick] `bootstrapStreams` does more than no-op when disabled — `bootstrap.go:35-37` — CLAUDE.md says the helper "no-ops when `Enabled=false`"; here it performs a read-only `js.Stream` existence check. The deviation is benign, read-only, fails fast, and matches `bot-message-worker/bootstrap.go:35`; worth codifying in CLAUDE.md rather than changing.

### Recommendations

- [high] Replace `MaxConcurrency`/`RequestTimeout` with `Guard natsrouter.GuardConfig` and call `cfg.Guard.Validate()` — `main.go:36-38`, `:61-64` — restores the single fleet-wide default; if 200 is deliberate, set it in `deploy/docker-compose.yml`, not in a tag.
- [medium] Assert site locality with data already fetched: compare the returned `Subscription.SiteID`/`Room.SiteID` against `h.siteID` and reject with `errcode.NotFound(..., BotRoomNotFound)` — `handler.go:143-153` — makes the documented contract in `store.go:15-16` true and stops a misrouted send landing on the wrong site's canonical stream.
- [medium] Add `//go:generate mockgen -destination=mock_store_test.go -package=main . Store,Publisher` to `store.go` and regenerate, replacing `fakeStore` — `store.go:11`, `handler_test.go:26` — brings the service onto the repo-standard double with `EXPECT()` arity/argument assertions.
- [medium] Add `deploy/azure-pipelines.yml` modelled on `message-gatekeeper/deploy/azure-pipelines.yml` — `bot-message-handler/deploy/`.
- [medium] Add DM-path tests mirroring the room tests plus one `Register` test asserting both patterns resolve to the right handler — `handler.go:71-76`, `:79-125`.
- [low] Extract the shared `model.Message` assembly + `publishCanonical` tail into one helper used by both handlers — `handler.go:111-124`, `:164-183`.

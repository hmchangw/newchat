## Executive summary

`tcard-service` is a small, clean, read-mostly HTTP service: it loads AdaptiveCard templates from a MongoDB `cards` collection into an in-process snapshot and serves them by `{path}@{version}`. Code quality and maintainability are the best of any service audited in this cycle (4 and 4) — tight files, honest WHY-comments, shared knobs mounted as named `mongoutil`/`ginutil` fields with nothing re-declared, and a semver gate with real tests. What holds it at 3.2 is that everything around the edges of that core is unfinished.

The sharpest problem is the trust boundary. `POST /api/v1/cards/validate` and `POST /api/v1/cards/refresh` carry no authentication (`routes.go:8-9`), while `docs/client-api.md:8827` documents `/validate` as "Admin only … Not for end-user browsers" and the accepted design defers enforcement to a network policy that does not exist in this repo. `ginutil.CORS()` sets `Access-Control-Allow-Origin: *` and allows `POST` preflight, so `/refresh` — an unbounded full-collection `Find(ctx, bson.D{})` — is a cross-origin scan amplifier reachable from any browser that can reach the read route. The repo already has the pattern to fix it (`client-update-service/routes.go:16` gates its privileged route with `requireServiceAccount`).

Second, the cache has no multi-replica story. Each pod holds a private snapshot refreshed at startup, once daily, or by a POST a load balancer delivers to exactly one replica — so a newly published card is servable on one pod and `404`s on the others for up to 24 hours, and `/validate`'s `409` ordering verdict depends on which pod answers. Compounding this, nothing in the repo writes `cards`: the publisher is out-of-repo, yet the service runs `EnsureIndexWithRepair`, which will silently drop and recreate the external owner's index if its options differ, and then warns-and-continues when the ensure fails — the exact silent behaviour the accepted design's Decision 11 rejected.

Third, two contract gaps that only show up in production. The read path emits relaxed extended JSON (`store_mongo.go:92`), so any BSON date/ObjectID/Decimal128 inside a card reaches the client as `{"$date":…}`, which no AdaptiveCard renderer accepts — while the docs promise the document verbatim. And immutable, content-addressed templates are served with no `ETag`, `Cache-Control` or `If-None-Match` handling (`handler.go:100`), so every client launch re-downloads every card in full; `media-service/handler.go:42-76` already implements exactly the pattern that would remove essentially all steady-state traffic. Twelve client-facing 400/409 cases also carry no machine-readable `reason` — there is no `codes_tcard.go` — so card authors must branch on prose.

Coverage is 69.3%, and the deficit is almost entirely one monolithic `run()` (68 statements, 0%) plus the Mongo layer; the tested logic sits at 96%+. Extracting `buildRouter`/`validateConfig` the way `admin-service` does would close most of it.

## 2. Code quality — score 4

### Evidence

- [medium] Bare `err` returned from a store method — `tcard-service/store_mongo.go:58` — `ListCards` returns `docToCard`'s error unwrapped (`return nil, err`), while every sibling path in the same function wraps (`find cards`, `decode card document`, `iterate cards`). CLAUDE.md §3 "Never return bare `err`"; the resulting chain loses the "was listing cards" frame.
- [medium] Request-scoped logs bypass the context-aware slog handler — `tcard-service/cache.go:105`, `cache.go:116`, `tcard-service/store_mongo.go:60` — `pkg/obs` installs the o11y SDK handler as the slog default specifically so contextual calls gain trace correlation (`pkg/obs/obs.go:175-176`), and `cache.Load` already receives the request-id-bearing ctx from `handler.go:56-58`. Using plain `slog.Info/Warn` drops `request_id`/`trace_id` from exactly the lines an operator needs after a failed `POST /api/v1/cards/refresh`; peer Gin services use `slog.InfoContext` (e.g. `botplatform-service/handler.go:159`).
- [medium] Load timeout is started before the write lock, contradicting its own contract — `tcard-service/cache.go:96-99` — `context.WithTimeout` is applied, then `writeMu.Lock()` blocks. The comment at `cache.go:15-16` claims `cacheLoadTimeout` "bounds a single full scan", but a second concurrent `Load` (the refresh endpoint is a plain unauthenticated POST, `routes.go:9`) spends its 60s budget queued behind the first and can enter `store.ListCards` with an already-expired ctx, turning a slow refresh into a cascade of `context deadline exceeded` 500s. Swap the two lines so the timeout starts after the lock is held.
- [low] Sentinel error compared with `!=` instead of `errors.Is` — `tcard-service/main.go:154` — `err != http.ErrServerClosed`. It happens to work because `ListenAndServe` returns the sentinel unwrapped, but §3 mandates `errors.Is`/`errors.As` for error identity, and it breaks silently if the server is ever wrapped in middleware that decorates the return.
- [low] Unactionable skip warning — `tcard-service/store_mongo.go:60` — `slog.Warn("card document missing a string path or _tcardVersion, skipping")` carries zero structured fields, so a silently dropped card cannot be located in Mongo. The doc is already decoded into `bson.D`; logging the `_id` (or whichever of `path`/`_tcardVersion` did parse) costs nothing and is what §3 "structured fields as key-value pairs" is for.
- [low] No domain `reason` codes despite a branch-heavy validation API — `tcard-service/handler.go:174-215` — `validateCard` returns eleven distinct `errcode.BadRequest`s that a client can only tell apart by prose message, plus the `409` at `handler.go:166`. There is no `pkg/errcode/codes_tcard.go`; the convention exists elsewhere (`codes_auth.go`, used at `auth-service/handler.go:141`). Any UI that must highlight the offending field is forced into string matching.
- [nitpick] Loop variable shadows a package type — `tcard-service/cache.go:113` — `for _, card := range cards` hides the `card` struct type declared in `store.go:12` for the body of `replace`.
- [nitpick] Pre-generics sorting on a Go 1.25 module — `tcard-service/cache.go:197`, `cache.go:218` — `sort.Slice`/`sort.Strings` where `slices.SortFunc`/`slices.Sort` are the current idiom (and `slices.SortFunc` is type-safe and faster here).
- [nitpick] Wrap text names the callee, not the caller — `tcard-service/cache.go:102` (`"list cards: %w"` around `store.ListCards`) and `store_mongo.go:45` (`"find cards: %w"` around `Find`) — §3 asks the frame to describe what the current function was doing; the chain reads "list cards: find cards: …".

### Recommendations

- [medium] Wrap the `docToCard` error — `tcard-service/store_mongo.go:58` → `fmt.Errorf("convert card document: %w", err)` — removes the only bare-`err` return in the service and restores the frame §3 requires.
- [medium] Convert the three request-reachable log sites to the `*Context` variants — `tcard-service/cache.go:105`, `cache.go:116`, `store_mongo.go:60` — `Load`/`replace`/`ListCards` all have a ctx in scope (thread ctx into `replace`), which restores trace and `request_id` correlation on the refresh path for free.
- [medium] Move `context.WithTimeout` below `writeMu.Lock()` — `tcard-service/cache.go:96-99` — makes the 60s budget bound the scan as documented, so queued refreshes each get a full budget instead of failing on arrival.
- [low] Use `errors.Is(err, http.ErrServerClosed)` — `tcard-service/main.go:154` — §3 compliance and robustness against future wrapping of the listener error.
- [low] Add `_id` (and the field that did parse) as structured fields to the skip warning — `tcard-service/store_mongo.go:60` — makes a dropped card findable in Mongo without a full re-scan.
- [low] Introduce `pkg/errcode/codes_tcard.go` with reasons for the validate failures and attach them via `errcode.WithReason` — `tcard-service/handler.go:174-215`, `handler.go:166` — lets the card-authoring UI branch on a stable code rather than on error prose.
- [nitpick] Rename the shadowing loop variable and switch to `slices.SortFunc`/`slices.Sort` — `tcard-service/cache.go:113`, `cache.go:197`, `cache.go:218` — small readability/idiom cleanups on an otherwise well-written file.

## 3. Architecture — score 3

### Evidence

- [high] No authentication on either state-mutating route, and wildcard CORS makes them browser-reachable from any origin — `tcard-service/routes.go:8-9`, `main.go:114` — `registerRoutes` attaches no guard and `main.go:111-121` installs no auth middleware. The ACCEPTED spec justifies this as "internal-only (network policy, no app-level auth)" (`docs/superpowers/specs/2026-07-14-tcard-service-design.md:91`), but `ginutil.CORS()` sets `Access-Control-Allow-Origin: *` and allows `POST` preflight (`pkg/ginutil/middleware.go:39-40`), and `obs.PublicIngressPropagator()` (`main.go:116`) is the public-ingress propagator. `POST /api/v1/cards/refresh` is therefore an unauthenticated, cross-origin trigger for an unbounded full-collection `Find(ctx, bson.D{})` (`store_mongo.go:43`). The repo already has the pattern: `client-update-service/routes.go:16` gates its privileged route with `requireServiceAccount`.
- [high] The cache has no cross-replica invalidation model — `tcard-service/cache.go:128-148`, `handler.go:55-65` — each pod holds a private `atomic.Pointer` snapshot refreshed at startup, once daily at `TCARD_CACHE_REFRESH_AT`, or by a POST that a load balancer delivers to exactly one replica. With >1 replica, a newly published card is servable on the pod that received the POST and `404`s on every other pod for up to 24h, and `/validate`'s `409` ordering verdict (`handler.go:165`) depends on which pod answers. Nothing in this repo writes `cards`, so there is no owner-of-record to publish an invalidation either; the service is authoritative for reads over a collection with no writer inside the system boundary.
- [medium] Shutdown order cancels the background refresher after `srv.Shutdown`, so a mid-scan reload can burn the whole 25s budget — `main.go:140-151` — `srv.Shutdown(ctx)` blocks on in-flight requests; a `HandleRefresh` queued on the non-context-aware `writeMu` (`cache.go:98`) cannot drain until `RefreshLoop`'s `Load` finishes, and that `Load` runs on `refreshCtx` (from `context.Background()`, `main.go:70,100`) with a 60s budget (`cache.go:16`) — longer than the 25s shutdown. `refreshCancel()` only runs at `main.go:144`, after `Shutdown` returns. `shutdown.Wait` then force-returns at 25s (`pkg/shutdown/shutdown.go:51-54`), skipping `obsShutdown` and losing the trace/metric flush.
- [medium] Two disagreeing request budgets, one of which is unreachable — `cache.go:16` vs `main.go:120,124-129` — `cacheLoadTimeout = time.Minute` is derived from `reqCtx(c)` on the HTTP path, which already carries `REQUEST_TIMEOUT` (default `10s`, `pkg/ginutil/timeoutconfig.go:16`), so the 60s scan budget never applies to `POST /refresh`. Raising `REQUEST_TIMEOUT` past 10s also does nothing, because `srv.WriteTimeout` is hardcoded at `10 * time.Second`. A catalog that grows past a 10s scan makes `/refresh` permanently 500 while the daily loop still succeeds.
- [medium] The uniqueness constraint the published contract leans on is best-effort, contradicting the ACCEPTED spec — `main.go:92-95` vs `docs/superpowers/specs/2026-07-14-tcard-service-design.md:95` — decision 11 says `EnsureIndexes` failure must exit non-zero; the code logs `slog.Warn` and serves on. `docs/client-api.md:8882` calls this index "the collection's only hard constraint" on publishing. Warn-and-continue is now the repo norm (17 of 18 `main.go` `EnsureIndexes` call sites), so the fix is likely the spec, not the code — but one of the two must move.
- [low] `isHighest` silently ignores non-semver cached versions — `semver.go:59-63` vs `docs/client-api.md:8834` — the doc says `_tcardVersion` "must be strictly greater than every cached `_tcardVersion` for this path"; the implementation skips any cached value that fails `parseSemver`, so `1.0.0` validates `200` against an existing `v2`. Undocumented contract carve-out.
- [low] The ACCEPTED design spec is stale enough to mislead — `docs/superpowers/specs/2026-07-14-tcard-service-design.md:40,52,91` still describes `POST /api/v1/cards/register` as the write path and flat single-segment paths. `register` no longer exists (replaced by the write-free `/validate`), and §2 of the 2026-07-24 spec superseded the routing. No spec records why the write path was removed.

### Recommendations

- [high] Gate `POST /refresh` and `POST /validate` behind a service-account/admin guard modelled on `client-update-service/middleware.go:52`, and scope `ginutil.CORS()` off those two routes — `routes.go:8-9` — removes the unauthenticated cross-origin scan amplifier.
- [high] Decide and document the multi-replica story — `cache.go:128-148` — either fan `/refresh` out (a NATS subject via `pkg/subject`, the repo's existing mechanism) or bound staleness with a short TTL reload instead of a 24h slot. Today two pods can disagree for a day.
- [medium] Cancel `refreshCancel()`/`refreshWG.Wait()` *before* `srv.Shutdown(ctx)`, and derive `RefreshLoop`'s load budget so it cannot exceed the 25s shutdown window — `main.go:140-148` — lets `obsShutdown` actually run.
- [medium] Reconcile the budgets: drop `cacheLoadTimeout` on the HTTP path (or make it a `min()` of the request deadline) and derive `srv.ReadTimeout`/`WriteTimeout` from `cfg.HTTP.RequestTimeout` — `cache.go:96`, `main.go:124-129`.
- [medium] Make `HandleRefresh` non-blocking under contention (`writeMu.TryLock` → `errcode.TooManyRequests`) so queued refreshes cannot serialize into N sequential full scans — `cache.go:98`, `handler.go:58`.
- [low] Update `docs/superpowers/specs/2026-07-14-tcard-service-design.md` decisions 9 and 11 to match shipped behaviour (no write path, best-effort index, CORS-exposed routes), and note the non-semver carve-out in `docs/client-api.md` §11.2.

## 5. Maintainability — score 4

### Evidence

- [medium] Two composed timeouts silently override the cache's documented scan budget — `tcard-service/cache.go:96` — `cacheLoadTimeout = time.Minute` (`cache.go:16`) is applied with `context.WithTimeout(ctx, ...)` on top of the caller's ctx, so it is the *min* that wins. `HandleRefresh` passes the Gin request ctx (`handler.go:58` → `reqCtx` → `c.Request.Context()`), which `cfg.HTTP.Middleware()` (`main.go:120`, `ginutil.TimeoutConfig` default `REQUEST_TIMEOUT=10s`) has already bounded — so the full-collection scan gets 10s via HTTP but the advertised 60s via `RefreshLoop` (`main.go:104`, ctx rooted at `context.Background`). The const means two different things depending on the caller, and neither file says so.
- [medium] Env-tunable handler timeout is paired with a hardcoded socket timeout, unvalidated — `tcard-service/main.go:128` — `WriteTimeout: 10 * time.Second` is a literal while `REQUEST_TIMEOUT` is operator-settable at the same 10s default. Raise `REQUEST_TIMEOUT` and the connection is dropped before the handler's own deadline fires, so the timeout response never reaches the client. `user-service/config/config.go:243` validates exactly this ordering (`WRITE_TIMEOUT` must exceed `HTTP_HANDLER_TIMEOUT`); tcard-service has no equivalent check.
- [medium] The store returns the HTTP response bytes — leaky abstraction across the store/handler boundary — `tcard-service/store_mongo.go:92` — `docToCard` calls `bson.MarshalExtJSON` and the result is written verbatim as the response body (`handler.go:100`, `c.Data(..., tmpl)`). The wire format of `GET /api/v1/cards/*file` is therefore decided inside the Mongo layer; changing it means editing `store_mongo.go`, and any second consumer of `CardStore` inherits the presentation choice.
- [low] The "storage-only keys" list is spelled twice in one file and can drift — `tcard-service/store_mongo.go:41` and `store_mongo.go:83` — `_id` / `migratedAt` appear once in the `Find` projection and once in the `docToCard` switch. The comment at `:38` names `docToCard` as the correctness guarantee, so a future internal key added to only one of the two either wastes bandwidth or — if added to neither — ships into served templates. One shared `var storageOnlyKeys` removes the double edit.
- [low] The request-ID read-back helper is copy-pasted across nine services — `tcard-service/handler.go:49` — `errcode.WithLogValues(c.Request.Context(), "request_id", c.GetString("request_id"))` appears verbatim in `upload-service/handler.go:92`, `portal-service/handler.go:157`, `admin-service/login.go:59`, `auth-service/handler.go:136`, `botplatform-service/handler.go:90`, `user-service/middleware.go:46` and others. `pkg/ginutil/middleware.go:24` is the sole writer of that magic key, so the reader belongs next to it (`ginutil.LogCtx(c)`); today the string is an unowned cross-service contract.
- [nitpick] Config lives in `main.go` but is tested from a `config_test.go` with no matching source file, and the cache's two tuning constants are split across files — `tcard-service/main.go:25` vs `tcard-service/cache.go:16` — `cacheRetryInterval` sits in `main.go` while `cacheLoadTimeout` sits in `cache.go`, so a reader tuning refresh behaviour has to find both. Peer service `client-update-service/config.go` keeps the config struct in its own file.
- [nitpick] `run()` is 107 lines — `tcard-service/main.go:53-160` — above the ~80-line guideline, though squarely in band for this repo (auth 100, media 112, portal 117, botplatform 131), so this is consistency-with-peers, not an outlier.

### Recommendations

- [medium] Make the refresh scan budget explicit and caller-independent — `handler.go:58` — derive the Load ctx from a non-request root (or document that the HTTP path is bounded by `REQUEST_TIMEOUT` and delete the misleading 60s const), so the endpoint cannot fail at 10s on a large collection while claiming a one-minute budget.
- [medium] Validate `REQUEST_TIMEOUT` against the server write timeout in `run()` — `main.go:61-63` — promote `WriteTimeout` to config or reject `REQUEST_TIMEOUT >= 10s`, mirroring `user-service/config/config.go:243`.
- [medium] Move ext-JSON rendering out of the store — `store_mongo.go:92` — have `ListCards` return the `bson.D` payload and let the handler (or a small `render.go`) serialize, so the response format is owned by the presentation layer.
- [low] Hoist `_id`/`migratedAt` into one package-level slice used by both the projection and the switch — `store_mongo.go:41,83` — removes the service's only double-edit site.
- [low] Promote `reqCtx` into `pkg/ginutil` as `LogCtx(c) context.Context` and switch the nine call sites — `handler.go:49` — puts the `"request_id"` key's writer and reader in the same file and lets the key become unexported-by-convention.
- [nitpick] Split the `config` struct and `parseRefreshAt` wiring into `config.go` beside the existing `config_test.go`, and co-locate `cacheRetryInterval` with `cacheLoadTimeout` in `cache.go` — `main.go:25,27-44`.

## 6. Integration — score 3

### Evidence

- [high] `POST /api/v1/cards/validate` is documented "**Admin only** … Not for end-user browsers" but has no auth — `tcard-service/routes.go:8-9` vs `docs/client-api.md:8827`. `registerRoutes` attaches no guard and `main.go:111-121` installs only CORS/o11y/RequestID/AccessLog/Timeout. The same Gin engine serves the browser-facing GET (`routes.go:10`), so anything that can reach the read route can also call `/validate` and the unauthenticated full-collection-scan `/refresh` (`routes.go:9`). The 2026-07-14 design defers to "network policy", but no ingress/NetworkPolicy exists in this repo to verify.
- [medium] The on-demand refresh budget is silently 10s, not the intended 60s — `tcard-service/cache.go:96` vs `handler.go:50,58`. `reqCtx` derives from `c.Request.Context()`, already bounded by `cfg.HTTP.Middleware()` (`main.go:120`, `pkg/ginutil/timeout.go:20`, default `REQUEST_TIMEOUT=10s`); a longer child timeout cannot extend a parent, and `WriteTimeout` is hardcoded 10s (`main.go:128`). The background `RefreshLoop` (`main.go:100-105`) gets the full minute. A collection taking >10s to scan can therefore never be refreshed on demand, only daily.
- [medium] A read-only consumer owns — and destructively repairs — the index of a collection it never writes — `tcard-service/store_mongo.go:26`. Nothing in this repo writes `cards`, so the publisher is out-of-repo, yet `EnsureIndexWithRepair` will **drop and recreate** a same-keys `(path,_tcardVersion)` index whose options differ (`pkg/mongoutil/indexes.go:157-160`). If the external publisher created that index, tcard-service silently rewrites its spec.
- [medium] Index-ensure failure is Warn-and-continue, contradicting the accepted design — `tcard-service/main.go:92-94` vs `docs/superpowers/specs/2026-07-14-tcard-service-design.md` Decision 11 ("`EnsureIndexes` fails and the service exits non-zero"). With the index absent, duplicate `(path,_tcardVersion)` rows become a first-wins warning (`cache.go:115-119`) — the silent behaviour Decision 11 rejected.
- [medium] Semver-gate contract drifts from the doc — `tcard-service/semver.go:59-63` vs `docs/client-api.md:8834`. The doc says `_tcardVersion` "must be **strictly greater** than every cached `_tcardVersion` for this path"; `isHighest` silently **ignores** existing versions that don't parse as `a.b.c`. Non-semver versions are real here (`integration_test.go:31,37` use `"v1"`/`"v2"`), so a path holding only `v1` accepts any semver — unpredictable from the doc.
- [medium] The read path serves **relaxed extended JSON**, not plain JSON — `tcard-service/store_mongo.go:92` (`bson.MarshalExtJSON(payload, false, false)`), while `docs/client-api.md:8750,8765` promises "the stored document verbatim" with `body` as an AdaptiveCard array. Any BSON date, ObjectID, binary or Decimal128 inside a card is emitted as `{"$date":…}`/`{"$oid":…}`, which no AdaptiveCard renderer accepts. Nothing validates the stored shape; the out-of-repo publisher is the only guard, and `migratedAt` shows legacy-migrated docs exist.
- [medium] Twelve distinct client-facing 400/409 cases carry no machine-readable `reason` — `tcard-service/handler.go:79-97,144-169,174-215`; there is no `pkg/errcode/codes_tcard.go`. `docs/client-api.md:8874-8878` honestly shows `reason` = "—" for every row, so a card-authoring client must branch on prose strings ("path must have exactly 3 segments" vs `version must be "1.5"`). CLAUDE.md §3 reserves `WithReason` for exactly this.
- [low] Two accepted design specs still describe a write path this service no longer has: `POST /api/v1/cards/register` (`docs/superpowers/specs/2026-07-14-tcard-service-design.md` API-contract table and Decision 13; `2026-07-24-tcard-path-versioning-design.md` §5). The shipped surface is `validate` (stores nothing). `docs/client-api.md` §11 is the only accurate description.
- [low] Write and read contracts disagree on shape: `validateCard` demands exactly 3 non-empty path segments and strict semver (`handler.go:190-201`), while the GET/list path is explicitly generic over depth (`cache.go:151-157,184-192`) and does no version parsing at all (`handler.go:89-99`) — a malformed version is a 404, not a 400. `/validate` being advisory, nothing enforces the write contract.

### Recommendations

- [high] Split the trust boundary: put `/validate` and `/refresh` behind auth (or a second listener/port), or state the enforced boundary in `docs/client-api.md:8827` instead of an unenforced "Admin only" — `tcard-service/routes.go:8-9`.
- [medium] Make `HandleRefresh` use a background-derived context with its own budget (`context.WithoutCancel(c.Request.Context())` + `cacheLoadTimeout`), so on-demand and daily refresh share one documented budget — `tcard-service/handler.go:58`, `cache.go:96`.
- [medium] Decide `cards` ownership explicitly. If the publisher is external, drop to `EnsureIndex` without repair (or probe-and-warn only) and restore fail-fast on a duplicate-key ensure failure per Decision 11 — `store_mongo.go:26`, `main.go:92-94`.
- [medium] Marshal the template with `bson.MarshalExtJSON(payload, false, false)` replaced by a canonical-JSON conversion, or reject/log non-JSON-representable BSON types at load time so a bad card fails in the log rather than in the renderer — `store_mongo.go:92`.
- [medium] Add `pkg/errcode/codes_tcard.go` (`CardPathShape`, `CardVersionNotSemver`, `CardSchemaPinned`, `CardVersionNotHighest`) and attach via `WithReason`; update the `reason` column of `docs/client-api.md:8874-8878` in the same PR — `handler.go:174-215`.
- [low] Document the non-semver carve-out at `docs/client-api.md:8834` ("existing `_tcardVersion` values that aren't `a.b.c` are ignored when computing the highest"), and mark the two superseded specs as superseded by §11.

## 7. Performance — score 3

### Evidence

- [high] Immutable versioned templates are served with no HTTP caching headers — `tcard-service/handler.go:100` — `c.Data(http.StatusOK, "application/json; charset=utf-8", tmpl)` sets no `ETag`, `Cache-Control` or `Last-Modified`, and nothing in the service handles `If-None-Match` (repo-wide grep finds those headers only in `media-service`). The URL `{path}@{version}.template.json` is content-addressed by construction: the body for a given URL can only change via an out-of-band Mongo rewrite. Every client launch therefore re-downloads every card in full. `media-service/handler.go:42-46,65` already implements exactly this pattern (`public, max-age=…` + ETag + 304) for its static content, so the missing win is not a design unknown.
- [medium] `POST /api/v1/cards/refresh` has no stampede protection: N concurrent calls serialize into N full collection scans — `tcard-service/cache.go:95-107` / `tcard-service/handler.go:58` — `Load` takes `writeMu` and runs `store.ListCards` (a full COLLSCAN) while holding it. There is no singleflight/coalescing, so a burst of refreshes (or a refresh landing during the daily `RefreshLoop` load) queues on a non-context-aware `sync.Mutex`; each waiter then repeats the identical scan. `cache_test.go` has a concurrent-read test (`:185`) but no concurrent-`Load` coalescing test.
- [medium] `http.Server` is missing `ReadHeaderTimeout`, `IdleTimeout` and `MaxHeaderBytes` — `tcard-service/main.go:124-129` — only `ReadTimeout`/`WriteTimeout` (10s) are set. `user-service/httpserver.go:18-22`, `search-service/main.go:315-318` and `upload-service/main.go:205` all set the full set. Slowloris header-trickling and unbounded idle keep-alives grow goroutines/buffers with no ceiling.
- [medium] No admission control on a service whose building blocks exist in-repo — `tcard-service/main.go:112-121` — the middleware chain uses `ginutil.CORS/RequestID/AccessLog` and `cfg.HTTP.Middleware()` but not `ginutil.MaxConcurrency` (`pkg/ginutil/limit.go:20`) or `ginutil.LimitListener` (`pkg/ginutil/listener.go:15`), both of which `user-service/routes.go:25` and `user-service/main.go:398` adopt. There is no bound on in-flight requests, so a listing burst is absorbed only by the Go scheduler.
- [medium] No response compression on a JSON-only service — `tcard-service/main.go:112-121` — `ginutil.Gzip` (`pkg/ginutil/gzip.go:44`, pooled `BestSpeed` encoder, already used at `user-service/routes.go:26`) is not wired. Adaptive-card templates and the `listResponse` arrays are highly compressible text; this is pure egress waste on every uncached fetch.
- [low] `ListCards` uses an *exclusion* projection, i.e. a near-whole-document fetch — `tcard-service/store_mongo.go:40-43` — `SetProjection(bson.D{{"_id",0},{"migratedAt",0}})` on `Find(ctx, bson.D{})`. The inline comment at `:38-39` justifies it (templates are schemaless), so I do not score it a violation. The same `Find` sets no `BatchSize` and no row cap: the whole catalog is materialised twice (`[]card` at `:49` plus the map at `cache.go:112`) with a per-doc `bson.D` decode + `MarshalExtJSON` re-render (`:92`).
- [low] The refresh endpoint's effective deadline (10s) is 6× tighter than the background loader's (60s) — `tcard-service/cache.go:16` vs `pkg/ginutil/timeoutconfig.go:18` — `cache.Load` wraps with `cacheLoadTimeout = time.Minute`, but on the HTTP path the parent already carries `REQUEST_TIMEOUT` (10s) and `context.WithTimeout` keeps the earlier deadline. Once the catalog scan exceeds 10s, `POST /refresh` returns 500 forever while the daily `RefreshLoop` still succeeds — a silent operational cliff.
- [low] Every suffix-less GET and every `/validate` does a full O(total-entries) snapshot scan with fresh allocations — `tcard-service/cache.go:161-219` (`List`: map+slice alloc, `sort.Slice` with `parseSemver` re-parsed inside the comparator) and `cache.go:73-85` (`Versions`). Fine for a bounded catalog, but it is linear in catalog size on a client-facing path with no memoisation.

### Recommendations

- [high] Emit `ETag` (e.g. a hash computed once in `cache.replace`) and `Cache-Control: public, max-age=…, immutable` at `tcard-service/handler.go:100`, and answer `If-None-Match` with 304 — mirror `media-service/handler.go:42-76`. This removes essentially all steady-state template traffic and is by far the largest available win.
- [medium] Wrap `cardCache.Load` in singleflight-style coalescing (or have `HandleRefresh` join an in-flight load instead of queueing behind `writeMu`) — `tcard-service/cache.go:95-107` — so a refresh burst costs one scan, not N.
- [medium] Add `ReadHeaderTimeout: 5s`, `IdleTimeout: 60s`, `MaxHeaderBytes: 16<<10` to the server at `tcard-service/main.go:124-129`, matching `user-service/httpserver.go:18-22`.
- [medium] Wire `ginutil.MaxConcurrency` + `ginutil.LimitListener` (and an env knob for each) at `tcard-service/main.go:120` / around `ListenAndServe` at `:134`, following `user-service/routes.go:25` and `main.go:398`, so overload sheds with 429 rather than degrading unboundedly.
- [medium] Wire `ginutil.Gzip(cfg.HTTP.GzipMinBytes)` into the chain at `tcard-service/main.go:119` — same pattern and default (1024) as `user-service/config/config.go:50`.
- [low] Bound and shape the loader: set `SetBatchSize` on the `Find` at `tcard-service/store_mongo.go:43`, and either raise `REQUEST_TIMEOUT` for this service or drop `cacheLoadTimeout` to match it (`cache.go:16`) so the HTTP and background refresh paths agree.
- [low] Precompute the sorted per-prefix listing and the per-path version list inside `cache.replace` (`tcard-service/cache.go:111-124`) so `List`/`Versions` become map lookups instead of full scans + a sort per request.

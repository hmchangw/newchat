**Overall score:** 3.7 / 5 (baseline 2026-09-01: 3.7, Δ -0.0)  
**Method:** six independent expert reviews (one per dimension) against `CLAUDE.md` and Go-at-scale practice; every finding cites `file:line` on this tree.

## Executive summary

translation-service is the only service in the fleet at or above the 80% coverage floor, and its suite is genuinely good: 97% on everything outside `main`, real error and edge paths, a 5XX classified before the body is parsed so an error response carrying stream data cannot leak a translation, and a mid-stream transport drop driven through a hijacked connection. The service is small, readable and cleanly seamed. Its problems are all about what happens when the upstream provider misbehaves. It is the only request/reply service in the repository with an admission cap and no per-request deadline — the shared router package documents the guarded constructor as existing precisely so a service cannot apply half the protection, and this is the half it skips. Worst case a handler holds its slot for about seventy seconds, which exceeds the shutdown budget, so in-flight requests survive graceful shutdown and are killed at the grace period. An access-token outage is worse: the token fetch runs under a plain mutex that is not context-aware and caches nothing on failure, so a hundred admitted handlers queue behind it one at a time and one slow dependency becomes a full service outage that drains for minutes. Both outbound clients keep the standard library's default of two idle connections per host against a hundred-way concurrency cap, so nearly every call pays a fresh handshake, and the stream reader has no size limit at all — a runaway upstream response is buffered whole. Upstream auth rejection is detected by a free-text substring rather than the HTTP status, so a differently-worded 401 never triggers the refresh-and-retry and surfaces as an internal error. Finally, the language vocabulary lives in this service while user-service validates only tag shape, so a user can persist a language that makes every subsequent translate call fail.

## 2. Code quality — score 4

### Evidence

- [medium] Overload guard is half-applied: admission cap without a per-request timeout — `translation-service/main.go:112-116` — the service builds `natsrouter.Default` + `WithMaxConcurrency` but never `router.Use(natsrouter.HandlerTimeout(...))`. `pkg/natsrouter/guard.go:57-63` documents `DefaultGuarded` as existing precisely "so a service can't apply only half the overload protection". Every other req/reply service pairs them (`room-service/main.go:395`, `media-service/main.go:96`, `bot-room-service/main.go:147`, `room-worker/main.go:285` via `DefaultGuarded`; `user-service/main.go:263`, `user-presence-service/main.go:173` via explicit `HandlerTimeout`). translation-service is the only one with a cap and no timeout, so a slow third-party backend holds each of the 100 slots for the full 30s resty timeout while callers have already given up.
- [medium] Upstream auth rejection is detected only by a free-text body substring, ignoring HTTP status — `translation-service/translator_stream.go:163-169`, `:178-185` — `translateOnce` classifies only 429 and 5XX by status; every other non-2xx falls into the SSE read loop and is auth-detected solely via `strings.Contains(msg, "failed to verify jwt")`. A 401/403 with any other wording never triggers the token refresh-and-retry at `:68-80` and surfaces as the untyped `fmt.Errorf("translate backend error (status %d)")` at `:168`, which collapses to `internal` at the boundary — a token-expiry outage would read as "our bug" on dashboards rather than `upstream_unavailable`/auth.
- [low] `readErr == io.EOF` instead of `errors.Is` — `translation-service/translator_stream.go:153` — CLAUDE.md §3 requires `errors.Is`/`errors.As` for error identity. If any layer under `resp.RawBody()` ever returns a wrapped EOF, a fully-read stream is misclassified as `errcode.Unavailable` at `:158` and a successful translation is thrown away. One-line fix, no behaviour change today.
- [low] Two contradictory `#nosec G304` annotations on one statement — `translation-service/j1source.go:26-27` — the second ("developer-supplied path in dev tooling") is a copy-paste artifact that contradicts the first and describes a different justification. This is the only doubled `#nosec` in the repo (all 16 other sites carry exactly one). The suppression itself is legitimate; the stale second line makes the review record ambiguous.
- [low] Shared token fetch runs on one caller's request context — `translation-service/token.go:84`, `:101-115` — `Token`/`Refresh` pass the calling handler's ctx into `fetchLocked` while holding `p.mu`, so the winner's cancellation aborts a fetch that every queued handler is waiting on. Latent today (no `HandlerTimeout`, so ctx has no deadline) but becomes live the moment the finding above is fixed. A detached ctx with the 5s cap from `:59-62` would be safer.
- [low] Transport failures are logged twice — `pkg/restyutil/restyutil.go:79-80` + `translation-service/translator_stream.go:98-103` — `restyutil`'s `OnError` emits `slog.Error("http error", …)`, then the returned `errcode.Unavailable` is logged again by `Classify` at the reply boundary. Inherited `pkg/` behaviour, not this service's code, but it is the "never log AND return" pattern CLAUDE.md warns about and it doubles the error rate this service appears to have.
- [nitpick] `fmt.Errorf` with no format verbs — `translation-service/token.go:124`, `translation-service/translator_stream.go:171` — should be `errors.New`; also `main.go:61` wraps verb-first (`"%w when TRANSLATION_BACKEND=stream"`) rather than leading with what the function was doing.

### Recommendations

- [medium] Switch to `natsrouter.DefaultGuarded` with a `GuardConfig{MaxConcurrency, RequestTimeout}` — `translation-service/main.go:112-116` — adopts the repo's guard helper, bounds slot occupancy, and removes the only cap-without-timeout service in the fleet. Add a `TRANSLATION_REQUEST_TIMEOUT` sized below the caller's NATS request budget and above the 30s resty timeout's intended ceiling (i.e. lower both together).
- [medium] Classify 401/403 by status before the body sniff — `translation-service/translator_stream.go:109-118` — treat a 401/403 as `jwtFailed=true` (refresh once), keep the substring check as a fallback for a 200-with-error-body, and map remaining 4xx to a typed `errcode` rather than letting them collapse to `internal`.
- [low] Replace `readErr == io.EOF` with `errors.Is(readErr, io.EOF)` — `translation-service/translator_stream.go:153`.
- [low] Delete the second `#nosec` line — `translation-service/j1source.go:27` — keep only the accurate operator-configured-mount justification.
- [low] Pass a detached, timeout-bounded context to `fetchLocked` — `translation-service/token.go:84,96` — so one cancelled caller cannot fail the shared refresh for everyone once a handler timeout exists.
- [nitpick] Use `errors.New` for the two constant-message `fmt.Errorf` calls — `translation-service/token.go:124`, `translator_stream.go:171`.

## 3. Architecture — score 4

### Evidence

- [high] Only request/reply service in the repo with no per-request deadline — `main.go:116` — it builds the router with `natsrouter.Default`, which documents that `HandlerTimeout` is "intentionally omitted ... Add it explicitly" (`pkg/natsrouter/router.go:135-136`). Every peer applies one: `DefaultGuarded` (room-service, media-service, room-worker, bot-room-service, bot-message-handler), `Guard.TimeoutMiddleware()` (history-service:393, search-service:297), or `HandlerTimeout` directly (user-service:263, user-presence-service:173). `pkg/natsrouter/guard.go:57-62` exists explicitly "so a service can't apply only half of the overload protection" — this service applies exactly the half it warns about (cap yes, deadline no).
- [high] `Translator`'s documented contract ("callers pass a context with a deadline", `translator.go:8`) is violated by its only caller — `handler.go:37` — the handler passes the raw `*natsrouter.Context`, whose ctx originates from `nc.QueueSubscribe(context.Background(), …)` (`pkg/natsrouter/router.go:295`) and carries no deadline. Worst case one handler runs token(≤5s) + translate(≤30s) + refresh(≤5s) + translate(≤30s) ≈ 70s (`translator_stream.go:58-82`, `token.go:59-62`, `main.go:36`), bounded only by resty. That exceeds the 25s shutdown budget (`main.go:121`), so in-flight handlers survive `router.Shutdown` and are SIGKILLed at the k8s 30s grace.
- [high] Access-token outage serializes every in-flight request behind an uncancellable mutex — `token.go:77-84`, `token.go:101-131` — `fetchLocked` runs under `p.mu` and only populates the cache on success (`token.go:130`), so there is no negative caching. With the token endpoint failing/hung, each of the 100 admitted handlers takes the lock in turn for up to 5s. `sync.Mutex.Lock` is not ctx-aware, so even adding `HandlerTimeout` would not release a waiter. Net effect: one upstream dependency being slow converts into a full translation-service outage that drains for minutes. `token_test.go:173` covers only the concurrent-*success* path; no failure-fan-in test exists.
- [medium] `MAX_CONCURRENCY` is re-declared with its own `envDefault` instead of mounting the owning package's config — `main.go:41` (`envDefault:"100"`) vs `pkg/natsrouter/guard.go:21` (`envDefault:"256"`). CLAUDE.md §6 Configuration: a knob shared by more than one service is declared once in the owning package and mounted as a named field. Mounting `Guard natsrouter.GuardConfig` would fix this finding and the two above in one change.
- [low] A fake backend ships inside the production binary and is runtime-selectable — `translator.go:15-19`, `main.go:50-51` — `TRANSLATION_BACKEND=mock` returns `"[zhTW] Hello"` to real clients. It is `required` so a *missing* var fails fast (`main.go:29`), but a copy-paste from `deploy/docker-compose.yml:27` (which ships `TRANSLATION_BACKEND=mock`) degrades silently instead of loudly.
- [nitpick] Stale comment references a file that does not exist — `integration_test.go:38-39` — "routes_test.go pins it to a golden file"; there is no `routes_test.go` in the service.

Verified correct (so the synthesizer does not re-check): interface in the consumer with only the method it needs (`translator.go:9`), mockgen'd; constructor DI, handler holds one dep (`handler.go:14-20`); single registration table in `main.go:131`, matching the NATS-router peers (user-presence-service:212, room-worker:418) — `routes.go` is a Gin-only rule; `errors.As` in `errcode/classify.go:17` means the typed `Unavailable`/`TooManyRequests` from `translator_stream.go:101,110,116,158` survives the handler's `fmt.Errorf` wrap with its reason intact; baggage stripped at both third-party egress points (`translator_stream.go:90`, `token.go:104`); `pkg/shutdown.Wait` in the documented order (`main.go:121-125`).

### Recommendations

- [high] Replace `main.go:41` + `:112-116` with `Guard natsrouter.GuardConfig` and `natsrouter.DefaultGuarded(nc, "translation-service", cfg.Guard, natsrouter.WithSiteID(...), natsrouter.WithMetrics(...))` — one change fixes the missing deadline, the half-applied guard, and the re-declared knob, and restores the fleet-wide `REQUEST_TIMEOUT`/`MAX_CONCURRENCY` defaults.
- [high] Make `REQUEST_TIMEOUT` < `TRANSLATION_HTTP_TIMEOUT` a validated invariant at startup (`main.go:70`, next to the existing positive-timeout check) — otherwise the new deadline is dead code on the translate leg, the way `user-service/config/config.go:243` guards WriteTimeout > HandlerTimeout.
- [high] Give `tokenProvider` ctx-aware single-flight and negative caching — `token.go:77-97` — e.g. a 1-slot channel acquired with `select { case <-ctx.Done(): … }`, plus caching the failure for a short cooldown so N waiters see one failed exchange instead of N serialized 5s ones. Without this, an accessToken outage still saturates the admission cap regardless of any handler deadline.
- [medium] Map `context.DeadlineExceeded` to `errcode.Unavailable(..., WithReason(TranslateUpstreamUnavailable))` in `handler.go:38-40`, as `pkg/natsrouter/middleware.go:170-179` prescribes — otherwise every timed-out request reaches the client as a generic `internal` and the existing `upstream_unavailable` reason under-reports the real failure mode.
- [low] Move `mockTranslator` behind an explicit non-production marker or drop it once `stream` is the deployed backend — `translator.go:15`, `main.go:50` — so a mis-set `TRANSLATION_BACKEND` cannot serve `[lang] text` to users; tests can keep a local fake in `_test.go`.

## 5. Maintainability — score 4

### Evidence

This is the one change in the service that is a refactor rather than an addition.

There is no `routes_test.go` in the service (nor anywhere in the repo; that string appears only in this comment). - [low] Contradictory duplicated suppression justifications on one statement — `translation-service/j1source.go:26-28` — two `#nosec G304` lines with mutually exclusive reasons ("operator-configured token mount, not user input" vs "developer-supplied path in dev tooling, not attacker-controlled"), plus a `nosemgrep`. - [nitpick] `translator_stream_test.go` is 374 lines of 16 near-identical one-off `httptest.NewServer` cases (`:131`, `:149`, `:169`, `:181`, `:279`, `:296`, `:329`, `:349`) despite `sseServer`/`streamTranslatorTo` helpers existing at `:24` and `:47`. ## 6. Integration — score 3

### Evidence

- [high] `MAX_CONCURRENCY` is re-declared in the service config with a divergent default instead of mounting the owning package's knob — `translation-service/main.go:41` (`envDefault:"100"`) vs `pkg/natsrouter/guard.go:21` (`envDefault:"256"`). `natsrouter.GuardConfig` is the declaring package for this knob and is mounted as a named field by `room-service/main.go:61`, `media-service/config.go:110`, `history-service/internal/config/config.go:84`, `search-service/main.go:136`, `room-worker/main.go:54`. CLAUDE.md §6 Configuration forbids re-declaring a shared knob's env tag/default; the defaults have already diverged. `GuardConfig.Validate` (`guard.go:29-31`) also rejects a negative value — here a negative `MAX_CONCURRENCY` silently falls through `main.go:113` and disables the cap.
- [high] Only half the overload guard is applied: the admission cap without the companion request timeout — `translation-service/main.go:112-117`. No `HandlerTimeout` is installed anywhere in the service (grep for `HandlerTimeout|REQUEST_TIMEOUT` under `translation-service/` is empty), so the handler context carries no deadline; `pkg/natsrouter/guard.go:56-66` documents `DefaultGuarded` as existing "so a service can't apply only half of the overload protection". Worst case one request holds its admission slot for ~70s (token 5s `token.go:60-62` + translate 30s + refresh 5s + retry 30s, `translator_stream.go:58-81`) long after the NATS requester gave up.
- [medium] The supported-language vocabulary is split across two services with no shared source — `translation-service/lang.go:12-19` accepts exactly `en|de|ja|zh(+script/region)`, while `user-service/service/settings.go:88` validates `settings.translateMessageInto` only for tag *shape* (`translateTagRe`, `settings.go:20`). A user can persist `fr`, `ko` or a bare `zh`, and every subsequent translate RPC then fails `bad_request`/`unsupported_lang`. `lang.go` is service-local, so `user-service` has no way to validate against it.
- [medium] The wire contract is asserted only behind `//go:build integration`, which no pipeline runs — `translation-service/integration_test.go:1,30-79` is the only test that exercises the registered subject (`subject.TranslateRequest`) and the reply envelope, and `translation-service/deploy/azure-pipelines.yml:44` runs untagged tests only (other services, e.g. `data-migration/oplog-connector/deploy/azure-pipelines.yml:48`, do pass `-tags=integration`). A wrong subject or a changed envelope shape would ship green.
- [medium] The J2 token cache has no minimum-validity floor and no negative caching — `token.go:126-130` stores `expiresAt - skew` verbatim. If the provider returns a short (or already-past, relative to `TRANSLATION_TOKEN_SKEW=60s`) `expiresAt`, every request misses the cache and serializes behind `p.mu` (`token.go:77-84`), turning the concurrency cap into effective single-file processing against the auth endpoint. `token_test.go:53-70` pins the refetch behaviour but nothing bounds the refetch rate.
- [low] Stale comment references a `routes_test.go` golden file that does not exist — `translation-service/integration_test.go:38-39`. There is no `routes_test.go` and no `testdata/` in the package (`ls translation-service/`), so the registration table is not in fact pinned by a golden.
- [nitpick] `zh-MY` resolves to Simplified (`lang.go:42`) but is absent from the documented resolution table — `docs/client-api.md:6293-6297`. The table is labelled "example tags", so this is a completeness gap, not a mismatch.

### Recommendations

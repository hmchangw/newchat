# notification-worker — production readiness review

**Date:** 2026-09-21  
**Branch:** `claude/production-readiness-report-2026-09-21` @ `2155c60` (base `main`)  
**Overall score:** 3.2 / 5 (baseline 2026-09-01: 3.2, Δ -0.0)  
**Method:** six independent expert reviews (one per dimension) against `CLAUDE.md` and Go-at-scale practice; every finding cites `file:line` on this tree.

## Executive summary

notification-worker's fan-out core is well engineered — error tiering, sonic on the hot path, projected reads, `jsretry.Settle` everywhere, and consumer-defined interfaces that make gates easy to swap — but four independent reviewers converged on the same shutdown bug and the same bootstrap defect. The ROOMS invalidation consumer goroutine is tracked by no WaitGroup, and shutdown calls `invalIter.Stop()` then immediately `close(invalCh)`, so a message already returned by `Next()` sends on a closed channel and panics, skipping the NATS drain and every database disconnect. The dev bootstrap hands `bootstrapStreams` the `.created` leaf instead of the `pkg/stream` schema, so with `BOOTSTRAP_STREAMS=true` a notification-worker restart narrows the shared MESSAGES-CANONICAL stream and history-service's edit/delete/pin publishes fail until another service re-widens it (production is unaffected). Beyond those: `PRESENCE_RPC_ENABLED=true` calls a snapshot RPC that no service serves, so DND suppression can never engage and the contracts doc still says "flip once live"; that same ops doc tells operators to provision a 5-minute duplicate window when the service refuses to start under 1 hour; the second consumer is hand-rolled inline in a 359-line `main()` bypassing `DurableConsumerDefaults`; per-message dependency timeouts sum well past `AckWait` with no overall deadline; `MONGO_URI` is defaulted while `WithDegradedStart` removes the fail-fast backstop; and the room-meta L2 tier is built with a nil breaker, unlike both sibling hot-path services. Coverage is 59.5% only because `main` holds 30% of the statements — everything else sits at 84.8% — but the consume loop, invalidation loop and shutdown sequence have no test at any tier, and the history parent fetcher is a verbatim copy of broadcast-worker's.

## 2. Code quality — score 4

### Evidence

- [medium] Shutdown race: untracked invalidation reader can send on a closed channel and panic — `notification-worker/main.go:305-326` vs `main.go:417-421` — The reader goroutine is in no WaitGroup. Step 3 calls `invalIter.Stop()`, step 4 immediately `close(invalCh)`; a message already returned by `Next()` (line 307) that reaches `invalCh <- evt.RoomID` (line 319) after the close panics — `select`/`default` does not protect a send on a closed channel. Shutdown-only and narrow, but the panic skips the remaining steps (NATS drain, Mongo/Valkey disconnect, obs flush).
- [medium] Per-message logs are not trace-correlated: 37 non-`Context` slog calls vs 2 `*Context` — `handler.go:247,332,387,497`, `presence.go:76,83,87,95`, `usersettings.go:107` — The o11y logger installed by `pkg/obs/obs.go:228-230` correlates trace/span ids only through the ctx passed to `Handle`; `slog.Warn(...)` passes `context.Background()`, so every in-pipeline warning is orphaned from its span. Siblings use `*Context` almost everywhere (broadcast-worker 32/39, message-worker 24/26). `presence.go:76-95` also carry no `request_id` at all.
- [medium] Connection string and secret defaulted, and `WithDegradedStart` removes the fail-fast backstop — `main.go:41` (`MONGO_URI` → localhost), `main.go:44` (`MONGO_PASSWORD` → ""), `main.go:120` — CLAUDE.md: never default connection strings/secrets. With `mongoutil.WithDegradedStart()` (`pkg/mongoutil/mongo.go:39-41`, "return a usable client on an unreachable MongoDB") a pod missing `MONGO_URI` starts "healthy" against localhost and NAKs every cold-room message for the outage budget instead of exiting. Repo-wide pattern (`broadcast-worker/main.go:53,56`), but this service's degraded start makes it bite.
- [low] Log-AND-return on batch emit failure — `handler.go:332-335`, then `main.go:376` → `pkg/jsretry/jsretry.go:137-138` — The per-batch `slog.Error` fires, then `jsretry.Settle` logs "message failed — retrying" with the aggregate whose text already embeds each `emit push batch N: …` (`handler.go:335,350`). One failure, two ERROR lines.
- [low] Ack errors silently discarded without the required comment — `main.go:314`, `main.go:324` — The same file logs ack failures on the migration path (`main.go:369-371`) and `jsretry.settle` logs them; these two are the odd ones out.
- [low] Bare `err` returned from the publisher adapter — `emit.go:88-92` — `jsPublisher.PublishMsg` records the metric and returns `err` unwrapped. The caller wraps at `emit.go:62`, so nothing is lost on the wire, but the per-function rule is broken.
- [nitpick] `errcode.Parse` used without the `Code.Valid()` guard the sibling clients apply — `presence.go:86` vs `badge_client.go:56`, `parent_fetcher.go:82` — Safe today (a `PresenceSnapshotReply` has no top-level `error` key), but three RPC clients should share one envelope check.
- [nitpick] Redundant loop-variable copy — `presence.go:70` (`ch := ch`) — go.mod is Go 1.25; `handler.go:383` correctly omits it.
- [nitpick] Two startup failures log the identical message "invalid config" — `main.go:94`, `main.go:98` — pool vs breaker validation are indistinguishable.
- [nitpick] `nosemgrep` suppression lacks the `-- <reason>` suffix the rule asks for — `badge_client.go:45` vs `.semgrep/jsnak.yml:65-66` — the justification sits on the lines above instead.
- [nitpick] Unit tests boot an in-process `nats-server` — `parent_fetcher_test.go:25-38`, reused by `badge_client_test.go` — grey against "never connect to real NATS in unit tests"; embedded (no Docker) and used repo-wide (`pkg/natsutil`, `pkg/natsrouter`, broadcast-worker), so noted, not scored.

### Recommendations

- [medium] Track the invalidation reader in a WaitGroup and wait for it between `invalIter.Stop()` and `close(invalCh)` — `main.go:305,417-421` — removes the send-on-closed-channel panic; or let the reader own `close(invalCh)` when `Next()` errors.
- [medium] Switch every in-pipeline log to `slog.WarnContext/ErrorContext(ctx, …)` and add `request_id` to the four presence lines — `handler.go:247,332,387,497`, `presence.go:76,83,87,95`, `usersettings.go:107` — restores the trace correlation the o11y handler gives for free; matches broadcast-worker/message-worker.
- [medium] Mark `MONGO_URI` `required` (drop the `""` default on `MONGO_PASSWORD`), or refuse `WithDegradedStart` when `MONGO_URI` is still the default — `main.go:41,44,120` — restores fail-fast on the one misconfiguration this service otherwise runs through silently.
- [low] Delete the per-batch `slog.Error` at `handler.go:332` (or downgrade to Debug); the aggregate returned at `handler.go:350` already reaches `jsretry.Settle`'s single log line.
- [low] Add `// ack error intentionally ignored: …` or log the failure at `main.go:314,324`, matching `main.go:369-371`.
- [low] Wrap the adapter's return at `emit.go:90-91` or move the metric call into `mobileEmitter.Emit` so the adapter is a pure pass-through by design.
- [nitpick] Extract one `parseRemoteEnvelope(data)` helper shared by `presence.go`, `badge_client.go`, `parent_fetcher.go` so all three check `Code.Valid()` identically.

## 3. Architecture — score 4

### Evidence

- [high] Dev bootstrap creates MESSAGES-CANONICAL with the `.created` leaf instead of the stream's `pkg/stream` schema — `notification-worker/bootstrap.go:32-35`, `notification-worker/main.go:195` — CLAUDE.md requires `Name + Subjects` from `pkg/stream.<Stream>(siteID)`; `stream.MessagesCanonical` binds `chat.msg.canonical.{site}.>` (`pkg/stream/stream.go:22-27`) but the helper is handed `wiring.CanonicalCreated` (`pkg/stream/pipeline.go:61`). Both compose files set `BOOTSTRAP_STREAMS=true` (`deploy/user/docker-compose.yml`, `deploy/bot/docker-compose.yml`), so a notification-worker restart after message-gatekeeper narrows the shared stream to `.created` (nats-server `updateWithAdvisory` does not reject a subject change against existing consumer filters), and `.edited`/`.deleted` canonical publishes fail until gatekeeper's bootstrap re-widens it. Production (`Enabled=false`) is unaffected. The output stream additionally sets `Compression` and `Duplicates` (`bootstrap.go:42-45`), beyond the Name+Subjects rule; the `Duplicates` window is at least load-bearing and verified on the disabled path (`bootstrap.go:58-74`).
- [medium] Shutdown race in the invalidation loop: send on a closed channel — `notification-worker/main.go:305-326`, `:417`, `:421` — the ROOMS-consumer goroutine is untracked by any WaitGroup; shutdown calls `invalIter.Stop()` and then immediately `close(invalCh)`. A message `Next()` returned just before `Stop()` is still being decoded, then hits `select { case invalCh <- evt.RoomID: ... default: }` — a send on a closed channel panics even with a `default` arm — and the panic skips `natsutil.Drain`, Mongo/Valkey disconnect and `obsShutdown`. The main loop explicitly guards this by counting itself in `wg` (`main.go:338-343`); the second loop does not.
- [medium] Second consumer hand-rolled in `main.go`, bypassing `stream.DurableConsumerDefaults`, with its consume loop living in `main.go` — `notification-worker/main.go:290-295`, `:305-326` — the ROOMS durable gets a bare `ConsumerConfig` (no derived `BackOff`, no `MaxDeliver`/`MaxAckPending`, so unlimited redelivery on default `AckWait`), and the decode/dispatch logic sits in `main.go` rather than `handler.go`, where nothing unit-tests it (`handler_test.go` has no coverage of it; only the primary loop's `buildConsumerConfig` is tested in `consumer_config_test.go`). CLAUDE.md scopes `main.go` to config, wiring, startup and shutdown.
- [low] A server-to-server dependency rides the client lane under a borrowed identity — `notification-worker/parent_fetcher.go:130` — the parent fetch requests `subject.MsgGet(account, …)` = `chat.user.{account}.request.…` on behalf of the reply sender, whereas the badge RPC uses an explicit server lane (`badge_client.go:50`, `chat.server.request.user.…`). history-service enforces the sender's subscription/access window (`history-service/internal/service/messages.go:425-437`, `utils.go:57` returns `Forbidden`), so follower/parent-author notifications depend on the sender still being a member at fetch time; a terminal reply after two deliveries is Ack-dropped (`handler.go:183-186`).
- [low] Presence status literals duplicated across the boundary — `notification-worker/presence.go:142` — hardcodes `"busy"`/`"in-call"` although `pkg/model/presence.go:24,27` defines `StatusBusy`/`StatusInCall`; the two lists can drift silently.
- [low] Dead extension seam: `Vetoer` is only ever `noopVetoer{}` — `notification-worker/main.go:265`, `hook.go:16-20` — no other implementation exists in the repo, yet the interface call runs per member in the hot loop (`handler.go:245`).
- [nitpick] Exported surface in `package main` and no `store.go` — `notification-worker/handler.go:36-68`, `routing.go:10`, `threads.go:21`, `usersettings.go:202` — `Handler`, `NewHandler`, `HandlerDeps`, `EligibleForPush`, `MemberCache` etc. are exported though nothing can import them; consumer-defined interfaces (correct) are spread across six files and Mongo implementations live in `threads.go`/`usersettings.go` rather than `store_mongo.go`.

### Recommendations

- [high] Pass `wiring.CanonicalStream.Subjects` (from `pkg/stream`) to `bootstrapStreams` for the input stream instead of the `.created` leaf — `notification-worker/main.go:195`, `bootstrap.go:32-35` — the consumer's `FilterSubjects` already narrows to `.created`; the stream schema must stay the one every canonical publisher/consumer agrees on. Add a test asserting the created `Subjects` equal `stream.MessagesCanonical(site).Subjects`.
- [medium] Track the invalidation goroutine with `invalWG` (or a dedicated WaitGroup) and wait on it between `invalIter.Stop()` and `close(invalCh)` — `notification-worker/main.go:305`, `:417-421` — removes the send-on-closed-channel panic and makes the second loop's shutdown as deterministic as the primary loop's.
- [medium] Derive the ROOMS consumer from `stream.DurableConsumerDefaults(cfg.Consumer)` with `Durable`/`FilterSubjects`/`DeliverPolicy=New` overridden, and move the decode/dispatch body into a small `invalidationHandler` in `handler.go` (or `invalidate.go`) with a unit test — `notification-worker/main.go:290-326` — same backoff/ack-pending discipline as the primary consumer, and the logic becomes testable without NATS.
- [low] Introduce a `chat.server.request.…msg.get` subject (or an internal history RPC) for the parent fetch so the worker no longer depends on the sender's client-side access rights — `notification-worker/parent_fetcher.go:130`, `pkg/subject/subject.go:131` — aligns with how `BadgeCountBatch` already separates server-to-server traffic.
- [low] Use `model.StatusBusy`/`model.StatusInCall` in `isInCall` — `notification-worker/presence.go:142` — one source of truth for the suppressing statuses.
- [low] Either delete the `Vetoer` seam or document the planned implementation — `notification-worker/hook.go`, `main.go:265` — YAGNI on a hot path.
- [nitpick] Unexport the handler surface and consolidate the consumer-defined interfaces into `store.go` per the documented per-service layout — `notification-worker/handler.go:36-68` and siblings.

## 7. Performance — score 4

### Evidence

- [medium] Invalidation consumer goroutine is untracked and can send on a closed channel at shutdown — `notification-worker/main.go:305-326`, `main.go:417-421` — the goroutine is in no WaitGroup; step 3 calls `invalIter.Stop()` and step 4 immediately `close(invalCh)`. A message already returned by `Next()` (Stop only closes `done`, `jetstream/pull.go:769-773`) that is between decode and `invalCh <- evt.RoomID` panics on the closed channel, aborting the remaining Drain/disconnect steps. Microsecond window, but real.
- [medium] Per-message dependency timeouts sum well past AckWait, with no overall per-message deadline — `handler.go:141-297` — GetMembers 10s (`pkg/roomsubcache/lookup.go:151`) → `Followers.Lookup` with no timeout at all (`threads.go:41`) → parent 2s (`parent_fetcher.go:19`) → settings 2s → presence 2s → badge 5s (`badge_client.go:19`) → room meta 10s (`pkg/roommetacache/roommetacache.go:34`) → mention names 2s → N sync publishes. Effective AckWait is 30s (`pkg/stream/consumer.go:19`), so a degraded run is redelivered while attempt 1 still executes: duplicate concurrent work (emits deduped by `Nats-Msg-Id`, badge bump is a SADD, so no user-visible damage) that doubles downstream load and burns ack-pending slots exactly when the system is slow.
- [medium] Room-meta L2 tier is built with a nil breaker — `main.go:157-158` — both sibling hot-path services guard the same tier (`message-gatekeeper/store_mongo.go:36`, `broadcast-worker/store_mongo.go:68`) and this service guards its own member loader (`main.go:174-177`). During a Mongo outage every L1 miss and every stale-window refresh (`pkg/valkeyutil/readthrough.go:180` calls `Load` synchronously) waits out `MONGO_SERVER_SELECTION_TIMEOUT` (2s, `pkg/mongoutil/poolconfig.go:49`) inside a worker slot. Fail-open, but the one unguarded Mongo read on the path.
- [low] Settings and presence snapshots run serially though independent — `handler.go:270-271` — both fail-open with their own 2s bound; serial execution adds up to 2s avoidable tail latency per message.
- [low] Push batches are published serially with a sync JetStream publish each — `handler.go:316-337`, `emit.go:61` — an `@all` in a 10k-member room is 100 sequential broker round trips holding one of `MAX_WORKERS` slots. The `{messageID}-b{N}` dedup key already makes concurrent publish safe.
- [low] Full member list is re-fetched and re-decoded from Valkey on every message with no process-local tier — `handler.go:141` → `pkg/roomsubcache/lookup.go:217` → `roomsubcache.go:207` → `pkg/valkeyutil/valkey.go:367` (`json.Unmarshal`, blob up to 16MB) — documented as deliberate (`lookup.go:160-161`), but a hot 5k-member room at 10 msg/s is ~50k `Member` (88B) decodes/s per pod.
- [low] Very large `@all` fan-out degrades unevenly — `usersettings.go:100-111` runs 512-account chunks sequentially under one shared 2s deadline (late chunks fail open → muted users pushed; documented), while `presence.go:69-104` spawns one unbounded goroutine per chunk (250k accounts ≈ 490 concurrent RPCs per message).
- [nitpick] `isRestricted` takes `model.Message` (312 bytes, measured) by value per member and is not inlined (`cannot inline isRestricted: cost 119 exceeds budget 80`) — `handler.go:222`, `handler.go:431` — the `//nolint:gocritic // hugeParam ... pointer indirection adds no benefit` justification is backwards: 312B copied per member per message.
- [nitpick] sonic pretouch list omits `BadgeCountBatchRequest/Response`, `getMessageByIDRequest`, `parentMessageProjection` — `pretouch.go:11-17` — their JIT compile lands on the first message instead of at startup.
- [nitpick] `batchAccounts` copy per batch is unnecessary (sonic.Marshal does not retain) and `siteByAccount` is sized `len(members)` even when badge is disabled — `handler.go:321-322`, `handler.go:213`.

### Recommendations

- [medium] Track the invalidation goroutine in a WaitGroup and wait on it after `invalIter.Stop()` and before `close(invalCh)` — `main.go:305-326`, `main.go:416-432` — removes the send-on-closed-channel panic and gives the goroutine a waited termination path.
- [medium] Wrap `handler.HandleMessage` in a per-message `context.WithTimeout` below effective AckWait (e.g. 20s) at `main.go:376`, and bound `mongoThreadFollowers.Lookup` like `usersettings.go:97` — guarantees attempt N finishes or NAKs before the server redelivers it.

- [low] Publish batches concurrently (bounded `errgroup`, or `PublishMsgAsync` + `PublishAsyncComplete`) keeping the per-batch error aggregation — `handler.go:316-337` — large-room `@all` stops serializing 100 RTTs per slot.
